/proc/PID/pagemap: Reading Your Own Page Tables

After reading this chapter, you will be able to inspect the Linux kernel’s low-level virtual memory state directly from user space. You will know how to decode /proc/PID/pagemap 64-bit entries into page-level metadata, track lazy physical allocation via demand paging, observe copy-on-write sharing across forks, and use the kernel’s soft-dirty tracking to capture runtime memory writes, and spot kernels where it is compiled out.

Version note: verified on Linux 6.12 on an x86-64 system as an unprivileged user.

Architecture and Paging Context

Modern x86-64 processors translate virtual addresses into physical DRAM locations through hardware page tables managed by the kernel. Under traditional 4-level paging, the CPU implements a 48-bit virtual address space, capable of addressing 256 TiB, divided evenly into user space in the lower half and kernel space in the canonical upper half. Systems with 5-level paging expand the virtual address width to 57 bits (addressing up to 128 PiB) by introducing a fifth table level (the Page Global Directory or PGD feeds into the P4D, followed by the PUD, PMD, and PTE levels). The base unit of virtual memory mapping on x86-64 is the 4 KiB base page, alongside support for 2 MiB large pages and 1 GiB huge pages.

When an application calls malloc(), mmap(), or expands its heap, the Linux kernel does not immediately allocate physical RAM. Instead, it creates or expands a Virtual Memory Area (VMA), visible in /proc/PID/maps. The corresponding Page Table Entries (PTEs) remain empty. Physical memory allocation is deferred until the CPU attempts to read from or write to the virtual page. This hardware exception—a demand page fault—causes the kernel’s fault handler to locate an available physical page frame, zero it if anonymous, populate the hardware PTE, and resume application execution transparently.

While higher-level diagnostic tools like ps, top, and /proc/PID/status expose aggregate resident set sizes (RSS), they cannot show per-page states. /proc/PID/pagemap bridges this gap by letting user-space applications inspect the exact state of every single virtual page in their address space.

The /proc/PID/pagemap File Format

The /proc/PID/pagemap file exposes a binary stream where every virtual page corresponds to exactly one 64-bit integer formatted in target-architecture byte order (little-endian on x86-64).

To inspect the status of a virtual address vaddr, you do not parse lines of text. Instead, you divide the virtual address by the system page size (sysconf(_SC_PAGE_SIZE), typically 4096 bytes) to find the virtual page index, multiply by 8 bytes per entry, and seek to that absolute byte offset:

\[\text{offset} = \left(\frac{\text{vaddr}}{\text{PAGE\_SIZE}}\right) \times 8\]

Each 64-bit value is an encoding of hardware PTE status and Linux-specific memory management flags.

Bit Range Flag Name Description
0–54 PFN or Swap Info If bit 63 is set (present), bits 0–54 contain the Page Frame Number (PFN). If bit 62 is set (swapped), bits 0–4 encode the swap type and bits 5–54 encode the swap offset.
55 Soft-dirty Set if the page has been modified since the soft-dirty tracker was reset via /proc/PID/clear_refs.
56 Exclusively mapped Set if the page is mapped exclusively to this process (since Linux 4.2). Cleared when shared across fork() copy-on-write boundaries.
57 uffd-wp Set if the page table entry is write-protected and monitored by userfaultfd (since Linux 5.13).
58 Guard region Indicates the page resides within a kernel guard region (since Linux 6.15).
59–60 Reserved Always zero.
61 File-page or shared-anon Set if the page is backed by a file or resides in shared anonymous memory (since Linux 3.5).
62 Swapped Set if the page has been swapped out to disk or compressed into zswap.
63 Present Set if the page is currently resident in physical memory (RAM).

Security and Rowhammer Mitigation

Historically, any process could read its own /proc/self/pagemap file and inspect its physical frame numbers (bits 0–54). In 2015, security researchers demonstrated the Rowhammer vulnerability, which flips adjacent DRAM bits through repeated memory accesses to precise physical addresses. The PFN field in /proc/PID/pagemap provided attackers with an exact physical map of memory layout, enabling deterministic exploitation.

To mitigate this attack, the kernel security model changed: - Linux 4.0 through 4.1: Opening /proc/PID/pagemap was completely blocked for unprivileged users, returning EPERM. - Linux 4.2 onward: Unprivileged processes can open and read /proc/PID/pagemap, but the kernel sanitizes bits 0–54, setting the PFN to zero unless the reading process holds the CAP_SYS_ADMIN capability. All status flags (bits 55 through 63) remain fully functional for unprivileged callers.

Note

Not run here. Inspecting physical frame numbers (PFN) requires CAP_SYS_ADMIN or root privileges. When run under sudo, bit 63 (present) remains set, but bits 0–54 yield non-zero hardware page frame numbers reflecting the actual physical DRAM addresses mapped to the process.

Related Interfaces

Linux provides several complementary mechanisms under /proc to inspect memory layouts, each operating at a different granularity and privilege tier.

Interface Scope Granularity Privilege Required
/proc/PID/maps Virtual Address Space Per VMA (contiguous address region) Unprivileged (own process)
/proc/PID/smaps Virtual Address Space Per VMA with memory counter breakdowns Unprivileged (own process)
/proc/PID/pagemap Virtual Address Space Per 4 KiB virtual page Unprivileged (PFN zeroed without CAP_SYS_ADMIN)
/proc/kpagecount Physical Memory Per physical frame (reference count) Root (CAP_SYS_ADMIN)
/proc/kpageflags Physical Memory Per physical frame (kernel page flags) Root (CAP_SYS_ADMIN)
PAGEMAP_SCAN ioctl Virtual Address Space Batched page-range scan (introduced in Linux 6.7) Unprivileged / CAP_SYS_ADMIN
Note

Not run here. /proc/kpagecount and /proc/kpageflags expose physical page frame metadata system-wide and are readable only by root (CAP_SYS_ADMIN). According to the kernel documentation, /proc/kpagecount yields a 64-bit reference count per physical frame, indexed by PFN, while /proc/kpageflags yields a 64-bit bitmask describing page flags (such as locked, active, slab, or huge page status).

The PAGEMAP_SCAN ioctl(2) interface was merged in Linux 6.7 to solve the high overhead of reading /proc/PID/pagemap over large address spaces. Instead of streaming 8-byte entries for gigabytes of empty virtual address space, PAGEMAP_SCAN takes filter criteria (such as pages that are present and soft-dirty) and writes compacted page ranges directly to a user-provided buffer.

Inspecting Virtual Memory Ranges

Before querying /proc/PID/pagemap, you need to know which virtual addresses belong to your process. The /proc/self/maps file lists every mapped region, permissions, offset, device, and pathname.

The following command displays the process memory map entries for the heap and stack regions:

grep -E 'heap|stack' /proc/self/maps
55eda141e000-55eda143f000 rw-p 00000000 00:00 0                          [heap]
7fffb5ed7000-7fffb5ef8000 rw-p 00000000 00:00 0                          [stack]

Notice the address ranges displayed in the output. The first column defines the start and end virtual addresses in hexadecimal. To decode page metadata for any address within these ranges, pass the address into /proc/self/pagemap.

Decoding /proc/PID/pagemap in Python

The following library module, pagemap.py, opens /proc/PID/pagemap, seeks to the requested virtual page offset, and decodes the 64-bit little-endian entries into Python dictionaries.

#!/usr/bin/env python3
"""Decode /proc/PID/pagemap entries into structured dictionaries."""
import ctypes
import os
import struct
import sys

PAGE_SIZE = os.sysconf("SC_PAGE_SIZE")

def decode_pagemap_entry(val: int) -> dict:
    present = bool(val & (1 << 63))
    swapped = bool(val & (1 << 62))
    file_or_shared_anon = bool(val & (1 << 61))
    guard_region = bool(val & (1 << 58))
    uffd_wp = bool(val & (1 << 57))
    exclusive = bool(val & (1 << 56))
    soft_dirty = bool(val & (1 << 55))

    pfn = 0
    swap_type = None
    swap_offset = None

    if present:
        # PFN resides in bits 0-54 (zeroed without CAP_SYS_ADMIN)
        pfn = val & ((1 << 55) - 1)
    elif swapped:
        swap_type = val & 0x1F
        swap_offset = (val >> 5) & ((1 << 50) - 1)

    return {
        "present": present,
        "swapped": swapped,
        "file_or_shared_anon": file_or_shared_anon,
        "guard_region": guard_region,
        "uffd_wp": uffd_wp,
        "exclusive": exclusive,
        "soft_dirty": soft_dirty,
        "pfn": pfn,
        "swap_type": swap_type,
        "swap_offset": swap_offset,
        "raw": val,
    }

def entries(pid: int | str, vaddr: int, npages: int = 1) -> list[dict]:
    page_idx = vaddr // PAGE_SIZE
    offset = page_idx * 8
    path = f"/proc/{pid}/pagemap"
    results = []

    with open(path, "rb") as f:
        f.seek(offset)
        raw_bytes = f.read(npages * 8)
        for i in range(len(raw_bytes) // 8):
            (val,) = struct.unpack("<Q", raw_bytes[i * 8 : (i + 1) * 8])
            entry_dict = decode_pagemap_entry(val)
            entry_dict["vaddr"] = (page_idx + i) * PAGE_SIZE
            results.append(entry_dict)

    return results

def main():
    pid = sys.argv[1] if len(sys.argv) > 1 else "self"
    buf = bytearray(PAGE_SIZE * 2)
    buf[0] = 1  # Touch the first page to populate its PTE
    addr = ctypes.addressof(ctypes.c_char.from_buffer(buf))

    records = entries(pid, addr, 2)
    for r in records:
        print(
            f"vaddr={r['vaddr']:#014x} "
            f"present={int(r['present'])} "
            f"exclusive={int(r['exclusive'])} "
            f"soft_dirty={int(r['soft_dirty'])} "
            f"pfn={r['pfn']:#x}"
        )

if __name__ == "__main__":
    main()

Lab: Observing Demand Paging

When allocating anonymous memory using mmap(..., MAP_ANONYMOUS | MAP_PRIVATE, ...), the kernel returns a valid virtual address range. However, none of the underlying pages are present in physical memory.

In demand_paging.py, we allocate 16 pages of anonymous memory. We inspect the pagemap entries across three distinct phases: 1. Immediately after mapping (untouched). 2. After writing a single byte to every even page (0, 2, 4, …). 3. After invoking madvise(MADV_DONTNEED) across the entire range to release the physical backing.

#!/usr/bin/env python3
"""Demonstrate kernel demand paging and madvise(MADV_DONTNEED)."""
import ctypes
import mmap
import os
from pagemap import entries

def main():
    page_size = os.sysconf("SC_PAGE_SIZE")
    total_pages = 16
    size = total_pages * page_size

    # Allocate 16 anonymous pages
    mm = mmap.mmap(-1, size, mmap.MAP_PRIVATE | mmap.MAP_ANONYMOUS, mmap.PROT_READ | mmap.PROT_WRITE)
    addr = ctypes.addressof(ctypes.c_char.from_buffer(mm))

    # Phase 1: Mapped but untouched
    res_before = entries("self", addr, total_pages)
    present_before = sum(1 for e in res_before if e["present"])
    print(f"Phase 1 (untouched):     present={present_before}/{total_pages}")

    # Phase 2: Touch every even page
    for p in range(0, total_pages, 2):
        mm[p * page_size] = ord("A")

    res_touched = entries("self", addr, total_pages)
    present_touched = sum(1 for e in res_touched if e["present"])
    print(f"Phase 2 (touched evens): present={present_touched}/{total_pages}")

    # Phase 3: Discard physical pages with MADV_DONTNEED
    mm.madvise(mmap.MADV_DONTNEED, 0, size)

    res_cleared = entries("self", addr, total_pages)
    present_cleared = sum(1 for e in res_cleared if e["present"])
    print(f"Phase 3 (MADV_DONTNEED): present={present_cleared}/{total_pages}")

    mm.close()

if __name__ == "__main__":
    main()

The following command runs the demand paging demonstration:

python3 demand_paging.py
Phase 1 (untouched):     present=0/16
Phase 2 (touched evens): present=8/16
Phase 3 (MADV_DONTNEED): present=0/16

Notice what happens across the phases: - In Phase 1, the count of present pages is zero because the kernel has not yet allocated physical frames for the VMA. - In Phase 2, touching the even pages triggers demand page faults that populate exactly half the pages. - In Phase 3, MADV_DONTNEED informs the kernel to release the allocated physical frames and clear the PTEs. The present count returns to zero while leaving the virtual address range intact.

Lab: Tracking Writes with Soft-Dirty Bits

The Linux soft-dirty subsystem allows user-space applications (such as checkpoint/restore engines like CRIU or garbage collectors) to detect which memory pages have been modified over time without requiring root access.

Writing the string "4" to /proc/self/clear_refs clears the soft-dirty bit on all page table entries belonging to the calling process. When the CPU subsequently writes to a page, the memory management subsystem catches the write and sets bit 55 (soft_dirty) on that page’s pagemap entry.

The script soft_dirty.py allocates 8 pages, touches them all, resets their tracking state via clear_refs, rewrites only pages 0 and 5, and inspects the resulting bits:

#!/usr/bin/env python3
"""Demonstrate write tracking using soft-dirty bits and clear_refs."""
import ctypes
import mmap
import os
from pagemap import entries

def main():
    page_size = os.sysconf("SC_PAGE_SIZE")
    total_pages = 8
    size = total_pages * page_size

    mm = mmap.mmap(-1, size, mmap.MAP_PRIVATE | mmap.MAP_ANONYMOUS, mmap.PROT_READ | mmap.PROT_WRITE)
    addr = ctypes.addressof(ctypes.c_char.from_buffer(mm))

    # Touch all 8 pages to fault them into physical memory
    for p in range(total_pages):
        mm[p * page_size] = ord("W")

    # Clear soft-dirty flags across the entire process
    with open("/proc/self/clear_refs", "w") as f:
        f.write("4\n")

    # Verify that no pages are marked dirty immediately after clearing
    res_cleared = entries("self", addr, total_pages)
    dirty_after_clear = [i for i, e in enumerate(res_cleared) if e["soft_dirty"]]
    print(f"Dirty immediately after clear_refs: {dirty_after_clear}")

    # Mutate only page 0 and page 5
    mm[0 * page_size] = ord("M")
    mm[5 * page_size] = ord("M")

    # Inspect the soft-dirty flags
    res_rewritten = entries("self", addr, total_pages)
    dirty_pages = [i for i, e in enumerate(res_rewritten) if e["soft_dirty"]]
    print(f"Dirty after modifying pages 0 and 5: {dirty_pages}")

    mm.close()

if __name__ == "__main__":
    main()

The following command executes the soft-dirty tracking script:

python3 soft_dirty.py
Dirty immediately after clear_refs: []
Dirty after modifying pages 0 and 5: []

Both lists are empty, even after the writes. That isn’t a bug in the script. This output came from a 6.12 kernel built without CONFIG_MEM_SOFT_DIRTY. The architecture supports the feature, but the kernel doesn’t compile it in. On such a kernel, writing 4 to clear_refs succeeds silently and bit 55 always reads 0. That includes freshly faulted pages, which would be soft-dirty on a kernel that tracks it. Check the kernel’s config before you trust an empty dirty set:

zcat /proc/config.gz 2>/dev/null | grep SOFT_DIRTY || grep SOFT_DIRTY /boot/config-"$(uname -r)"

On the machine above, only CONFIG_HAVE_ARCH_SOFT_DIRTY=y showed up, with no CONFIG_MEM_SOFT_DIRTY=y line.

Note

Not run here. On a kernel with CONFIG_MEM_SOFT_DIRTY=y, the soft-dirty documentation describes this behavior: clear_refs clears the bits and write-protects the PTEs, and the next write to a page faults and sets bit 55 again. The script should then print [] followed by [0, 5]. Many distribution kernels enable the option because CRIU depends on it. Minimal, cloud and sandbox kernels may not.

A robust tool should detect the missing feature instead of reporting “nothing changed”. One way: fault in a page right after mmap and check bit 55. With soft-dirty compiled in, a newly faulted page is reported soft-dirty.

Lab: Fork and Copy-on-Write Exclusivity

When a process calls fork(), the kernel duplicates the parent’s page tables rather than copying the underlying physical RAM. To prevent one process from corrupting the other’s state, the kernel marks all shared anonymous pages as read-only and clears bit 56 (exclusive).

When either the parent or child writes to the page, the CPU raises a write-protection page fault. The kernel allocates a fresh, private physical page, copies the original data into it, updates the faulting process’s page table to point to this new frame, and sets bit 56 (exclusive) back to true.

The script fork_cow.py monitors bit 56 across three key events: 1. When the page is first written in the parent. 2. After fork(), when the child shares the page. 3. After the parent writes to the page again, triggering copy-on-write duplication.

#!/usr/bin/env python3
"""Demonstrate page exclusivity (bit 56) and Copy-on-Write via fork()."""
import ctypes
import mmap
import os
import time
from pagemap import entries

def main():
    page_size = os.sysconf("SC_PAGE_SIZE")
    mm = mmap.mmap(-1, page_size, mmap.MAP_PRIVATE | mmap.MAP_ANONYMOUS, mmap.PROT_READ | mmap.PROT_WRITE)
    addr = ctypes.addressof(ctypes.c_char.from_buffer(mm))

    # Step 1: Write to the page to allocate physical memory
    mm[0] = ord("P")
    e1 = entries("self", addr, 1)[0]
    print(f"Before fork:        present={int(e1['present'])} exclusive={int(e1['exclusive'])}")

    # Step 2: Fork a child process
    pid = os.fork()
    if pid == 0:
        # Child holds the mapping open briefly then exits
        time.sleep(0.5)
        os._exit(0)

    # In parent: the page is now shared with the child
    e2 = entries("self", addr, 1)[0]
    print(f"After fork:         present={int(e2['present'])} exclusive={int(e2['exclusive'])}")

    # Step 3: Parent writes to the page, triggering Copy-on-Write
    mm[0] = ord("Q")
    e3 = entries("self", addr, 1)[0]
    print(f"After parent write: present={int(e3['present'])} exclusive={int(e3['exclusive'])}")

    os.waitpid(pid, 0)
    mm.close()

if __name__ == "__main__":
    main()

The following command executes the Copy-on-Write demonstration:

python3 fork_cow.py
Before fork:        present=1 exclusive=1
After fork:         present=1 exclusive=0
After parent write: present=1 exclusive=1

Notice the state transitions in the output: - Before the fork, the page is both present and exclusive (mapped only into the parent process). - Immediately after fork(), the page remains present, but the exclusive bit drops to false because the page frame is shared by both parent and child. - After the parent performs a write, the kernel triggers copy-on-write and allocates a separate private frame, restoring the exclusive bit to true.

Pitfalls and Common Mistakes

  • Seeking by byte address instead of entry offset. Seeking to vaddr directly in /proc/PID/pagemap is incorrect. The file contains 8-byte entries indexed by page number. The seek target must be (vaddr // PAGE_SIZE) * 8. Seeking to the unadjusted vaddr reads unrelated metadata far past the intended mapping.
  • Assuming PFN availability for unprivileged processes. Since Linux 4.2, reading PFNs (bits 0–54) requires CAP_SYS_ADMIN. Code that assumes non-zero PFNs for present pages will silently misbehave unless executed as root.
  • Ignoring unaligned base addresses. If inspecting arbitrary pointers, always mask or divide by PAGE_SIZE. Passing a pointer into the middle of a page without integer division results in an off-by-one or non-8-byte-aligned file seek.
  • Missing kernel config for soft-dirty. Soft-dirty tracking requires the kernel to be compiled with CONFIG_MEM_SOFT_DIRTY=y. If this option is omitted, writing 4 to /proc/PID/clear_refs still succeeds, but bit 55 is permanently 0. The empty result above shows exactly that, and it is easy to misread as “no writes happened”.
  • Sequential pagemap parsing at high frequency. Reading /proc/PID/pagemap sequentially across sparse multi-gigabyte heaps causes significant overhead because the kernel must traverse page tables for every 8-byte slice. For bulk dirty-page detection on Linux 6.7 and newer, use the PAGEMAP_SCAN ioctl instead.

Summary

  • /proc/PID/pagemap provides a binary representation of user-space page table entries, formatted as 64-bit little-endian words.
  • Seek offsets are computed by (vaddr // PAGE_SIZE) * 8, allowing direct indexing into any virtual address range.
  • Bit 63 indicates physical memory residency (present), bit 62 indicates swap residency, bit 56 flags whether a page is exclusively mapped, and bit 55 tracks modifications (soft_dirty).
  • Physical Page Frame Numbers (bits 0–54) are sanitized to zero for unprivileged processes to mitigate Rowhammer attacks.
  • Demand paging defers physical RAM allocation until first access, while madvise(MADV_DONTNEED) unbinds physical frames and clears present bits without destroying the virtual mapping.
  • Writing "4" to /proc/self/clear_refs clears the soft-dirty bit across the calling process’s address space, turning bit 55 into an incremental write log, but only on kernels built with CONFIG_MEM_SOFT_DIRTY=y.
