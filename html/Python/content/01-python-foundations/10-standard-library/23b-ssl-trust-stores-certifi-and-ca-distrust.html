TLS Trust Stores in Python: ssl, certifi, pip and the 2026 emSign Distrust

After this page you will be able to list every copy of the certificate authority (CA) roots a Python environment may trust, explain why updating the operating system’s certificates does not update the bundle requests uses, and remove a distrusted root from each copy.

Thesis

A Python program has no single trust store. One environment can hold three copies of the roots: the operating system’s store that the standard library ssl module loads by default, the certifi package that requests, httpx and many SDKs use, and pip’s own vendored copy, pip._vendor.certifi.

When a CA is distrusted, as eMudhra/emSign was in October 2026, each copy has to be updated separately. Updating the OS package does nothing for code that uses an old certifi, and the reverse is also true.

Trust Store Source Primary Consumers Default Location / Mechanism How to Update
OS store, loaded by ssl ssl.create_default_context(), so urllib.request, http.client and plain ssl sockets Whatever ssl.get_default_verify_paths() reports; on Linux usually under /etc/ssl The OS package manager (ca-certificates on Debian/Ubuntu)
certifi requests, httpx, many SDKs certifi.where(), a cacert.pem in site-packages Upgrade certifi in each environment
pip._vendor.certifi pip itself pip/_vendor/certifi/cacert.pem in site-packages Upgrade pip (distribution builds may point it at the OS bundle)

The Three Trust Copies

When Python establishes a secure TLS connection, the underlying engine must validate the server’s certificate chain against a set of trusted root CAs. Which certificates are trusted depends entirely on the library initiating the connection.

  1. The ssl module loads OpenSSL’s default locations, which ssl.get_default_verify_paths() reports. On Linux that is usually /etc/ssl/certs or a file such as /usr/lib/ssl/cert.pem. The SSL_CERT_FILE and SSL_CERT_DIR environment variables override these defaults.
  2. certifi is Mozilla’s root bundle packaged as a Python module. requests uses certifi.where() unless you pass verify=/path/to/pem or set REQUESTS_CA_BUNDLE. httpx also defaults to certifi. Plain urllib3 2.x only uses certifi if you pass ca_certs=certifi.where() yourself.
  3. pip._vendor.certifi is pip’s own copy, so pip can verify PyPI before anything else is installed. Recent pip versions can also use the OS store through the truststore package. Some distributions (Debian/Ubuntu python3-pip) patch the vendored module to return the OS bundle /etc/ssl/certs/ca-certificates.crt instead.

Updating one copy leaves the others untouched. A patched host can still run virtual environments whose pinned certifi trusts the distrusted root.

The October 2026 Distrust in Brief

In October 2026 the Python security announcement on Discourse told users to remove trust in eMudhra/emSign. For Python, it comes down to these releases:

  • certifi Advisory (GHSA-6q48-6c7w-9gw2): the advisory lists certifi releases from 2019.03.09 up to (not including) 2026.10.18 as containing affected eMudhra roots, and says to upgrade to 2026.10.19 or later. 2026.10.19 removes “emSign ECC Root CA - G3”. In the lab below the bundle goes from 121 certificates (2026.07.22) to 120 (2026.10.19). 2026.10.23, the latest when this was written, has 118.
  • pip Updates: upgrade pip to 26.2.2 or later for an updated vendored copy. pip 26.3, used in the lab, ships certifi 2026.10.23. For uv, upgrade to 0.13.6 or later.
  • CPython: point releases 3.15.2, 3.14.10, 3.13.18, 3.12.16 and 3.11.18 add a denylist for the affected CA keys to the ssl module, so those keys are not trusted even if the OS store has not been updated yet.

The Audit Script Walk-Through

trust_report.py finds each copy and reports whether a given root is still in it. It has no third-party dependencies: it splits PEM files into certificates with base64, then searches each certificate’s DER bytes for the CA’s name.

Note

Caveat. The name is stored as a plain string, so a byte search finds it in the subject, and also in the issuer field of any certificate that CA issued. Root bundles don’t contain such certificates, so for a bundle this is a reliable presence check. It is not a substitute for comparing fingerprints or SPKI hashes. For a capath directory the script only scans *.pem files.

"""trust_report.py: show every CA bundle this interpreter might trust,
and whether a given root CA is still in each one."""
import base64
import importlib
import os
import ssl
import sys

TARGET = sys.argv[1] if len(sys.argv) > 1 else "emSign ECC Root CA - G3"


def pem_blocks(path):
    """Yield the DER bytes of every certificate in a PEM file."""
    with open(path, encoding="ascii", errors="replace") as f:
        b64 = None
        for line in f:
            line = line.strip()
            if line == "-----BEGIN CERTIFICATE-----":
                b64 = []
            elif line == "-----END CERTIFICATE-----" and b64 is not None:
                yield base64.b64decode("".join(b64))
                b64 = None
            elif b64 is not None:
                b64.append(line)


def scan(paths):
    """Count certificates and those whose DER contains TARGET. The CA name
    is stored as a plain string in the subject, so a byte search finds it
    (it also matches certificates *issued by* that CA, which a root bundle
    should not contain)."""
    total = hits = 0
    needle = TARGET.encode()
    for p in paths:
        for der in pem_blocks(p):
            total += 1
            hits += needle in der
    return total, hits


def report(name, paths, version=None):
    paths = [p for p in paths if p and os.path.isfile(p)]
    if not paths:
        print(f"{name:<24} (not present)")
        return
    total, hits = scan(paths)
    ver = f" v{version}" if version else ""
    state = "PRESENT" if hits else "absent"
    where = paths[0] if len(paths) == 1 else f"{os.path.dirname(paths[0])}/ ({len(paths)} files)"
    print(f"{name:<24} {total:>4} certs{ver}  {TARGET!r}: {state}")
    print(f"{'':<24} {os.path.realpath(where) if len(paths) == 1 else where}")


print(f"python {sys.version.split()[0]}  {ssl.OPENSSL_VERSION}")
vp = ssl.get_default_verify_paths()
print(f"ssl default cafile: {vp.cafile}")
print(f"ssl default capath: {vp.capath}")

for mod_name, label in [("certifi", "certifi"), ("pip._vendor.certifi", "pip's vendored certifi")]:
    try:
        mod = importlib.import_module(mod_name)
    except ImportError:
        print(f"{label:<24} (not importable)")
        continue
    report(label, [mod.where()], getattr(mod, "__version__", None))

if vp.cafile:
    report("ssl default cafile", [vp.cafile])
elif vp.capath and os.path.isdir(vp.capath):
    files = sorted(os.path.join(vp.capath, f) for f in os.listdir(vp.capath) if f.endswith(".pem"))
    report("ssl default capath", files)

Running the Audit Script

The script was run in three environments on one machine. Paths in the output are shortened to ~/certlab.

Environment 1: Legacy Virtual Environment (un-patched certifi)

Executing the audit script inside an un-patched virtual environment configured with certifi==2026.7.22:

old/bin/python trust_report.py

The command above produces the following output:

python 3.15.0  OpenSSL 3.5.9 29 Sep 2026
ssl default cafile: None
ssl default capath: /etc/ssl/certs
certifi                   121 certs v2026.07.22  'emSign ECC Root CA - G3': PRESENT
                         ~/certlab/old/lib/python3.15/site-packages/certifi/cacert.pem
pip's vendored certifi   (not importable)
ssl default capath        150 certs  'emSign ECC Root CA - G3': PRESENT
                         /etc/ssl/certs/ (150 files)

This uv-managed CPython has no default cafile, only the capath /etc/ssl/certs. certifi 2026.07.22 has 121 certificates and still contains the root. pip is not installed in this venv, so there is no vendored copy. The OS store has the root too: this machine’s ca-certificates package had not been updated yet.

Environment 2: Modern Virtual Environment (upgraded certifi and pip)

Executing the audit script inside an updated environment with certifi>=2026.10.19 and pip 26.3:

new/bin/python trust_report.py

The command above produces the following output:

python 3.15.0  OpenSSL 3.5.9 29 Sep 2026
ssl default cafile: None
ssl default capath: /etc/ssl/certs
certifi                   120 certs v2026.10.19  'emSign ECC Root CA - G3': absent
                         ~/certlab/new/lib/python3.15/site-packages/certifi/cacert.pem
pip's vendored certifi    118 certs v2026.10.23  'emSign ECC Root CA - G3': absent
                         ~/certlab/new/lib/python3.15/site-packages/pip/_vendor/certifi/cacert.pem
ssl default capath        150 certs  'emSign ECC Root CA - G3': PRESENT
                         /etc/ssl/certs/ (150 files)

certifi 2026.10.19 has 120 certificates and the root is gone. pip 26.3’s vendored copy (2026.10.23, 118 certificates) doesn’t have it either. The OS store line is unchanged, PRESENT, because nothing in a venv can change it.

Environment 3: System Interpreter (Debian/Ubuntu patched pip)

Executing the audit script via the Debian system interpreter:

python3 trust_report.py

The command above produces the following output:

python 3.13.5  OpenSSL 3.5.7 9 Jun 2026
ssl default cafile: /usr/lib/ssl/cert.pem
ssl default capath: /usr/lib/ssl/certs
certifi                   121 certs v2026.07.22  'emSign ECC Root CA - G3': PRESENT
                         /usr/local/lib/python3.13/dist-packages/certifi/cacert.pem
pip's vendored certifi    150 certs v2025.01.31  'emSign ECC Root CA - G3': PRESENT
                         /etc/ssl/certs/ca-certificates.crt
ssl default cafile        150 certs  'emSign ECC Root CA - G3': PRESENT
                         /etc/ssl/certs/ca-certificates.crt

Debian’s Python 3.13.5 has a default cafile, /usr/lib/ssl/cert.pem, a symlink to /etc/ssl/certs/ca-certificates.crt. Debian’s pip is patched: its vendored module says version 2025.01.31, yet where() returns the same OS file with 150 certificates. A separate certifi 2026.07.22 sits in /usr/local/lib/python3.13/dist-packages, installed system-wide outside the package manager, and it still has the root. Updating ca-certificates would fix two of these three lines; that certifi needs its own upgrade.

Remediation Strategies

Fix each copy in turn.

1. Upgrade Application Dependencies (certifi)

To see the fix in a fresh environment, first create a venv with the old release:

uv venv demo && uv pip install -p demo/bin/python certifi==2026.7.22

The command above produces the following output:

Using CPython 3.15.0
Creating virtual environment at: demo
Activate with: source demo/bin/activate
Using Python 3.15.0 environment at: demo
Resolved 1 package in 2ms
Installed 1 package in 1ms
 + certifi==2026.7.22

To remediate, upgrade certifi to 2026.10.19 or higher:

uv pip install -p demo/bin/python -U 'certifi>=2026.10.19'

The command above produces the following output:

Using Python 3.15.0 environment at: demo
Resolved 1 package in 94ms
Prepared 1 package in 0.57ms
Uninstalled 1 package in 0.47ms
Installed 1 package in 1ms
 - certifi==2026.7.22
 + certifi==2026.10.23

uv resolved >=2026.10.19 to the newest release, 2026.10.23. Run the report again:

demo/bin/python trust_report.py

The command above produces the following output:

python 3.15.0  OpenSSL 3.5.9 29 Sep 2026
ssl default cafile: None
ssl default capath: /etc/ssl/certs
certifi                   118 certs v2026.10.23  'emSign ECC Root CA - G3': absent
                         ~/certlab/demo/lib/python3.15/site-packages/certifi/cacert.pem
pip's vendored certifi   (not importable)
ssl default capath        150 certs  'emSign ECC Root CA - G3': PRESENT
                         /etc/ssl/certs/ (150 files)

2. Upgrade Package Installer (pip and uv)

Upgrade pip in every environment that has it (to 26.2.2 or later):

python -m pip install --upgrade pip
Note

Not run here. The test machine has uv 0.13.1. uv carries its own root certificates by default, so upgrade it to 0.13.6 or later (for example with uv self update if you installed it with the standalone installer, or through your package manager). That upgrade was not run on this machine.

3. Upgrade Operating System Trust Store

On the test machine the OS store (/etc/ssl/certs, 150 certificates) still contains the root, because the distribution’s ca-certificates package had not been updated there. Fixing that needs the OS package manager and root.

Note

Not run here (it needs root). On Debian/Ubuntu:

sudo apt update && sudo apt install --only-upgrade ca-certificates
sudo update-ca-certificates

Once the distribution ships a ca-certificates without the root, this rebuilds /etc/ssl/certs without it.

4. Upgrade CPython Runtime

A CPython release with the ssl denylist covers the affected keys for anything that verifies through the ssl module, even with an old OS store.

Note

Not run here. The interpreters evaluated in this lab are versions 3.15.0 and 3.13.5. Upgrading to CPython point releases 3.15.2, 3.14.10, 3.13.18, 3.12.16, or 3.11.18 adds the denylist. This was not tested here.

Pinning, Lockfiles, and Container Environments

Lockfiles and pinned requirements (requirements.txt, poetry.lock, uv.lock) pin exact versions. If one pins certifi==2026.7.22, every pip install -r or uv sync installs the old bundle again until you regenerate the lock (uv lock --upgrade-package certifi, for example).

Dependabot or Renovate can open that upgrade for you. A minimal Dependabot version-update config looks like this (security updates are switched on separately in the repository settings):

# Example Dependabot configuration update
version: 2
updates:
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "daily"

Container images bake both the OS bundle and the installed certifi in at build time. Updating the certificates on the host or Kubernetes node doesn’t change them. Rebuild the images with updated ca-certificates and dependencies, then redeploy.

Single Source of Truth: truststore

If you want one source of truth, the OS store, an application can use the truststore package. It verifies certificates with the platform’s own APIs on Windows and macOS, and with the system’s OpenSSL store on Linux. Not run here:

import truststore

# Inject truststore into standard ssl contexts
truststore.inject_into_ssl()

# Subsequent HTTP client calls use OS trust settings
import urllib.request
response = urllib.request.urlopen("https://example.com")

Then OS updates are the only thing to keep current, and an old certifi stops mattering for that application.

Common Mistakes

  • Updating only the OS store. Code using requests or httpx in a venv keeps its old certifi.
  • Updating only certifi. urllib.request, plain ssl sockets and pip still use their own copies.
  • Assuming verify=True means the OS store. In requests it means certifi (or REQUESTS_CA_BUNDLE), not /etc/ssl.
  • Disabling verification to “fix” errors. verify=False or ssl._create_unverified_context() turns off every check, not just the one that failed.
  • A stale SSL_CERT_FILE. It overrides OpenSSL’s defaults for the ssl module (and httpx honours it too). If it points at an old bundle copied somewhere, updates to the OS store never reach the program. For requests, the same mistake is a stale REQUESTS_CA_BUNDLE.

Exercises

  1. Run trust_report.py with every interpreter and venv you deploy, and list each copy that still says PRESENT.
  2. Write a pytest test that fails if certifi.where() still contains “emSign ECC Root CA - G3”. Reuse pem_blocks from the script.
  3. Point SSL_CERT_FILE at an empty file and run the report again. What does ssl default cafile show, and what happens to urllib.request.urlopen("https://pypi.org")?
  4. Pass a different CA name as the first argument (any root you know is in your OS store) and compare the counts.

Key takeaways

  • Python TLS trust is distributed across three main locations: system default paths via ssl, standalone bundled PEM files via certifi, and isolated installer files via pip._vendor.certifi.
  • Upgrading the OS CA package does not fix applications that use certifi, and upgrading certifi does not fix the OS store.
  • For the October 2026 eMudhra/emSign distrust: certifi>=2026.10.19, pip>=26.2.2, uv 0.13.6 or later, an updated ca-certificates, and a CPython point release with the ssl denylist.
  • Containerized environments and locked dependencies preserve stale CA bundles until explicitly rebuilt or re-locked.
