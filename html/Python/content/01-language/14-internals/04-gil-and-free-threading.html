September 4, 2026

GIL and Free-Threading

The Global Interpreter Lock is a CPython mutex: in the default build, only one thread runs Python bytecode at a time. Python 3.14 made a free-threaded (no-GIL) build official. Same language, different machine.

Mental model

  default 3.14
    thread A  ████░░░░████     (█ = holds GIL, runs bytecode)
    thread B  ░░░░████░░░░
    C code / I/O can release the GIL

  free-threaded 3.14
    thread A  ████████
    thread B  ████████         both run bytecode
    memory model and some extensions must cope

What the GIL does and does not do

True False
One bytecode-running thread per process (default build) “Python has no threads”
I/O and many C extensions release the GIL Threads never help
threading is still useful for I/O wait CPU-bound Python threads scale on 8 cores (default build)

For CPU-bound work on the default build, use multiprocessing, NumPy/PyTorch (C loops), or a free-threaded interpreter you have actually tested.

See it

# burn_threads.py
import threading
import time


def burn(n):
    x = 0
    for i in range(n):
        x += i
    return x


def run(workers):
    t0 = time.perf_counter()
    threads = [threading.Thread(target=burn, args=(4_000_000,)) for _ in range(workers)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return time.perf_counter() - t0


if __name__ == "__main__":
    print("1 thread", run(1))
    print("4 threads", run(4))

On a default GIL build, 4 threads of this loop are not 4× faster (often similar or slower). On a free-threaded build, they can scale. I/O-bound threads (waiting on sockets) overlap even with the GIL.

3.13–3.14 timeline

Release Free-threading
3.13 Experimental opt-in build (PEP 703)
3.14 Official (PEP 779); still a separate build / ABI

uv python install 3.14 gives you the GIL build unless you ask for a free-threaded interpreter. Some binary wheels lag behind.

Check:

# gil_status.py
import sys

print(sys.version)
print(getattr(sys, "_is_gil_enabled", lambda: "n/a")())

(API names around GIL detection have been moving; read help(sys) on your exact 3.14 patch.)

Multiple interpreters (PEP 734)

3.14 also exposes subinterpreters in the stdlib: separate isolated states inside one process, each historically with its own GIL. They are a third isolation tool next to threads and processes. Treat them as advanced until you have a reason.

When to care

  • Writing a web worker that waits on HTTP: threads or asyncio (Concurrency section). GIL is not your problem.
  • Burning CPU in pure Python: measure; then processes, native code, or a tested free-threaded build.
  • Shipping a C extension: know whether you support the free-threaded ABI.

CS connection

A GIL is a coarse lock on the interpreter. Free-threading replaces it with finer safety (atomics, biased refcounting). That is a runtime problem, not a language-syntax problem.

Pitfalls

  • Switching production to free-threading because a blog said “no GIL.” Measure, test extensions, read the porting notes.
  • Using threads as a synonym for “uses all cores.”
  • Sharing a non-thread-safe list across threads and blaming the GIL when you forgot a Lock. The GIL is not a substitute for your own locks on invariants.

Exercises

  1. Run the burn snippet with 1 and 4 threads. Record the times and your sys.version.
  2. Change burn to time.sleep(0.5) (I/O-like wait). Compare 1 vs 4 threads again.
  3. In one paragraph, explain why NumPy matrix multiply can use multiple cores even on a GIL build.
