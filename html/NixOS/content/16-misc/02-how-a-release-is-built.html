How a Release Is Built

Goal: Follow one store path from a merged nixpkgs commit to the NAR your rebuild downloads, and decide which machines in that path you trust.

The useful split is the signature. Plenty of computers compile nixpkgs. One build farm is allowed to publish those results as cache.nixos.org.

pull request on github:NixOS/nixpkgs
    GitHub Actions     lint, eval, labels, reviewer pings
    OfBorg             builds and VM tests on the PR
         │  a committer merges
         ▼
Hydra jobset           evaluate, build what the cache lacks, sign
         │
         ▼
S3 in us-east-1        nar, narinfo, build logs
    Fastly in front    cache.nixos.org
         │
         ▼
tested job green  →  channels.nixos.org moves that branch
         │
         ▼
your flake.lock  →  nixos-rebuild  →  narinfo  →  NAR

Who does what

Stage Runs on Allowed to do Refuses to do
GitHub Actions Hosted runners, Nix installed for the job Lint, eval, label, name reviewers, build docs and the Nixpkgs tarball Sign for cache.nixos.org
OfBorg The project’s PR builders Build the packages a PR touches, run NixOS VM tests, comment on the PR Upload a substitute you should enable
Hydra The release build farm Build after merge, sign, upload Review the PR for you
Fastly Edge cache Serve the bucket, hide raw S3 errors behind a 404 Decide that a build is trusted
Your daemon The lab Substitute a path whose narinfo verifies, or build it Treat a green PR comment as a cache hit

Anyone can open a nixpkgs pull request. Merge rights sit with the committers. The infrastructure repository (github:NixOS/infra) is the one that declares DNS, the channel bucket, the cache bucket, and the Hydra host. The production-labs part of this book reads that tree for shapes. This chapter is the path a package takes, not a tour of their hosts.

Actions that matter on a PR:

  • Lint, including nixpkgs-vet, which enforces the simple package-path policy.
  • Eval across the supported systems. The job records which attributes appeared, changed, or disappeared. Labels are applied from that list.
  • A build workflow for docs, the Nixpkgs shell, lib, and the source tarball. It uses a CI binary cache that exists for those workflows. That cache is not a substituter for a NixOS host.
  • Reviewer selection from the maintainers of the attributes that changed.

OfBorg is the system that actually builds pull-request packages and runs VM tests, then writes the result back to the PR. It has been the PR builder alongside Actions since the end of 2024, when the old sponsored builder fleet went away and Actions took the eval and lint load. OfBorg output is evidence for the reviewer. It is not a signed release artifact.

Hydra builds after the merge. Jobsets hang off projects: nixos/release-26.05 for the stable ISO and system tests, nixos/unstable for the rolling channel, nixpkgs/trunk for the package set on the development branch. The jobset expression in nixpkgs (nixos/release-combined.nix and its siblings) is the list of jobs. The minimal ISO you download is one of those jobs (nixos.iso_minimal), copied out to channels.nixos.org when the channel advances.

A jobset evaluation walks the attributes, realises derivations, and queues a build only when that output is not already in the cache. Successful builds are signed and uploaded. nix log /nix/store/<hash>-name works later because the log was uploaded next to the NAR.

The cache is a signed bucket

cache.nixos.org is an S3 bucket in us-east-1 with Fastly in front of it. There is no package database. The object key is the store hash.

Object Role
<hash>.narinfo Text record: NAR URL, sizes, hashes, runtime references, signature
nar/<file>.nar.zst or .nar.xz The compressed store path. NAR is a small archive format, stable for twenty years.
log/ Build log for nix log
realisations/ Content-addressed mappings, for CA derivations
nix-cache-info Cache-wide metadata

The Foundation’s public figures, measured in July 2026 and written up that September, are the current published picture: on the order of a billion objects, about 636 TB, and several thousand requests a second. Older objects sit in a cheaper S3 tier. Fastly terminates TLS, fills from S3 on a miss, and turns some S3 permission errors into 404 so a client sees “not in the cache”.

From about July 2026 the farm runs on the order of 40,000 fewer jobs than the year before, because x86_64-darwin builds stopped. aarch64-darwin remains. 26.05 is the last release that still publishes x86_64-darwin binaries, through the end of that release’s support window.

A NAR from another builder is the same bytes when the derivation inputs match. The Foundation’s account of reproducibility puts that at about 99.9% of the package set, with the rest tracked as nondeterministic outliers. That is why a cache you build yourself can substitute for cache.nixos.org on the paths you have actually built. It does not make that cache trusted. Trust is the public key in your nix.conf.

The key you already have

Official narinfo lines look like this:

Sig: cache.nixos.org-1:<base64>

Nix checks that signature against trusted-public-keys. The name cache.nixos.org-1 is the key id, not a promise that the key rotates every year. The rotation proposal (so the cache can sign with a new key and the old key during a transition) is still an open draft. Nix itself can verify a path that carries more than one signature. The live cache has not finished moving clients onto a second key.

Consequences for a lab:

  • Leave require-sigs on.
  • Keep cache.nixos.org-1 in trusted-public-keys. The NixOS module does this when you have not replaced the defaults.
  • Add a key only for a cache you run or a cache whose operators you have named in the config. The key sits next to the substituter URL in nix.settings.
  • A flake nixConfig.extra-trusted-public-keys is a hint. The daemon ignores it until the user accepts flake config or the same key is in the system config.
  • Do not point the host at the GitHub Actions cache, an OfBorg result, or a substituter URL copied from a PR comment.

A Hydra build page can exist for a path that is absent from the bucket. The queue that uploads has had periods where a finished build never became a narinfo. The client is right to build locally in that case. Check before you disable anything:

store=$(readlink -f /run/current-system)
hash=$(basename "$store" | cut -d- -f1)
curl -fsS -o /dev/null -w '%{http_code}\n' \
  "https://cache.nixos.org/${hash}.narinfo"

200 means the cache has a signed record. 404 means it does not. Build the path, or wait until a later channel commit has it. The same test works for any store path you were about to compile by hand.

How a channel moves

channels.nixos.org is a second bucket, also behind Fastly. A channel name (nixos-26.05, nixos-unstable, nixos-26.05-small, the Darwin variants) advances when Hydra’s tested job for that jobset succeeds. status.nixos.org shows the commit and whether the job is green. A “build problem” line means the channel did not move. Your flake.lock is unaffected until you update.

Name What it is
nixos-26.05 Stable branch. The pin for this book.
nixos-26.05-small A smaller jobset of the same release. NixOS’s own infra pins the small channel tarball. This book uses the full branch unless you have measured that the small set is enough.
nixos-unstable Rolling, but only commits whose tested job passed.
master, staging, staging-next Where nixpkgs integrates. Hydra builds them. They are not a channel you put in a desk flake.

Two honest ways to pin 26.05:

{
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-26.05";
}
{
  inputs.nixpkgs.url =
    "https://channels.nixos.org/nixos-26.05/nixexprs.tar.zst";
}

The GitHub ref is what the rest of this book uses: a branch plus a lock, easy to review in a diff. The channel tarball is what you want when you care about a smaller download and IPv6 on the channel host. Prefer .tar.zst. The .tar.xz channel tarballs are on a retirement path that finishes with the 27.05 release, after 31 December 2027.

nix flake update nixpkgs moves the lock along the ref you wrote. It does not change the ref. Switching to 26.11 is an edit to flake.nix, then an update, then a lab boot. Commit flake.lock with the rebuild that worked.

What you do on the desk

  1. Pin nixos-26.05 (or the 26.05 channel tarball) and commit the lock.
  2. Trust cache.nixos.org and any cache whose key you set yourself.
  3. Read status.nixos.org when substitutes disappear on a day you did not change the lock. A red tested job explains a stuck channel. It does not explain a lock you already have.
  4. When a path 404s, build it. Keep signatures required.
  5. Update one input at a time. nix flake update nixpkgs, rebuild, then the next input.
  6. Keep the previous generation bootable. A rollback swaps which closure is active. It does not revert the git tree, and it does not unmigrate a database.

The production-labs chapters turn the infra repo into a desk factory, a keys file, and a promotion table. The table there is the small version of Hydra’s tested job: a closure you are willing to name, pushed to a cache you signed.

The boring rule

  • OfBorg and GitHub Actions inform a merge. Hydra signs a release.
  • The trust anchor is cache.nixos.org-1 on the narinfo, checked by your daemon.
  • A channel advances when its tested job is green. A flake advances when you update the lock.
  • master is not nixos-unstable. nixos-unstable is not nixos-26.05.
  • Another person’s CI cache stays out of nix.settings.
