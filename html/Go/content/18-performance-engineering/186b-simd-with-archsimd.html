SIMD Without Assembly: simd/archsimd

Until recently, the only way to make a Go hot loop use the vector units in your CPU was to write Plan 9 assembly by hand, or to hope the compiler would do it for you (it largely doesn’t auto-vectorize). Go 1.26 added an experimental, amd64-only SIMD API behind GOEXPERIMENT=simd. Go 1.27 revised it, added arm64 (NEON) and wasm (128-bit SIMD), and put a portable, width-agnostic simd package on top. Both remain experimental. They exist only when you build with the experiment, and they are not covered by the Go 1 compatibility promise.

This chapter is about the low layer, simd/archsimd: real vector types, real instructions, and the engineering discipline that keeps them safe to ship. That means build tags, runtime CPU checks, a scalar twin, and tests that exercise every path on one machine. Everything below was compiled and run with Go 1.27.1 on an amd64 box whose CPU reports AVX2, FMA, AVX-512 and GFNI.

Mental model

 your code ──► simd            portable, width chosen at run time (Float32s, Uint8s…)
           │      │ ToArch / *FromArch
           └────► simd/archsimd fixed-width, per-architecture (Float32x8, Uint8x64…)
                          │  methods are compiler intrinsics
                          ▼
                 VFMADD213PS, VPCMPEQB, VGF2P8AFFINEQB …  (one method ≈ one instruction)
  • Types carry shape. Float32x8 is 256 bits of eight float32s; Uint8x64 is a 512-bit register of bytes. Masks are separate opaque types (Mask8x64) because AVX-512, AVX2, NEON and wasm encode them differently.
  • Methods have plain names. x.Add(y), x.MulAdd(y, acc), x.Equal(y), not _mm512_fmadd_ps. The doc comment of each method names the instruction and the CPU feature it needs (Asm: VFMADD213PS, CPU Feature: FMA).
  • The compiler doesn’t know your CPU. A binary built for amd64 may run on a machine without AVX-512. You must branch on archsimd.X86.AVX512() (and friends). Otherwise the program dies with SIGILL. The check also tells the compiler which instruction forms are allowed inside that branch.
  • It is not portable by design. Float32x8 does not exist on arm64. Code that imports archsimd needs a build constraint and a fallback for every other target.
Layer Use it for Cost of using it
Plain Go loop Everything, until a profile says otherwise None
Standard library (bytes.Count, bytes.Index, crypto/*) Searching, hashing, crypto. These already have hand-written vector code None
simd (portable) Arithmetic kernels you want on every architecture Experiment flag
simd/archsimd Instructions with no portable equivalent (GFNI, lane permutes), or the last few % on one target Experiment flag, build tags, CPU dispatch, per-arch tests

Worked examples

Set up a module. The go line must be 1.27 or later.

mkdir simdlab && cd simdlab
go mod init example.com/simdlab   # then set "go 1.27" in go.mod
go version
go version go1.27.1 linux/amd64

The package is split into three files, which is the shape every archsimd package should have:

  1. a scalar reference that always compiles,
  2. a vector file guarded by //go:build goexperiment.simd && amd64,
  3. a fallback file with the opposite constraint, so the package builds everywhere.

Case 1: the scalar twin

// scalar.go — portable reference implementations (always compiled)
package simdlab

import "math/bits"

func dotScalar(a, b []float32) float32 {
    var s float32
    for i := range a {
        s += a[i] * b[i]
    }
    return s
}

func countScalar(s []byte, c byte) int {
    n := 0
    for _, x := range s {
        if x == c {
            n++
        }
    }
    return n
}

func reverseScalar(dst, src []byte) {
    for i, x := range src[:len(dst)] {
        dst[i] = bits.Reverse8(x)
    }
}

These functions are the specification. Every vector path is tested against them, and they are what runs on every machine the vector code doesn’t cover.

Case 2: dispatching vector code

// dispatch_simd.go — vector paths, built only with GOEXPERIMENT=simd on amd64
//go:build goexperiment.simd && amd64

package simdlab

import (
    "math/bits"
    "simd/archsimd"
)

// Path reports which implementation Dot will use on this CPU.
func Path() string {
    switch {
    case archsimd.X86.AVX512():
        return "avx512"
    case archsimd.X86.AVX2() && archsimd.X86.FMA():
        return "avx2+fma"
    default:
        return "scalar"
    }
}

// Dot returns the inner product of a and b (len(b) must be >= len(a)).
func Dot(a, b []float32) float32 {
    b = b[:len(a)]
    switch {
    case archsimd.X86.AVX512():
        return dot16(a, b)
    case archsimd.X86.AVX2() && archsimd.X86.FMA():
        return dot8(a, b)
    }
    return dotScalar(a, b)
}

func dot8(a, b []float32) float32 {
    var acc archsimd.Float32x8
    i := 0
    for ; i < len(a)-8+1; i += 8 {
        x := archsimd.LoadFloat32x8(a[i : i+8])
        y := archsimd.LoadFloat32x8(b[i : i+8])
        acc = x.MulAdd(y, acc)
    }
    if i < len(a) {
        x, _ := archsimd.LoadFloat32x8Part(a[i:])
        y, _ := archsimd.LoadFloat32x8Part(b[i:])
        acc = x.MulAdd(y, acc) // zero-filled lanes add 0
    }
    var lanes [8]float32
    acc.StoreArray(&lanes)
    var s float32
    for _, v := range lanes {
        s += v
    }
    return s
}

func dot16(a, b []float32) float32 {
    var acc archsimd.Float32x16
    i := 0
    for ; i < len(a)-16+1; i += 16 {
        x := archsimd.LoadFloat32x16(a[i : i+16])
        y := archsimd.LoadFloat32x16(b[i : i+16])
        acc = x.MulAdd(y, acc)
    }
    if i < len(a) {
        x, _ := archsimd.LoadFloat32x16Part(a[i:])
        y, _ := archsimd.LoadFloat32x16Part(b[i:])
        acc = x.MulAdd(y, acc)
    }
    var lanes [16]float32
    acc.StoreArray(&lanes)
    var s float32
    for _, v := range lanes {
        s += v
    }
    return s
}

// Count returns how many bytes of s equal c.
func Count(s []byte, c byte) int {
    if !archsimd.X86.AVX512() {
        return countScalar(s, c)
    }
    needle := archsimd.BroadcastUint8x64(c)
    n, i := 0, 0
    for ; i < len(s)-64+1; i += 64 {
        m := archsimd.LoadUint8x64(s[i : i+64]).Equal(needle)
        n += bits.OnesCount64(m.ToBits())
    }
    return n + countScalar(s[i:], c)
}

// ReverseBits writes bits.Reverse8(src[i]) into dst[i] for every i.
func ReverseBits(dst, src []byte) {
    if !archsimd.X86.AVX512GFNI() {
        reverseScalar(dst, src)
        return
    }
    src = src[:len(dst)]
    rev := archsimd.BroadcastUint64x8(0x8040201008040201) // anti-diagonal bit matrix
    i := 0
    for ; i < len(src)-64+1; i += 64 {
        v := archsimd.LoadUint8x64(src[i : i+64])
        v.GaloisFieldAffineTransform(rev, 0).Store(dst[i : i+64])
    }
    if i < len(src) {
        v, _ := archsimd.LoadUint8x64Part(src[i:])
        v.GaloisFieldAffineTransform(rev, 0).StorePart(dst[i:])
    }
}
// dispatch_generic.go — the same API without the experiment (or on other GOARCHes)
//go:build !(goexperiment.simd && amd64)

package simdlab

func Path() string                { return "scalar (no GOEXPERIMENT=simd)" }
func Dot(a, b []float32) float32  { return dotScalar(a, b[:len(a)]) }
func Count(s []byte, c byte) int  { return countScalar(s, c) }
func ReverseBits(dst, src []byte) { reverseScalar(dst, src) }

Things to notice:

  • Dispatch once per call, at the top. Each exported function asks the CPU what it has and picks the widest safe path. Inside dot16, every instruction is AVX-512, and the call is only reached when X86.AVX512() is true.
  • Full vectors, then one partial vector. LoadFloat32x16Part zero-fills the lanes past the end of the slice and StorePart writes only the real ones. For a dot product the zero lanes contribute 0*0, so the tail needs no special case.
  • Count reduces a mask to an integer. Equal yields a Mask8x64, ToBits() turns it into a uint64 with one bit per byte, and bits.OnesCount64 counts them: 64 comparisons, one compare instruction, one popcount.
  • ReverseBits is the GFNI trick from the Go team’s archsimd article. One VGF2P8AFFINEQB multiplies every byte by an 8×8 bit matrix, and the anti-diagonal matrix reverses the bits of 64 bytes at once. No portable SIMD API has this instruction. It is the kind of thing archsimd exists for.
  • The loop bound is i < len(s)-64+1, not i+64 <= len(s). That is deliberate. See the trap below.

A small driver:

// cmd/demo/main.go — call the dispatching API and compare with plain loops
package main

import (
    "bytes"
    "fmt"
    "math/bits"

    "example.com/simdlab"
)

func main() {
    fmt.Println("path:", simdlab.Path())

    a := make([]float32, 1000)
    b := make([]float32, 1000)
    for i := range a {
        a[i] = 1.0 / float32(i+1)
        b[i] = float32(i%3) + 0.1
    }
    var loop float32
    for i := range a {
        loop += a[i] * b[i]
    }
    fmt.Printf("dot: simd=%.7f loop=%.7f equal=%t\n", simdlab.Dot(a, b), loop, simdlab.Dot(a, b) == loop)

    text := bytes.Repeat([]byte("line one\nline two\n"), 50)
    fmt.Println("newlines:", simdlab.Count(text, '\n'), "bytes.Count:", bytes.Count(text, []byte{'\n'}))

    src := []byte{0b0000_0001, 0b1100_0000, 0b1010_1010, 0xF0}
    dst := make([]byte, len(src))
    simdlab.ReverseBits(dst, src)
    for i := range src {
        fmt.Printf("%08b -> %08b (bits.Reverse8 %08b)\n", src[i], dst[i], bits.Reverse8(src[i]))
    }
}

Case 3: test every path on one machine

A vector path that only runs on the CI machine’s CPU is a path you haven’t tested. The table test compares all three functions with the scalar twin at every length from 0 to 300, so every tail size is covered:

// simdlab_test.go — vector paths must agree with the scalar reference at every length
package simdlab

import (
    "bytes"
    "math"
    "math/rand/v2"
    "testing"
)

func TestAgainstScalar(t *testing.T) {
    t.Logf("path: %s", Path())
    r := rand.New(rand.NewPCG(1, 2))
    for n := 0; n <= 300; n++ {
        a, b := make([]float32, n), make([]float32, n)
        for i := range a {
            a[i], b[i] = r.Float32()*2-1, r.Float32()*2-1
        }
        got, want := Dot(a, b), dotScalar(a, b)
        if math.Abs(float64(got-want)) > 1e-4*float64(n+1) {
            t.Fatalf("Dot n=%d: got %v want %v", n, got, want)
        }

        s := make([]byte, n)
        for i := range s {
            s[i] = byte(r.IntN(4))
        }
        if got, want := Count(s, 2), countScalar(s, 2); got != want {
            t.Fatalf("Count n=%d: got %d want %d", n, got, want)
        }

        d1, d2 := make([]byte, n), make([]byte, n)
        ReverseBits(d1, s)
        reverseScalar(d2, s)
        if !bytes.Equal(d1, d2) {
            t.Fatalf("ReverseBits n=%d differs", n)
        }
    }
}

The Count row is the lesson. A naive byte loop is slow, but nobody should be running one. bytes.Count already has hand-written vector assembly, and beating it by 20% on one CPU family is not worth an experimental dependency. ReverseBits is the opposite case: no library function does it, and the instruction that does it isn’t reachable any other way.

For plain arithmetic, the portable layer usually does as well. The same dot product written with simd.Float32s (which picked 512-bit vectors on this CPU, or 256-bit under GODEBUG=cpu.avx512f=off) ran at the same speed (portable_simd.go, plus a TestPortable / BenchmarkDotPortable pair in portable_simd_test.go built under the same goexperiment.simd tag):

// portable_simd.go — the same inner product with the portable simd package (any GOARCH)
//go:build goexperiment.simd

package simdlab

import "simd"

// DotPortable uses whatever vector width this machine has (or an emulation).
func DotPortable(a, b []float32) float32 {
    b = b[:len(a)]
    var acc simd.Float32s
    w := acc.Len()
    i := 0
    for ; i < len(a)-w+1; i += w {
        acc = simd.LoadFloat32s(a[i:i+w]).MulAdd(simd.LoadFloat32s(b[i:i+w]), acc)
    }
    if i < len(a) {
        x, _ := simd.LoadFloat32sPart(a[i:])
        y, _ := simd.LoadFloat32sPart(b[i:])
        acc = x.MulAdd(y, acc)
    }
    lanes := make([]float32, w)
    acc.Store(lanes)
    var s float32
    for _, v := range lanes {
        s += v
    }
    return s
}

// VectorBits reports the width the portable package picked.
func VectorBits() (int, bool) { return simd.VectorBitSize(), simd.Emulated() }

The trap

Importing archsimd without a build constraint

// main.go — imports archsimd with no build constraint
package main

import (
    "fmt"
    "simd/archsimd"
)

func main() {
    v := archsimd.BroadcastFloat32x8(1.5)
    fmt.Println(v.Add(v))
}
go build .
GOEXPERIMENT=simd go run .
GOEXPERIMENT=simd GOARCH=arm64 go build .
package example.com/naive
    imports simd/archsimd: build constraints exclude all Go files in /home/box/sdk/go1.27.1/src/simd/archsimd
{3,3,3,3,3,3,3,3}
# example.com/naive
./main.go:10:16: undefined: archsimd.BroadcastFloat32x8

It fails twice. Without the experiment the package does not exist. With the experiment on arm64 the package exists, but 256-bit types don’t. The rule is mechanical: every file that imports simd/archsimd carries //go:build goexperiment.simd && <arch>, and a sibling file with the negated constraint provides the same API.

Expecting bit-identical floating-point results

The vector dot product keeps 16 partial sums and adds them at the end. The loop keeps one. Floating-point addition is not associative, so 7.3820782 vs 7.3820772 is correct behaviour, not a bug. Compare float kernels against the scalar twin with a tolerance scaled to the input length, as the test does. Never use ==. If a caller truly needs reproducible results across machines, the vector path can’t be used for that value.

Writing the loop bound the “obvious” way

The Go team calls this out explicitly, and the compiler’s bounds-check debug flag shows why:

// bce.go — the same loop, two ways of writing the bound
//go:build goexperiment.simd && amd64

package bce

import "simd/archsimd"

func SumA(s []float32) archsimd.Float32x8 { // i+8 <= len(s): i+8 might overflow
    var acc archsimd.Float32x8
    for i := 0; i+8 <= len(s); i += 8 {
        acc = acc.Add(archsimd.LoadFloat32x8(s[i : i+8]))
    }
    return acc
}

func SumB(s []float32) archsimd.Float32x8 { // i < len(s)-8+1: provably in range
    var acc archsimd.Float32x8
    for i := 0; i < len(s)-8+1; i += 8 {
        acc = acc.Add(archsimd.LoadFloat32x8(s[i : i+8]))
    }
    return acc
}
GOEXPERIMENT=simd go build -gcflags='-d=ssa/check_bce/debug=1' .
# example.com/bce
./bce.go:11:41: Found IsSliceInBounds

Only SumA (line 11) keeps a bounds check inside the loop. The compiler cannot rule out i+8 overflowing, so it cannot prove s[i:i+8] is in range. In a scalar loop that is noise. In a loop whose body is one or two instructions, it is a large part of the work.

Vectors in arrays and structs

archsimd values are 16–64 bytes. Go’s register allocator currently keeps them in registers only as plain locals and parameters. Put eight of them in a [8]archsimd.Int32x8 or a struct and the compiler spills them to the stack on every access. That is why the Go team’s 8×8 transpose takes eight separate parameters. Keep vectors as locals in hot loops, and don’t store them in heap objects. The package documentation says so explicitly.

The boring rule

  • Profile first. If the hot loop is a search, a hash or crypto, the standard library has probably vectorized it already.
  • Prefer simd (portable) for arithmetic. Use archsimd when you need a specific instruction or have measured that simd is not enough.
  • Every archsimd file: //go:build goexperiment.simd && amd64 (or arm64 / wasm), plus a negated-constraint fallback with the same API.
  • Every exported entry point checks CPU features first and falls back to a scalar twin. Never call a vector helper that hasn’t been guarded.
  • Test against the scalar twin at every tail length, under GODEBUG=cpu.avx512f=off and cpu.avx2=off, and without the experiment. Use tolerances for floats.
  • Treat the API as unstable. Go 1.27 already renamed Merge → IfElse and replaced the As* casts with ToBits / BitsTo* / ReshapeTo* (the old names still compile, marked Deprecated). Pin the Go version in CI and expect to edit this code when you upgrade.

Try this

  1. Add a CountAVX2 path using Uint8x32 and Mask8x32.ToBits(), wire it into Count for CPUs without AVX-512, and prove it runs with GODEBUG=cpu.avx512f=off.
  2. Change dot16 to keep four accumulators. Benchmark it with -count=10 and benchstat. Does it help on your CPU, and is the kernel limited by FMA latency or by memory?
  3. Write ReverseBits with the portable simd package. What operation is missing, and how fast is the best portable version you can write compared with GFNI?
  4. Build the module with GOEXPERIMENT=simd GOOS=wasip1 GOARCH=wasm and add a wasm build tag to a 128-bit Float32x4 version of dot. Run the tests under a WASI runtime.
  5. Look up go doc simd/archsimd.Float32x8.Merge and AsUint32x8 in your toolchain and replace any deprecated calls in the code you write.
