Upgrading a Module to Go 1.27: A Hands-On Lab

Thesis

What’s New in Go 1.27 lists the changes. This chapter is the companion lab: you run the upgrade on small modules and watch each 1.27 tooling change either catch a bug or rewrite a file. Most of these changes only take effect once a module’s go line says 1.27, so the order you do the steps in matters.

Verified with Go 1.27.2 (linux/amd64) on 2026-10-11. Go 1.26.2 was fetched with GOTOOLCHAIN=go1.26.2 for the before-and-after comparisons. Primary source: Go 1.27 release notes.

Learning goals

  • Find standard-library calls that are too new for your go line before CI does
  • Raise the go line safely, including godebug settings that no longer exist
  • Let go mod tidy, go fix and go vet clean up what 1.27 knows how to clean
  • Use the new traceback labels, go test -json output types and go doc queries in daily debugging

Step 0: which toolchain is running?

go version
go version go1.27.2 linux/amd64

Inside a module, the go command may switch to a newer toolchain if go.mod asks for one (GOTOOLCHAIN=auto, the default). In this lab GOTOOLCHAIN=local is set, so the installed 1.27.2 is always used, except where a step names an older one explicitly.

Step 1: go test now runs stdversion

The trap: your laptop has Go 1.27, CI or a downstream user still builds with 1.26, and your module says go 1.26. You call a 1.27 API, everything passes locally, and their build breaks.

// go.mod
module example.com/pathx

go 1.26
// pathx.go
package pathx

import "strings"

// Base returns the final element of a slash-separated path.
func Base(p string) string {
    _, file, ok := strings.CutLast(p, "/") // added in Go 1.27
    if !ok {
        return p
    }
    return file
}
// pathx_test.go
package pathx

import "testing"

func TestBase(t *testing.T) {
    if got := Base("desk/shift/ticket.txt"); got != "ticket.txt" {
        t.Fatalf("Base = %q", got)
    }
}
go build ./...; echo "exit=$?"
go test ./...;  echo "exit=$?"
exit=0
# example.com/pathx
# [example.com/pathx]
./pathx.go:8:25: strings.CutLast requires go1.27 or later (module is go1.26)
FAIL    example.com/pathx [build failed]
FAIL
exit=1

go build succeeds because the 1.27 toolchain does have strings.CutLast. go test now runs the stdversion analyzer as part of its vet subset (atomic, bools, buildtag, directive, errorsas, ifaceassert, nilfunc, printf, stdversion, stringintconv, tests), so the mismatch fails the test run. With a real 1.26 toolchain the same file does not build at all:

GOTOOLCHAIN=go1.26.2 go build ./...
# example.com/pathx
./pathx.go:8:25: undefined: strings.CutLast

There are two correct fixes:

  1. Raise the go line (Step 2) if you no longer support 1.26.
  2. Keep supporting 1.26 with a pair of build-tagged files:
// pathx.go
package pathx

// Base returns the final element of a slash-separated path.
func Base(p string) string {
    _, file, ok := cutLast(p, "/")
    if !ok {
        return p
    }
    return file
}
// cut_go127.go
//go:build go1.27

package pathx

import "strings"

func cutLast(s, sep string) (before, after string, found bool) {
    return strings.CutLast(s, sep)
}
// cut_old.go
//go:build !go1.27

package pathx

import "strings"

func cutLast(s, sep string) (before, after string, found bool) {
    if i := strings.LastIndex(s, sep); i >= 0 {
        return s[:i], s[i+len(sep):], true
    }
    return s, "", false
}
go test ./...
GOTOOLCHAIN=go1.26.2 go test ./...
ok      example.com/pathx   0.002s
ok      example.com/pathx   0.002s

stdversion reads the //go:build go1.27 constraint as raising that file’s language version, so cut_go127.go passes the check.

Step 2: raise the go line, and check godebug

go mod edit -go=1.27

Setting go 1.27 turns on the new language features (generic methods, promoted-field keys in struct literals, wider function type inference), traceback labels (Step 6) and go mod tidy’s block merging (Step 3). It also makes the go command strict about removed GODEBUG settings. A setting whose support has been removed is accepted only at its final default value:

// go.mod
module example.com/gd

go 1.27

godebug asynctimerchan=1
go run .
go: error loading go.mod:
go.mod:5: removed GODEBUG "asynctimerchan" set to old value "1" (https://go.dev/doc/godebug#go-127)

With godebug asynctimerchan=0 the same module builds and prints built. If the error appears, the program depended on pre-1.23 buffered timer channels. Fix the code, then delete the line. Go 1.27 also removed tlsunsafeekm, tlsrsakex, tls3des, tls10server, x509keypairleaf and gotypesalias. Search for all of them:

grep -rnE 'asynctimerchan|tlsunsafeekm|tlsrsakex|tls3des|tls10server|x509keypairleaf|gotypesalias' \
  --include=go.mod --include='*.go' .

Step 3: go mod tidy merges require blocks

Long-lived modules collect stray require blocks from hand edits and merge conflicts:

// go.mod (before)
module example.com/svc

go 1.27

require github.com/google/uuid v1.6.0

// Pinned for the YAML config loader; see ADR-7.
require gopkg.in/yaml.v3 v3.0.1

require (
    golang.org/x/sync v0.10.0
    golang.org/x/text v0.21.0 // indirect
)
// main.go
package main

import (
    "fmt"

    "github.com/google/uuid"
    "golang.org/x/sync/errgroup"
    "gopkg.in/yaml.v3"
)

func main() {
    var g errgroup.Group
    g.Go(func() error { return nil })
    out, _ := yaml.Marshal(map[string]string{"id": uuid.Nil.String()})
    fmt.Print(string(out), g.Wait(), "\n")
}
go mod tidy && cat go.mod
module example.com/svc

go 1.27

require (
    github.com/google/uuid v1.6.0
    golang.org/x/sync v0.10.0
    // Pinned for the YAML config loader; see ADR-7.
    gopkg.in/yaml.v3 v3.0.1
)

The three blocks became one direct block, the comment followed its requirement, and the unused x/text was dropped as before. The merge only happens for modules that say go 1.27 or later. The same input with go 1.26 keeps its shape:

module example.com/svc

go 1.26

require github.com/google/uuid v1.6.0

// Pinned for the YAML config loader; see ADR-7.
require gopkg.in/yaml.v3 v3.0.1

require golang.org/x/sync v0.10.0

Commit the tidy in its own commit, so reviewers can see that the dependency set did not change.

Step 4: let go fix modernize

go fix now runs the modernizer suite. Go 1.27 adds atomictypes, embedlit, slicesbackward and unsafefuncs, renames waitgroup to waitgroupgo, and removes fmtappendf. Here is a file written in 1.20-era style:

// main.go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

type Address struct{ City, State string }

type Employee struct {
    Address
    Title string
}

var hits int64

func main() {
    e := Employee{Address: Address{City: "Lisbon", State: "PT"}, Title: "Engineer"}

    var wg sync.WaitGroup
    for range 4 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            atomic.AddInt64(&hits, 1)
        }()
    }
    wg.Wait()

    xs := []int{1, 2, 3}
    for i := len(xs) - 1; i >= 0; i-- {
        fmt.Print(xs[i], " ")
    }
    fmt.Println()
    fmt.Println(e.City, e.Title, atomic.LoadInt64(&hits))
}
go fix -diff ./...; echo "exit=$?"

(The diff header normally shows absolute paths. They are shortened here.) Four 1.27-era analyzers fired: embedlit (promoted-field keys), atomictypes (atomic.Int64), waitgroupgo (wg.Go, Go 1.25) and slicesbackward. -diff exits 1 when it has changes, which makes it usable as a CI gate. Apply and confirm that behaviour is unchanged:

go fix ./... && go run . && go vet ./...
3 2 1 
Lisbon Engineer 4

The output matches the original program. To apply one analyzer at a time, for example in a large repository, name it: go fix -embedlit ./.... go tool fix help lists every registered analyzer.

atomictypes changed an exported-looking package variable’s type. In a library, review that kind of change as an API change.

Step 5: vet catches %w with a pointer to a value error

// main.go
package main

import (
    "errors"
    "fmt"
)

type NotFound struct{ Key string }

func (e NotFound) Error() string { return "not found: " + e.Key }

func lookup(k string) error {
    p := &NotFound{Key: k}
    return fmt.Errorf("lookup: %w", p)
}

func main() {
    err := lookup("port")
    var nf NotFound
    fmt.Println(err, errors.As(err, &nf))
}

Before 1.27 this compiled and vetted cleanly, and printed lookup: not found: port false. The false is the bug: the chain holds a *NotFound, so errors.As for NotFound never matches. 1.27’s printf analyzer reports it, and because printf is in the go test subset, so does go test:

go vet .
main.go:15:29: %w wants operand of error type NotFound, not pointer type *NotFound (defeats errors.Is)

Fix it by wrapping the value (fmt.Errorf("lookup: %w", NotFound{Key: k})), or by giving Error a pointer receiver if the type is meant to be used by pointer.

Step 6: goroutine labels in crash tracebacks

For modules at go 1.27, a traceback header now includes the goroutine’s runtime/pprof labels. If you already label request goroutines for profiling, crashes now identify the request too.

// main.go
package main

import (
    "context"
    "runtime/pprof"
    "time"
)

func main() {
    labels := pprof.Labels("request_id", "r-42", "route", "/checkout")
    pprof.Do(context.Background(), labels, func(context.Context) {
        go handle() // a goroutine started here inherits the labels
    })
    time.Sleep(time.Second)
}

func handle() {
    var m map[string]int
    m["boom"]++ // nil map write
}
go run . 2>&1 | head -5
panic: assignment to entry in nil map

goroutine 7 [running] {request_id: "r-42", route: /checkout}:
main.handle()
    /workspace/go127lab/ch3/tbl-child/main.go:20 +0x28

With GODEBUG=tracebacklabels=0, or with the same code in a go 1.26 module, the header is the familiar goroutine 7 [running]:. Turn labels off if they might carry sensitive data such as user emails, because tracebacks end up in logs and crash reports.

There is one surprise. A panic directly inside the function passed to pprof.Do prints no labels:

// main.go
package main

import (
    "context"
    "runtime/pprof"
)

func main() {
    labels := pprof.Labels("request_id", "r-42", "route", "/checkout")
    pprof.Do(context.Background(), labels, func(context.Context) {
        var m map[string]int
        m["boom"]++ // panics inside Do itself
    })
}
panic: assignment to entry in nil map

goroutine 1 [running]:
main.main.func1({0x58a490?, 0x2eae847841e0?})
    /workspace/go127lab/ch3/tbl-direct/main.go:13 +0x28

pprof.Do is implemented as defer SetGoroutineLabels(ctx) followed by setting the new labels and calling f. An unrecovered panic runs deferred calls before it prints the traceback, so the labels are already restored by the time the header is written. Labels survive in goroutines started inside Do (as above) and in code that calls pprof.SetGoroutineLabels directly.

Step 7: go test -json classifies output

Test dashboards that parse go test -json used to guess which lines were failures. 1.27 adds an optional OutputType field to "Action":"output" events:

// tj_test.go
package tj

import "testing"

func TestPort(t *testing.T) {
    t.Log("checking default port")
    if got := 8081; got != 8080 {
        t.Errorf("port = %d, want 8080", got)
    }
}
go test -json ./... | python3 -c '
import sys, json
for l in sys.stdin:
    e = json.loads(l)
    if e.get("Action") == "output":
        print(json.dumps({k: e[k] for k in ("Action","Test","OutputType","Output") if k in e}))'
{"Action": "output", "Test": "TestPort", "OutputType": "frame", "Output": "=== RUN   TestPort\n"}
{"Action": "output", "Test": "TestPort", "Output": "    tj_test.go:7: checking default port\n"}
{"Action": "output", "Test": "TestPort", "OutputType": "error", "Output": "    tj_test.go:9: port = 8081, want 8080\n"}
{"Action": "output", "Test": "TestPort", "OutputType": "frame", "Output": "--- FAIL: TestPort (0.00s)\n"}
{"Action": "output", "OutputType": "frame", "Output": "FAIL\n"}
{"Action": "output", "OutputType": "frame", "Output": "FAIL\texample.com/tj\t0.002s\n"}

t.Log lines carry no OutputType. t.Errorf lines are error, continuation lines of a multi-line error are error-continue, and the harness’s own === RUN / --- FAIL lines are frame. A CI annotator can now select exactly the error and error-continue events. go doc cmd/test2json documents the field.

Step 8: go doc for a version you have not installed

During an upgrade you often need to know whether a dependency’s API changed between versions. go doc now accepts package@version and fetches it through the module proxy without touching go.mod:

go doc github.com/google/uuid@v1.3.0 NewV7
go doc github.com/google/uuid@v1.6.0 NewV7 | head -4
go: downloading github.com/google/uuid v1.3.0
doc: no symbol NewV7 in package github.com/google/uuid
package uuid // import "github.com/google/uuid"

func NewV7() (UUID, error)
    UUID version 7 features a time-ordered value field derived from the widely

The -ex flag lists the runnable examples next to each symbol, and naming an example prints its source and expected output:

go doc strings.ExampleCut
package main

import (
    "fmt"
    "strings"
)

func main() {
    show := func(s, sep string) {
        before, after, found := strings.Cut(s, sep)
        fmt.Printf("Cut(%q, %q) = %q, %q, %v\n", s, sep, before, after, found)
    }
    show("Gopher", "Go")
    show("Gopher", "ph")
    show("Gopher", "er")
    show("Gopher", "Badger")
}

Output: 
Cut("Gopher", "Go") = "", "pher", true
Cut("Gopher", "ph") = "Go", "er", true
Cut("Gopher", "er") = "Goph", "", true
Cut("Gopher", "Badger") = "Gopher", "", false

New 1.27 symbols do not always ship with examples yet: go doc strings.ExampleCutLast reports no symbol ExampleCutLast in package strings on 1.27.2.

Other 1.27 tooling changes to know

Change What to do
gofmt column-alignment fix Running 1.27 gofmt over already formatted code can produce small whitespace diffs. Reformat in a separate commit.
go tool trace -http=:6060 binds to localhost only Use -http=0.0.0.0:6060 inside containers you reach from outside.
bzr support removed Modules hosted only on Bazaar can no longer be fetched directly. Use a proxy or vendor them.
Response files (@file) for compile, link, asm, cgo, cover, pack Build systems with very long command lines can pass arguments in a file.
GOEXPERIMENT=nosizespecializedmalloc, nojsonv2 Temporary escape hatches for runtime/JSON regressions. Expect them to disappear in a later release.

The upgrade checklist

  1. go test ./... on 1.27 before changing go.mod. Fix stdversion and new printf findings.
  2. go mod edit -go=1.27. Fix any removed-godebug errors.
  3. go mod tidy in its own commit.
  4. go fix -diff ./..., review, go fix ./..., in its own commit.
  5. gofmt -l . and accept the whitespace-only changes.
  6. Decide on tracebacklabels for services whose labels could be sensitive.
  7. Update CI to annotate from OutputType.

The trap

  • Trusting go build alone. It does not run stdversion. go test and go vet do.
  • Raising go and godebug in the same commit without testing. The removed-setting error stops every build until it is fixed.
  • Bulk go fix in a library. atomictypes can change the types of package variables.
  • Expecting labels from a panic inside pprof.Do. They are restored before the traceback prints.

The boring rule

Upgrade the toolchain first, the go line second and the code third, and keep each step in its own reviewable commit.
