Why a Goroutine Switch Is Cheap: The Mechanism

Thesis

A goroutine switch on Go 1.27.2 takes about 100–185 ns on the test machine below. A blocking hand-off between two OS threads takes 0.7–3.6 µs, between 4 and 20 times longer. The usual explanation is “Go saves fewer registers”, which is true but explains only a tiny part of the gap. In the CPU profile later in this chapter, runtime.gogo, the routine that restores registers, accounts for under 1% of a channel ping-pong.

The gap really comes from three things:

  1. The switch is a function call. Goroutines give up the CPU inside a runtime call (gopark → mcall). Go’s internal ABI has no callee-saved registers, so the compiler has already spilled every live value to the stack before that call. Only a handful of values (SP, PC, BP, the closure context and the g pointer) describe where to resume.
  2. It never enters the kernel. Parking, readying and resuming a goroutine are loads, stores and a few atomics on runtime structures in user space. No trap, no kernel scheduler, no TLB or address-space work, and the OS thread keeps running.
  3. Stacks are small and movable. A parked goroutine costs about 2 KiB of stack, so a million of them fit in RAM, and growth is a prologue check plus a copy.

The chapter goes through each mechanism in the Go 1.27.2 runtime source, measures it, and then shows the cases where a “goroutine switch” costs as much as a thread switch: blocking syscalls, hand-offs to idle Ps, and signal-based preemption.

Scheduler Deep Dive (GMP) introduces G, M and P, and Stack Growth and Copying introduces stack growth. This chapter goes one level lower, to the instructions.

Verified on Go 1.27.2 (linux/amd64), Linux 6.12 on an 8-vCPU KVM guest (Intel Xeon), on 2026-10-11. All source links are pinned to the go1.27.2 tag.

Learning goals

  • Name the fields in g, m, p and gobuf that a switch touches
  • Read gogo, mcall, morestack and asyncPreempt in asm_amd64.s / preempt_amd64.s
  • Explain why a cooperative switch saves only SP/PC/BP/ctxt, and why asynchronous preemption saves everything
  • Follow gopark → park_m → schedule → execute → gogo, and goready → runnext
  • Measure goroutine and thread hand-offs with benchmarks, perf stat, getrusage and schedtrace
  • Predict when a goroutine operation turns into an OS context switch

1. The data: g, m, p and gobuf

Excerpts from runtime2.go (Go 1.27.2):

type gobuf struct {          // runtime2.go:303
    sp   uintptr
    pc   uintptr
    g    guintptr
    ctxt unsafe.Pointer      // closure context (DX on amd64); a GC root
    lr   uintptr             // link register (arm64, ppc64, …); unused on amd64
    bp   uintptr             // frame pointer
}

type g struct {              // runtime2.go:471
    stack        stack       // [lo, hi) of this goroutine's stack
    stackguard0  uintptr     // compared in every function prologue
    m            *m          // current M, nil when not running
    sched        gobuf       // where to resume
    atomicstatus atomic.Uint32
    goid         uint64
    waitreason   waitReason
    preempt      bool
    lockedm      muintptr    // set by runtime.LockOSThread
    // …
}

type m struct {              // runtime2.go:616
    g0   *g                  // goroutine with the scheduling stack
    curg *g                  // goroutine currently running on this M
    p    puintptr            // attached P, nil in a syscall
    // …
}

type p struct {              // runtime2.go:774
    runqhead uint32
    runq     [256]guintptr   // local run queue
    runnext  guintptr        // next G to run, inheriting the time slice
    // …
}

Some things to notice:

  • A paused goroutine is represented by one gobuf: six words, two of which (g, lr) are bookkeeping on amd64. Everything else the goroutine needs (locals, spilled registers, return addresses) is on its own stack, which stays where it is.
  • Every M has a g0, a goroutine with a normal-sized OS-thread stack, on which the scheduler itself runs. A switch is therefore two jumps: user G → g0 (to run scheduler code) → next G.
  • The current g lives in R14 on amd64 under ABIInternal (ABI spec, amd64 table). Restoring “which goroutine am I” is a single register move.

2. Why so few registers: the ABI and cooperative safe-points

The Go internal ABI (abi-internal.md) says, for amd64:

There are no callee-save registers, so a call may overwrite any register that doesn’t have a fixed meaning, including argument registers.

The section on clobber sets adds the reason: “As defined, the ABI does not use callee-save registers. This significantly simplifies the garbage collector and the compiler’s register allocator, but at some performance cost.”

The consequence for switching: a goroutine always parks inside a function call. Channel operations, mutexes, time.Sleep, network I/O and runtime.Gosched all end up in gopark or mcall. Because no register survives a call, the compiler has already stored every live value in the caller’s frame before the call instruction. The non-cooperative preemption design (proposal 24543) states the property directly: function-call safe-points “ensure that no registers are live”, and the GC “has complete information about its entire stack” at them. So the state to save is just where the goroutine is:

Saved by a cooperative switch (amd64) Why
SP top of this goroutine’s stack
PC the return address into the caller
BP frame pointer, so profilers and tracebacks can unwind
ctxt (DX) closure context, only non-zero on a few paths such as morestack
g (R14, TLS) identity of the running goroutine

Compare that with a kernel thread switch. The kernel cannot know which registers are live at an arbitrary interrupt point, so it saves the full user register file on kernel entry. The FPU/SSE/AVX state is saved with XSAVE-family instructions when the next task needs the FPU (on AVX-512 machines that is over 2 KiB). After that it still runs the kernel scheduler.

The comparison is not “Go saves fewer registers than C”. A hand-written user-space context switch in C, such as Boost.Context’s fcontext, also saves only the callee-saved registers plus SP and PC (about 8 words on x86-64 SysV), and it is also fast. glibc’s swapcontext is slower because it also makes an rt_sigprocmask system call. The expensive part of a thread switch is the kernel path: trap, scheduler, wakeup, mitigations. Section 6 measures this.

3. The instructions: mcall and gogo

Going to sleep: mcall (asm_amd64.s#L425)

gopark ends with mcall(park_m). mcall saves the caller’s resume point into g.sched, switches to g0’s stack and calls park_m(g) there:

TEXT runtime·mcall<ABIInternal>(SB), NOSPLIT, $0-8
    MOVQ    AX, DX  // DX = fn
    // Save state in g->sched. The caller's SP and PC are restored by gogo to
    // resume execution in the caller's frame (implicit return). …
    MOVQ    SP, BX  // hide (SP) reads from vet
    MOVQ    8(BX), BX   // caller's PC
    MOVQ    BX, (g_sched+gobuf_pc)(R14)
    LEAQ    fn+0(FP), BX    // caller's SP
    MOVQ    BX, (g_sched+gobuf_sp)(R14)
    MOVQ    (BP), BX // caller's BP
    MOVQ    BX, (g_sched+gobuf_bp)(R14)

    // switch to m->g0 & its stack, call fn
    MOVQ    g_m(R14), BX
    MOVQ    m_g0(BX), SI    // SI = g.m.g0
    …
    MOVQ    R14, AX     // AX (and arg 0) = g
    MOVQ    SI, R14     // g = g.m.g0
    get_tls(CX)     // Set G in TLS
    MOVQ    R14, g(CX)
    MOVQ    (g_sched+gobuf_sp)(R14), SP // sp = g0.sched.sp
    MOVQ    $0, BP  // clear frame pointer, as caller may execute on another M
    PUSHQ   AX  // open up space for fn's arg spill slot
    MOVQ    0(DX), R12
    CALL    R12     // fn(g)

(… marks lines omitted here, such as the runtimesecret experiment and the badmcall check.) The whole save is three stores: PC, SP, BP. The stored PC is the caller’s return address, so when the goroutine resumes it looks to the caller as though mcall simply returned.

Waking up: gogo (asm_amd64.s#L402)

When the scheduler on g0 has picked the next goroutine, execute calls gogo(&gp.sched):

TEXT runtime·gogo(SB), NOSPLIT, $0-8
    MOVQ    buf+0(FP), BX       // gobuf
    MOVQ    gobuf_g(BX), DX
    MOVQ    0(DX), CX       // make sure g != nil
    JMP gogo<>(SB)

TEXT gogo<>(SB), NOSPLIT, $0
    get_tls(CX)
    MOVQ    DX, g(CX)
    MOVQ    DX, R14     // set the g register
    MOVQ    gobuf_sp(BX), SP    // restore SP
    MOVQ    gobuf_ctxt(BX), DX
    MOVQ    gobuf_bp(BX), BP
    MOVQ    $0, gobuf_sp(BX)    // clear to help garbage collector
    MOVQ    $0, gobuf_ctxt(BX)
    MOVQ    $0, gobuf_bp(BX)
    MOVQ    gobuf_pc(BX), BX
    JMP BX

That is the whole context switch: about 15 instructions, all memory moves, ending in an indirect JMP. No privilege change and no system call.

The related helpers in 1.27.2 are systemstack (L489), which runs a function on g0 and comes back (used by goready), and gosave_systemstack_switch (L855), its save half. There is no longer a standalone runtime·gosave on amd64.

4. The control flow: gopark, goready and runnext

G1: ch <- v  ─ no receiver ─►  gopark ─► mcall(park_m) ─┐
                                                        │ on g0
                                  park_m: casgstatus(_Grunning→_Gwaiting)
                                          dropg(); unlockf(); schedule()
                                  schedule ─► findRunnable ─► execute(G2)
                                  execute ─► gogo(&G2.sched)  ─► G2 runs

G2: <-ch  ─ sender waiting ─► goready(G1) ─► systemstack(ready)
                                  ready: casgstatus(_Gwaiting→_Grunnable)
                                         runqput(pp, G1, next=true)   // runnext
                                         wakep()   // maybe wake an idle P
  • gopark records the wait reason and unlock function on the M and calls mcall(park_m).
  • park_m changes the status, detaches G from M (dropg), runs the unlock callback (for channels, chanparkcommit releases the channel lock only after the G is safely parked), and calls schedule.
  • goready → ready puts the woken G in p.runnext. When the current G blocks, schedule finds it there first and calls execute(gp, inheritTime=true).
  • inheritTime means the woken goroutine shares the current time slice, and execute skips schedtick++. A ping-pong pair therefore behaves like one goroutine to the scheduler, which is why its fairness depends on sysmon preemption. The comment in runqput explains this. You can see the effect in schedtrace below: millions of switches, but only hundreds of schedticks.

5. Small, growable stacks

Cheap switching only helps if you can afford many goroutines, and that depends on stack size. Every Go function prologue (except //go:nosplit ones) compares SP with g.stackguard0. Here is deep from the listing below, disassembled:

morestack uses the same trick as mcall. It saves f’s PC/SP/BP/ctxt into g.sched, switches to g0 and calls newstack. That function allocates a stack of twice the size (newsize := oldsize * 2, stack.go:1179) and calls copystack. copystack copies the old stack and uses the compiler’s stack maps to adjust every pointer into it. Stacks can move because the runtime knows exactly where every pointer to them is.

The same prologue check is the cooperative preemption hook. To preempt a goroutine, the runtime sets stackguard0 = stackPreempt, so the next prologue “fails”, and newstack reschedules instead of growing (comment at the top of preempt.go).

    "fmt"
    "runtime"

    metrics.Read(s)

//go:noinline
func deep(n int) int {
    var pad [128]byte // make each frame big enough to force growth
    if n == 0 {
        return int(pad[0])
    }
    return deep(n-1) + int(pad[n%128])
}

func main() {
    // 1. What does a parked goroutine cost?
    const N = 100_000
    runtime.GC()

    var wg sync.WaitGroup
    block := make(chan struct{})
    for range N {
        wg.Add(1)
        go func() { wg.Done(); <-block }()
    }
    wg.Wait()
    fmt.Printf("stack memory per parked goroutine: %d bytes\n", (stackBytes()-before)/N)
    close(block)

    // 2. Stacks move when they grow.
    done := make(chan struct{})
    go func() {
        var x int
        p0 := uintptr(unsafe.Pointer(&x))
        deep(10_000) // needs well over 1 MiB of stack
        p1 := uintptr(unsafe.Pointer(&x))
        fmt.Printf("&x before growth: %#x\n&x after growth:  %#x\nmoved: %v\n", p0, p1, p0 != p1)
        close(done)
    }()
    <-done
}

6. Measuring: goroutine vs OS-thread hand-off

One program with four ways to bounce control between two parties:

  • gosched: two goroutines alternate with runtime.Gosched (the bare switch, through the global run queue)
  • chan: two goroutines, unbuffered channels (the realistic Go case)
  • futex: two goroutines locked to their own OS threads (runtime.LockOSThread) that sleep and wake each other with raw futex(2), so every hand-off is a kernel thread switch
  • pipe: the same, using blocking read(2)/write(2) on pipes through syscall.Read, which goes through the runtime’s syscall path
// main.go
//
// Ping-pong between two execution contexts and report the cost of one
// hand-off (half a round trip). Modes:
//
//  gosched  two goroutines taking turns with runtime.Gosched (bare switch)
//  chan   two goroutines, unbuffered channels (runtime switch)
//  futex  two locked OS threads, raw futex wait/wake (kernel switch)
//  pipe   two locked OS threads, blocking read/write on pipes
package main

import (
    "flag"
    "fmt"
    "os"
    "runtime"
    "sync/atomic"
    "syscall"
    "time"
    "unsafe"
)

const (
    futexWait = 0 | 128 // FUTEX_WAIT | FUTEX_PRIVATE_FLAG
    futexWake = 1 | 128 // FUTEX_WAKE | FUTEX_PRIVATE_FLAG
)

func chanPingPong(n int) {
    ping, pong := make(chan struct{}), make(chan struct{})
    go func() {
        for range n {
            <-ping
            pong <- struct{}{}
        }
    }()
    for range n {
        ping <- struct{}{}
        <-pong
    }
}

// With GOMAXPROCS=1, each Gosched hands the P to the other goroutine,
// so one call is one goroutine switch.
func goschedPingPong(n int) {
    done := make(chan struct{})
    go func() {
        for range n {
            runtime.Gosched()
        }
        close(done)
    }()
    for range n {
        runtime.Gosched()
    }
    <-done
}

// turn is 0 when it is the main thread's turn and 1 for the partner.
func futexPingPong(n int) {
    var turn atomic.Uint32
    addr := uintptr(unsafe.Pointer(&turn))
    wait := func(v uint32) { // sleep in the kernel while turn == v
        for turn.Load() == v {
            syscall.RawSyscall6(syscall.SYS_FUTEX, addr, futexWait, uintptr(v), 0, 0, 0)
        }
    }
    wake := func(v uint32) {
        turn.Store(v)
        syscall.RawSyscall6(syscall.SYS_FUTEX, addr, futexWake, 1, 0, 0, 0)
    }
    done := make(chan struct{})
    go func() {
        runtime.LockOSThread()
        for range n {
            wait(0)
            wake(0)
        }
        close(done)
    }()
    runtime.LockOSThread()
    for range n {
        wake(1)
        wait(1)
    }
    <-done
}

func pipePingPong(n int) {
    var a, b [2]int
    must(syscall.Pipe(a[:]))
    must(syscall.Pipe(b[:]))
    buf := []byte{0}
    done := make(chan struct{})
    go func() {
        runtime.LockOSThread()
        x := []byte{0}
        for range n {
            syscall.Read(a[0], x)
            syscall.Write(b[1], x)
        }
        close(done)
    }()
    runtime.LockOSThread()
    for range n {
        syscall.Write(a[1], buf)
        syscall.Read(b[0], buf)
    }
    <-done
}

func must(err error) {
    if err != nil {
        fmt.Fprintln(os.Stderr, err)
        os.Exit(1)
    }
}

func rusage() (vol, invol int64) {
    var ru syscall.Rusage
    must(syscall.Getrusage(syscall.RUSAGE_SELF, &ru))
    return ru.Nvcsw, ru.Nivcsw
}

func main() {
    mode := flag.String("mode", "chan", "gosched | chan | futex | pipe")
    n := flag.Int("n", 1_000_000, "round trips")
    flag.Parse()

    run := map[string]func(int){"gosched": goschedPingPong, "chan": chanPingPong, "futex": futexPingPong, "pipe": pipePingPong}[*mode]
    if run == nil {
        must(fmt.Errorf("unknown mode %q", *mode))
    }
    run(*n / 10) // warm up threads, stacks and caches

    v0, i0 := rusage()
    start := time.Now()
    run(*n)
    el := time.Since(start)
    v1, i1 := rusage()

    handoffs := 2 * *n
    fmt.Printf("mode=%-7s GOMAXPROCS=%d round-trips=%d  %6.1f ns/hand-off  ctx-switches: voluntary=%d involuntary=%d (%.2f per hand-off)\n",
        *mode, runtime.GOMAXPROCS(0), *n, float64(el.Nanoseconds())/float64(handoffs),
        v1-v0, i1-i0, float64(v1-v0+i1-i0)/float64(handoffs))
}

How to read this:

  • A goroutine hand-off costs zero OS context switches. The kernel never sees it. The goroutine is 4–7× cheaper than the best thread case (same core, futex) and ~20× cheaper than the cross-core case, which is the usual one when threads block and wake each other on a multi-core machine.
  • The thread figures include a little Go overhead (the RawSyscall wrapper and an atomic load), so they are a close approximation of a raw kernel thread switch, not an exact measurement. In the pinned runs about 40% of the switches are involuntary. With both threads on one CPU, the kernel most likely preempts the waker in favour of the thread it just woke, and the runtime’s own threads share that CPU too.
  • The cross-core thread case is the slowest because waking a sleeping thread on another CPU means an inter-processor interrupt and, on a VM, a trip through the hypervisor to wake an idle vCPU. Bare metal is usually faster in absolute terms. The ratio is what carries over.
  • pipe costs more than futex because it adds real syscalls (read/write) and the runtime’s entersyscall/exitsyscall bookkeeping.
  • Treat these as one machine’s numbers. Run the program on your own hardware.

7. When a goroutine switch is not cheap

Blocking system calls: entersyscall, handoffp and new threads

A goroutine making a blocking syscall cannot be “switched out” in user space, because its OS thread is stuck in the kernel. The runtime detaches the P instead. entersyscall marks the P as in-syscall. If the call takes longer than one sysmon tick (at least 20 µs), retake takes the P and handoffp hands it to another M, starting a new thread if none is idle, whenever there is other work for that P. Goroutines that block in syscalls therefore cost threads, while goroutines parked in the runtime do not:

// main.go
package main

import (
    "bufio"
    "fmt"
    "os"
    "strings"
    "syscall"
    "time"
)

func threads() string {
    f, _ := os.Open("/proc/self/status")
    defer f.Close()
    sc := bufio.NewScanner(f)
    for sc.Scan() {
        if v, ok := strings.CutPrefix(sc.Text(), "Threads:"); ok {
            return strings.TrimSpace(v)
        }
    }
    return "?"
}

func main() {
    const N = 50
    fmt.Println("start:                         threads =", threads())

    block := make(chan struct{})
    for range N {
        go func() { <-block }() // parks in the runtime: gopark
    }
    time.Sleep(100 * time.Millisecond)
    fmt.Printf("%d goroutines parked on a chan: threads = %s\n", N, threads())

    var p [2]int
    if err := syscall.Pipe(p[:]); err != nil {
        panic(err)
    }
    for range N {
        go func() {
            var b [1]byte
            syscall.Read(p[0], b[:]) // blocks this OS thread in the kernel
        }()
    }
    time.Sleep(100 * time.Millisecond)
    fmt.Printf("%d goroutines blocked in read(2): threads = %s\n", N, threads())
}

Changing the read to an *os.File from os.Pipe keeps the thread count at 4 in the same experiment (50 goroutines blocked in (*os.File).Read: threads = 4, GOMAXPROCS=2). os registers pipes and sockets with the netpoller, so the goroutine parks with gopark and only one thread waits in epoll. Raw syscall.Read, cgo calls and file I/O on regular files have no such path. Each one in flight holds an OS thread, and waking it costs a thread switch plus exitsyscall reacquiring a P.

Hand-offs to idle Ps

When goready makes a goroutine runnable and there is an idle P, wakep may wake a parked M with a futex: a real OS wakeup. This is the 0.01 OS switches per hand-off in the 8-P runs above. It is amortized, but in fan-out patterns that repeatedly wake idle workers, these wakeups can dominate.

LockOSThread and the futex trap

A goroutine locked to a thread (g.lockedm) can only run on that M. Handing control to or from it means a real thread switch, as the futex and pipe numbers show. Mixing locked threads with syscall.RawSyscall is worse. A raw syscall skips entersyscall, so the runtime thinks the goroutine is still running and never releases its P. The futex benchmark above deadlocks under taskset -c 0 without an explicit GOMAXPROCS. Go sets GOMAXPROCS from the CPU affinity mask, which gives 1 there, so the partner goroutine never gets a P to run on. The listings use GOMAXPROCS=4 for that reason, and you should keep RawSyscall for calls that cannot block.

Asynchronous preemption (Go 1.14+)

Cooperative safe-points are function prologues and blocking runtime calls. A loop without calls has none:

// main.go
package main

import (
    "fmt"
    "runtime"
    "time"
)

//go:noinline
func spin(n *uint64) {
    for { // no calls, no allocation: no cooperative preemption point
        *n++
    }
}

func main() {
    runtime.GOMAXPROCS(1)
    var n uint64
    go spin(&n)

    start := time.Now()
    time.Sleep(10 * time.Millisecond) // main must get the only P back
    fmt.Printf("main resumed after %v (asked for 10ms)\n", time.Since(start).Round(time.Millisecond))
}
go build -o preempt . && ./preempt && ./preempt
GODEBUG=asyncpreemptoff=1 timeout 5 ./preempt; echo "exit=$?"
main resumed after 20ms (asked for 10ms)
main resumed after 14ms (asked for 10ms)
exit=124

With asynchronous preemption, sysmon notices that the spinning goroutine has run for more than forcePreemptNS = 10ms (proc.go:6679) and calls preemptone, which sends SIGURG to its thread (sigPreempt = _SIGURG, signal_unix.go:74). Without it (asyncpreemptoff=1) the program never prints and timeout kills it, giving exit 124. Here is the signal under strace:

strace -f -e trace=tgkill -e signal=SIGURG ./preempt 2>&1 | grep -E 'tgkill|SIGURG|main resumed'
[pid 513631] tgkill(513630, 513630, SIGURG <unfinished ...>
[pid 513630] --- SIGURG {si_signo=SIGURG, si_code=SI_TKILL, si_pid=513630, si_uid=1000} ---
[pid 513631] <... tgkill resumed>)      = 0
main resumed after 10ms (asked for 10ms)

Thread 513631 (sysmon) signals 513630, the thread running spin. The signal handler checks that the interrupted PC is an async safe-point (isAsyncSafePoint). If it is, the handler rewrites the signal context so the thread “calls” asyncPreempt. That function is the opposite of mcall: because it interrupts arbitrary code, it saves every register, 14 general-purpose registers plus flags, then the vector register state into p.xRegs. The generated file has 179 lines of register MOVs across its save and restore halves. Then it enters the scheduler. The GC scans that innermost frame conservatively, since there is no register map for an arbitrary PC. The comment block in preempt.go describes this design.

So preemption is the expensive kind of goroutine switch: a signal (a kernel round trip), a full register save, and a conservative scan. It happens at most about every 10 ms per goroutine that hogs a P, so its amortized cost is negligible. Deadlock-free fairness is its purpose, not speed.

The trap

  • “Goroutines are free, so block in syscalls freely.” Each goroutine blocked in a raw syscall or cgo call holds an OS thread. Use os/net types, which use the netpoller, or bound the concurrency.
  • Benchmarking switches with GOMAXPROCS>1 and calling it “switch cost”. Part of what you measure is idle-P wakeups and parallelism. Measure with GOMAXPROCS=1 and with your production setting.
  • RawSyscall plus LockOSThread. The P is never released. Under taskset or a cgroup CPU limit of 1 it can deadlock.
  • Hot ping-pong pairs starving others. runnext with inheritTime lets a pair share one time slice. Fairness relies on sysmon’s 10 ms preemption, so expect tail-latency spikes of that size for other goroutines on the P.
  • Explaining the speed by register count. In the profile, the switch itself is ~1%. Bookkeeping is the rest.

The boring rule

Goroutine switches are cheap when goroutines block on Go things (channels, mutexes, timers, network and pipe I/O through os/net). Anything that blocks in the kernel directly is a thread switch with a goroutine wrapped around it.
