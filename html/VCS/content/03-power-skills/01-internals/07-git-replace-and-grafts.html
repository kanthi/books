git replace: Swapping Objects and Grafting History Without Rewriting

After reading this chapter, you will be able to graft disjoint repository histories together, transparently swap corrupted or sensitive Git objects without altering existing commit hashes, inspect and bypass active replacements in your toolchains, and safely transfer or permanently solidify replace references when migrating repositories.

The problem with immutable history

Every object in Git—commit, tree, blob, or annotated tag—is named by the cryptographic hash of its exact payload. If you change a single byte in a commit message, alter a parent commit pointer to stitch old history together, or redact an exposed token in a file blob, the object’s hash changes. Because child commits store the hashes of their parents and trees store the hashes of their blobs, that single change cascades down the entire directed acyclic graph (DAG). Every downstream commit receives a new identifier, breaking open pull requests, invalidating cryptographic signatures, and disrupting team clones.

Yet engineers frequently face situations where history needs adjustment:

  • Historical archives: A repository was imported as a shallow or squashed snapshot to shed gigabytes of legacy history, but developers still need git log and git blame to trace lines back into the historical archive.
  • Accidental giant blobs or secrets: A local review branch contains a 2 GB test file or an API credential that blocks local tooling or makes diffs sluggish.
  • Upstream commit corrections: A commit message in an upstream vendor branch has a catastrophic typo or missing issue key that local tools require, but rebasing is prohibited because thousands of downstream branches already branch off it.

Git resolves this tension through object replacement (git replace). Instead of rewriting the DAG, Git creates an overlay reference under refs/replace/. High-level Git porcelain commands transparently read the replacement object whenever the original object is requested, while the original object remains untouched in the object database.

How object replacement works under the hood

When Git parses an object identifier (whether looking up a commit during git log, loading a tree during git checkout, or displaying a blob with git show), it consults the ref namespace refs/replace/.

If an object has a SHA-1 or SHA-256 hash of <target-hash>, Git checks for the existence of a reference named:

refs/replace/<target-hash>

If that reference exists, it points to another object in the .git/objects database: <replacement-hash>. Git substitutes <replacement-hash> in place of <target-hash> in memory.

Property Standard History Rewrite (git rebase / filter-repo) Overlay Replacement (git replace)
Object Hash Changes for target and all descendants Remains identical for target and all descendants
Cryptographic Signatures Broken; must be re-signed with new commit hashes Originals keep their signatures; the replacement commit itself is new and unsigned
Remote Propagation Pushed to standard branch refs (refs/heads/*) Skipped by default; requires explicit refspecs
Blast Radius Forces downstream developers to reconcile divergent history Local to repos configured with refs/replace/*
Storage Overhead Rewrites commit tree; requires garbage collection to drop old objects Adds one loose ref and the replacement object
Reversibility Requires reflog recovery or branch backup restore Trivial; delete the reference with git replace -d

The replacement is completely transparent to high-level commands. For instance, running git rev-parse HEAD on a commit that has been replaced returns the original commit hash. But running git cat-file -p HEAD displays the commit header and tree of the replacement object.

       refs/heads/main
              │
              ▼
       ┌──────────────┐
       │ Commit C3    │
       │ parent: C2   │
       └──────┬───────┘
              │
              ▼
       ┌──────────────┐         refs/replace/<C2>
       │ Commit C2    │ ◄───────────────────────────────┐
       │ parent: C1   │                                 │
       └──────┬───────┘                                 │
              │                                         │
              ▼                                         │
       ┌──────────────┐                         ┌───────┴──────┐
       │ Commit C1    │                         │ Commit C2'   │
       │ (root)       │                         │ parent: A3   │
       └──────────────┘                         └───────┬──────┘
                                                        │
┌───────────────────────────┐                           │
│ Archive Repository Tip    │ ◄─────────────────────────┘
│ Commit A3                 │
│ parent: A2                │
└─────────────┬─────────────┘
              │
              ▼
             ...

Because Git substitutes the object in memory when traversing parent pointers, tools traversing C3 -> C2 are transparently routed through C2', continuing back into A3, A2, and A1.

Mechanics of the git replace command

The git replace command suite manages references under refs/replace/. Verified against Git 2.47.3 on Linux, the command supports several operational modes.

1. Basic object-for-object replacement

The fundamental form replaces any arbitrary object with another existing object of the same type:

git replace <target-object> <replacement-object>

This creates refs/replace/<target-object> pointing to <replacement-object>. Both objects must already exist in the object database. They must also be the same type: on Git 2.47.3, replacing a commit with a blob fails with error: Objects must be of the same type. (-f only lets you overwrite an existing replacement for the same target).

2. Grafting parents (--graft)

The most common use is changing a commit’s parents. Git used to support this with a plain text file, .git/info/grafts, holding lines of hashes (<commit> <parent1> <parent2>...). That file was never transferred by fetch or push, and it silently changed what every command saw. It is deprecated and slated for removal.

git replace --graft is the modern replacement:

git replace --graft <commit> [<parent>...]

Git reads <commit>, duplicates its tree, author, committer, and commit message, constructs a new commit object with the newly specified parent list, writes the new commit to the database, and creates refs/replace/<commit>. If you invoke --graft without providing any parents, <commit> becomes a root commit with no parents.

If you have legacy .git/info/grafts files in older repositories, Git provides an automated migration flag:

git replace --convert-graft-file

This command parses .git/info/grafts, instantiates corresponding refs/replace/ entries for every graft line, and removes the deprecated flat file.

3. Interactive editing (--edit)

To tweak an object without manually generating and hashing raw replacement files:

git replace --edit <object>

Git exports the raw contents of <object> into a temporary file and launches the editor configured in $GIT_EDITOR or $EDITOR. For a commit object, you can edit the tree hash, author timestamps, or commit message. Once you save and close the editor, Git hashes the edited buffer into .git/objects and sets refs/replace/<object>.

4. Listing and formatting

To list all active replacement references:

git replace -l

By default, -l prints the target object names. To inspect what target objects point to what replacements, pass --format=long:

git replace -l --format=long

This prints each mapping as <target> (<type>) -> <replacement> (<type>), as the lab output below shows.

5. Deletion

Removing a replacement restores default behavior immediately:

git replace -d <target-object>

This deletes refs/replace/<target-object>. The replacement object remains in .git/objects until pruned by garbage collection, but Git stops referencing it immediately.

Bypassing replacements

Because replacements mask underlying objects, scripts and verification tools often need to inspect the authentic, unmasked repository state. Git provides two mechanisms to bypass all replacement references.

The CLI flag: --no-replace-objects

Passing --no-replace-objects before the sub-command forces Git to ignore refs/replace/*:

# Views the replaced history:
git log --oneline

# Views the raw, unmodified history:
git --no-replace-objects log --oneline

Plumbing commands respect this flag as well:

# Displays the replacement object:
git cat-file -p <target-sha>

# Displays the raw target object stored at <target-sha>:
git --no-replace-objects cat-file -p <target-sha>

The environment variable: GIT_NO_REPLACE_OBJECTS

When running automated audit scripts, continuous integration builds, or verification pipelines where passing a CLI flag to every nested Git command is impractical, export the environment variable:

export GIT_NO_REPLACE_OBJECTS=1
git log --oneline

Setting GIT_NO_REPLACE_OBJECTS=1 disables lookup across all operations in that shell session.

Hands-on Lab 1: Grafting split repositories

The following automated script constructs two separate repositories: old (an archive repository containing initial versions v0.1 through v1.0) and new (an active repository starting from a squashed v1.0 snapshot followed by v1.1 and v1.2). It fetches old into new, uses git replace --graft to stitch the active history to the archive history, verifies the graft with git log and git replace -l, inspects the refs, and cleans up.

#!/usr/bin/env bash
set -euo pipefail

LAB_DIR="/tmp/replace-lab"
rm -rf "$LAB_DIR"
mkdir -p "$LAB_DIR"
cd "$LAB_DIR"

# Isolate environment from user gitconfig
export GIT_CONFIG_GLOBAL=/dev/null
export GIT_CONFIG_SYSTEM=/dev/null

echo "== 1. Initializing old archive repository =="
git init -q old
cd old
git config user.name "Demo"
git config user.email "demo@example.com"
echo "Release 0.1 code" > project.txt && git add project.txt && git commit -q -m "v0.1: initial code"
echo "Release 0.2 code" > project.txt && git add project.txt && git commit -q -m "v0.2: bug fixes"
echo "Release 1.0 code" > project.txt && git add project.txt && git commit -q -m "v1.0: stable release"
OLD_TIP=$(git rev-parse HEAD)
cd ..

echo "== 2. Initializing new repository from squashed snapshot =="
git init -q new
cd new
git config user.name "Demo"
git config user.email "demo@example.com"
echo "Release 1.0 code" > project.txt && git add project.txt && git commit -q -m "Import v1.0 snapshot"
NEW_ROOT=$(git rev-parse HEAD)
echo "Release 1.1 code" > project.txt && git add project.txt && git commit -q -m "v1.1: new feature"
echo "Release 1.2 code" > project.txt && git add project.txt && git commit -q -m "v1.2: performance tuning"

echo "== 3. Fetching archive repository into active repository =="
git remote add archive ../old
git fetch -q archive

echo "== 4. Log before grafting (active repo only) =="
git log --oneline

echo "== 5. Grafting new root onto old tip =="
git replace --graft "$NEW_ROOT" "$OLD_TIP"

echo "== 6. Log after grafting (full combined history) =="
git log --oneline

echo "== 7. Log with --no-replace-objects =="
git --no-replace-objects log --oneline

echo "== 8. Inspecting replace refs =="
git replace -l --format=long
git for-each-ref refs/replace

echo "== 9. Deleting replace ref =="
git replace -d "$NEW_ROOT"

echo "== 10. Log after deletion =="
git log --oneline

The following command executes the script:

bash lab.sh

== 3. Fetching archive repository into active repository ==
== 4. Log before grafting (active repo only) ==

Hands-on Lab 2: Swapping raw blobs

Object replacement is not restricted to commits. You can replace any Git object type, including raw blobs. This is useful when a large binary or sensitive credential was committed to a branch and you want local tools to see sanitized or lightweight content without rewriting tree objects.

The following script commits an API token into a file named secret.txt, hashes a sanitized replacement string using git hash-object -w, applies git replace, and contrasts git show against git --no-replace-objects show.

#!/usr/bin/env bash
set -euo pipefail

LAB_DIR="/tmp/blob-replace-lab"
rm -rf "$LAB_DIR"
mkdir -p "$LAB_DIR"
cd "$LAB_DIR"

export GIT_CONFIG_GLOBAL=/dev/null
export GIT_CONFIG_SYSTEM=/dev/null

git init -q
git config user.name "Demo"
git config user.email "demo@example.com"

echo "== 1. Creating commit with sensitive token =="
echo "api_token=secret_production_key_998877" > secret.txt
git add secret.txt
git commit -q -m "Add API token configuration"

OLD_BLOB=$(git rev-parse HEAD:secret.txt)

echo "== 2. Writing sanitized replacement blob into object database =="
NEW_BLOB=$(echo "api_token=REDACTED_LOCAL_DUMMY_KEY" | git hash-object -w --stdin)

echo "== 3. Creating blob replacement =="
git replace "$OLD_BLOB" "$NEW_BLOB"

echo "== 4. Inspecting secret.txt with standard git show =="
git show HEAD:secret.txt

echo "== 5. Inspecting secret.txt with --no-replace-objects =="
git --no-replace-objects show HEAD:secret.txt

echo "== 6. Verifying replacement mapping =="
git replace -l --format=long

The following command executes the script:

bash blob.sh

The following output was produced by running bash blob.sh on Git 2.47.3:

== 2. Writing sanitized replacement blob into object database ==
== 3. Creating blob replacement ==
== 4. Inspecting secret.txt with standard git show ==

== 5. Inspecting secret.txt with --no-replace-objects ==

== 6. Verifying replacement mapping ==

When running git show HEAD:secret.txt, Git resolves HEAD to the commit, loads the commit’s root tree, finds the entry for secret.txt, retrieves its blob hash ($OLD_BLOB), checks refs/replace/, and reads $NEW_BLOB instead. With --no-replace-objects, Git bypasses the ref check and returns the original text.

Warning

Step 5 is the important lesson: the real token is still in the object database, in every clone and in every push of the branch. git replace only hides it from you. A leaked credential must be revoked and rotated, and removing it from history requires a rewrite, for example with git filter-repo --replace-text.

Practical production use cases

1. Archival repository stitching (The Linux history graft)

The best-known use of git replace is in the Linux kernel. The kernel’s Git history starts at 2.6.12-rc2 in April 2005. The earlier BitKeeper-era history (2002–2005) was later converted into a separate repository, tglx/history.git.

Rewriting the modern kernel repository to prepend the historical commits would have altered every single commit hash in the modern Linux kernel, invalidating references in commit messages, mailing lists, and bug trackers worldwide.

Instead, the historical tree is cloned alongside the modern tree:

git remote add history https://git.kernel.org/pub/scm/linux/kernel/git/tglx/history.git
git fetch history

The initial commit of the modern repository (1da177e4c3f4) is then grafted onto the tip of the archive repository:

git replace --graft 1da177e4c3f4b8077d3020086a0f4be56e7416ff <archive-tip-commit>

Developers who add this replacement ref can run git log and git blame back through the 2005 boundary into the BitKeeper era. Developers who never fetch the graft keep working with the normal modern history.

2. Large blob masking in developer environments

Suppose a model checkpoint or database dump was committed to a branch. A developer can replace that blob locally with a small placeholder, so git show, git diff and checkouts stop handling the huge file. This changes only what Git shows. The original blob is still in the repository and is still downloaded by clone and fetch. To avoid transferring it, use a partial clone (--filter=blob:limit=...) or rewrite history.

3. Local commit message hot-patching

When cherry-picking or bisecting upstream commits with malformed commit headers or misleading messages, developers can run:

git replace --edit <commit-hash>

This updates the message locally so tooling parses ticket identifiers or bug numbers cleanly without creating divergent upstream branches.

Sharing replacement refs across remotes

By default, Git’s transfer protocols deliberately exclude refs/replace/*. When you run git push origin main or git clone <url>, replacement references are neither sent nor received. This prevents one developer’s local overrides from silently masking objects across an entire engineering organization.

To share replacements, you must explicitly transfer the refs/replace namespace.

Pushing replacement refs

To push all local replacement references to a remote:

git push origin 'refs/replace/*'

To push a single replacement reference:

git push origin 'refs/replace/<target-hash>'

Fetching replacement refs

To retrieve replacement references from a remote:

git fetch origin 'refs/replace/*:refs/replace/*'

Automating fetch in repository configuration

If your team maintains an official archive graft or set of shared replacements, you can configure Git to fetch replacement references automatically alongside normal branches.

Edit .git/config (or configure via git config --add) under the remote specification:

[remote "origin"]
    url = git@github.com:example/project.git
    fetch = +refs/heads/*:refs/remotes/origin/*
    fetch = +refs/replace/*:refs/replace/*

With this refspec in place, every routine git fetch or git pull synchronizes replacements into your local repository.

Making replacements permanent

git replace is intended as a non-destructive overlay. However, teams often use git replace to prototype a complex history reconstruction—such as splicing repositories or amputating corrupted directories—and then want to bake those changes permanently into the repository DAG.

To make replacements permanent, every child commit in the repository must be rewritten to reference the replacement objects natively.

The modern approach: git-filter-repo

The Git project’s own filter-branch documentation points to the separately installed git-filter-repo. Its manual lists “making grafts or replacement refs permanent” as a supported job, and it notes that grafts and replace refs, if present, are used in the rewrite and made permanent. --proceed is needed only because nothing else was passed on the command line:

git replace --graft <commit> <new-parent>
git filter-repo --proceed
Note

Not run here. git-filter-repo is a separate install and wasn’t available on the machine used for the labs. This step comes from the filter-repo manual.

filter-repo rewrites history through the replacement overlay, so the new commits contain the grafted parents or replaced blobs as real objects. Afterwards, run git replace -l to check which replace refs are left. By default filter-repo writes its own replace refs mapping old commit IDs to new ones, so don’t confuse those with your original grafts.

The deprecated approach: git filter-branch

Git includes a built-in rewriting tool, git filter-branch.

Warning

git filter-branch is deprecated by the Git project. It is notoriously slow on large repositories, has subtle edge cases where commit metadata and signatures are corrupted, and does not scale. Use git-filter-repo instead.

If you must use git filter-branch on environments where third-party tools cannot be installed, it converts grafts into real commits because it runs porcelain commands that honor replacement references:

git filter-branch -- --all

After the filter completes, remove the replacement refs to verify that the rewritten commits persist:

git for-each-ref --format="%(refname)" refs/replace/ | xargs -n 1 git update-ref -d

Pitfalls and operational trade-offs

While git replace is a surgical tool, deploying it in production workflows introduces specific failure modes.

1. Invisibility during clones and CI failures

Because git clone only downloads branches and tags by default, continuous integration runners, Docker build containers, and new team member clones do not receive replacement refs. If a build relies on a commit graft to find a submodule commit or an older tag, the build will pass on the author’s workstation (which has the graft) and fail on the CI server. Always configure explicit fetch refspecs in automated build pipelines if your workflow depends on replacement refs.

2. Confusion during git bisect

git bisect traverses the DAG using replacement references. If you graft an active repository onto an archival repository where build flags or directory layouts differed, git bisect may navigate into the archival history and test commits that cannot compile in the modern build environment. When bisecting regressions that are strictly confined to modern history, either bypass replacements using GIT_NO_REPLACE_OBJECTS=1 git bisect start or specify a known root boundary:

git bisect start HEAD <modern-root-commit>

3. Deleting a replacement can lose its object

The replacement object is usually reachable only through refs/replace/<hash>. After git replace -d, nothing references it, and a later git gc --prune=now deletes it. That includes a hand-edited commit from git replace --edit or a redacted blob you built. If you might want it back, keep a branch or tag pointing at it before deleting the ref.

When you diagnose a confusing repository, compare git log and git cat-file -p with and without --no-replace-objects. If they disagree, an overlay is in play. Run git replace -l --format=long to see exactly which objects are swapped.

4. Performance scaling with massive ref counts

Every time Git accesses an object by hash, it checks whether that object has a corresponding ref in refs/replace/.

  • Git loads all replace refs into an in-memory map the first time it needs one, so each Git command pays a cost that grows with the number of refs. A handful of grafts is free. Tens of thousands of replace refs make every command slower and every fetch of refs/replace/* larger.

Summary

git replace provides an overlay mechanism for the Git object database:

  • Non-destructive: Swaps objects as Git reads them, without changing the original commit hashes, trees or signatures. A replacement commit is a new, unsigned object.
  • Reference layout: Managed under refs/replace/<original-object-sha>, pointing to the replacement object hash.
  • Modern grafting: git replace --graft <commit> [<parents>...] completely supersedes the deprecated .git/info/grafts file.
  • Bypassable: Run git --no-replace-objects <command> or set GIT_NO_REPLACE_OBJECTS=1 to inspect underlying reality.
  • Isolated by default: git push and git fetch ignore refs/replace/* unless explicit refspecs are defined (refs/replace/*:refs/replace/*).
  • Solidification: Prototype history changes with git replace, then bake them permanently into history using git-filter-repo.
