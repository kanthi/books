Automate Bisect with Tests

After completing this chapter, you will be able to write non-interactive regression test scripts, pass them to git bisect run, handle untestable commits with exit code 125, and use custom bisect terms to hunt performance degradation or other non-bug state changes automatically.

Manual bisection requires checking out each candidate commit, running tests by hand, and marking commits good or bad. This manual step becomes tedious and error-prone over dozens of commits. git bisect run automates the entire search loop by executing a designated script at every step and inspecting its exit code to decide whether to search earlier or later in history.

Thesis

If you can write a script that answers “is this commit old-behaviour or new-behaviour?” with an exit code, Git can find the first new commit in about \(\log_2 N\) runs while you do something else. The answer is only as good as the script, though. Untestable commits must say so (exit 125), and a check that flips randomly sends the search down the wrong half without any warning. This page works through a performance regression, a function that quietly went quadratic, in a 30-commit history with one broken commit in the middle. Tested with git 2.47.3.

The exit-code contract

When git bisect run <cmd> [args] executes your command, it evaluates the returned exit code to determine the candidate commit’s status:

Exit code Bisection decision Meaning
0 Good / Old The commit satisfies the check (e.g. tests pass or code is fast).
1–127 (except 125) Bad / New The commit fails the check (e.g. test broken or code is slow).
125 Skip The commit cannot be tested (e.g. syntax error or build failure).
128–255 (or killed by a signal) Abort Bisect stops and marks nothing.
Note

Not run here. The abort case isn’t exercised in this lab. A script killed by SIGKILL (seen as 137) or one that ends with exit 255 stops the whole bisect instead of marking the commit bad. Decide which failures mean what: “can’t build or can’t run here” should be an explicit exit 125, and only the behaviour you’re hunting should give 1.

Writing a check script

The check script gives exactly one verdict per commit. This one has three exits:

  • If any .py file fails py_compile, the commit can’t be tested, so it exits 125. If the timing snippet itself crashes (for example, dedupe won’t import), it also exits 125.
  • Otherwise it times dedupe() on 40,000 items (20,000 distinct values, each twice) three times and keeps the best.
  • It prints the timing, then exits 0 (fast) if the best time is under LIMIT, or 1 (slow) if not.
#!/usr/bin/env bash
# perf-check.sh: exit 0 if dedupe() is fast, 1 if slow, 125 if this commit
# can't be tested. Used with: git bisect run ../perf-check.sh
LIMIT=${LIMIT:-0.5}   # seconds; pick a limit far from both timings
python3 -m py_compile ./*.py 2>/dev/null || exit 125
best=$(python3 - <<'PY'
import time
import dedupe

data = list(range(20_000)) * 2
times = []
for _ in range(3):                 # best of 3 damps scheduler noise
    t0 = time.perf_counter()
    dedupe.dedupe(data)
    times.append(time.perf_counter() - t0)
print(f"{min(times):.3f}")
PY
) || exit 125
echo "dedupe: ${best}s (limit ${LIMIT}s)"
python3 -c "import sys; sys.exit(0 if $best < $LIMIT else 1)"

The script lives outside the repository and is run as ../perf-check.sh. Bisect checks out a different commit at every step. A script tracked in the repo would change, or disappear, along with the commit. If your check is already in the repo, copy it out before you start.

Building the demo history

make-history.sh builds a 30-commit repository, perf-demo. It fixes the author, committer and dates, so the commit hashes below should come out the same when you run it.

  • Commit 15 adds extra.py with a syntax error. That makes it an untestable commit.
  • Commit 16 removes extra.py.
  • Commit 17 changes dedupe() from set membership to list membership. Each x not in out is then \(O(n)\), so the whole function is \(O(n^2)\).
#!/usr/bin/env bash
# make-history.sh: build a demo repo with 30 commits. Commit 17 makes
# dedupe() quadratic; commit 15 has a syntax error (an untestable commit).
set -euo pipefail
rm -rf perf-demo && git init -q -b main perf-demo && cd perf-demo
export GIT_AUTHOR_NAME=Dev GIT_AUTHOR_EMAIL=dev@example.com
export GIT_COMMITTER_NAME=Dev GIT_COMMITTER_EMAIL=dev@example.com

write_fast() {
  cat > dedupe.py <<'PY'
def dedupe(items):
    seen = set()
    out = []
    for x in items:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out
PY
}
write_slow() {
  cat > dedupe.py <<'PY'
def dedupe(items):
    out = []
    for x in items:
        if x not in out:          # list membership: O(n) per item
            out.append(x)
    return out
PY
}

write_fast
for i in $(seq 1 30); do
  export GIT_AUTHOR_DATE="2026-10-01T12:$(printf %02d "$i"):00+05:30" GIT_COMMITTER_DATE="2026-10-01T12:$(printf %02d "$i"):00+05:30"
  if [ "$i" -eq 17 ]; then write_slow; fi
  if [ "$i" -eq 15 ]; then echo "def broken(:" > extra.py; fi
  if [ "$i" -eq 16 ]; then rm -f extra.py; fi
  echo "change $i" >> CHANGELOG
  git add -A
  git commit -q -m "change $i"
done
git log --oneline | wc -l

Build it:

./make-history.sh

It prints the number of commits:

30

Running the automated bisection

good and bad work, but for “when did this get slow” it’s clearer to name the two states yourself. Git also accepts old and new as built-in synonyms. Custom terms:

git bisect start --term-old=fast --term-new=slow

After that the subcommands are git bisect slow <rev> and git bisect fast <rev>. git bisect terms prints the current terms:

git bisect terms

bisect.sh starts with those terms, marks the newest commit slow and the first commit fast, and hands over to git bisect run. When the run finishes, it saves the log and runs git bisect reset, which returns you to main.

#!/usr/bin/env bash
# bisect.sh: find the commit that made dedupe() slow.
set -euo pipefail
cd perf-demo
git bisect start --term-old=fast --term-new=slow
git bisect slow main          # today: slow
git bisect fast main~29       # first commit: fast
git bisect run ../perf-check.sh
git bisect log > ../bisect.log
git bisect reset

Run it:

./bisect.sh

Reading the run

Why commit 15 was skipped

Bisect’s first pick was the midpoint, change 15. There py_compile failed on extra.py, and the script exited 125 before it got to the timing. That’s why no dedupe: line follows the first running line. Git recorded the commit as skipped (git bisect skip in the log) and chose a nearby commit, change 16, instead. Had the script returned 1 there, Git would have treated change 15 as slow. The search would then have ended on change 15, with the wrong answer and no warning.

Step count efficiency

With 30 commits, binary search needs about \(\log_2 30 \approx 5\) verdicts. The script ran five times: once on change 15 (skipped), then on 16 (fast) and on 23, 19 and 17 (all slow). Once 16 was fast and 17 slow, nothing was left to test, and Git printed the commit along with its diffstat (dedupe.py | 4 +---). Doing it by hand would have meant up to 30 checkouts and timings.

Making performance checks trustworthy

A timing check is the easiest kind to get wrong. One misjudged commit sends the search into the wrong half, and bisect still reports a “first slow commit” with full confidence. Some habits that help:

  1. Put the limit far from both timings. Here, fast runs took about 0.001 s and slow ones about 1.4 s. A 0.5 s limit is hundreds of times the fast time and still well under the slow one. Measure both ends before you pick the limit. If they’re only 20% apart, make the workload bigger until they aren’t.
  2. Repeat and take the best. Noise only ever makes a run slower, so the minimum of several runs (best of 3 here) is steadier than one run or the mean.
  3. Keep the machine quiet. Don’t run a build or a browser-heavy session alongside it. Serious benchmarking also pins CPU frequency and cores; this lab didn’t.
  4. Watch what survives checkouts. Untracked files stay put when bisect switches commits. Here py_compile leaves a __pycache__ directory, which is harmless because Python checks each .pyc against its source. A stale build directory is not harmless: it can make one commit look like another. Use a fresh build directory per step, or clean in the script.

Other regressions to hunt with terms

The same pattern covers other things that change at some commit. The only rule is that exit 0 means the old term:

Target problem Custom terms Command / Check logic
Binary size --term-old=small --term-new=big Build, then [ "$(stat -c %s bin/app)" -lt 5000000 ] (GNU stat). Exit 125 if the build fails.
Peak memory --term-old=lean --term-new=heavy Peak RSS from /usr/bin/time -v (GNU time, not the shell’s time built-in), compared with a limit
When a test started passing --term-old=broken --term-new=fixed Exit 0 must mean old, which here is still broken, so invert the test: exit 0 when it fails and 1 when it passes
Merge-heavy history any git bisect start --first-parent (Git 2.29+) follows only first parents, so the answer is a merge into main, not a commit inside a topic branch

Common mistakes

  • Placing the check script inside the working tree: If perf-check.sh is tracked inside the repository, each checkout can replace the script, or delete it. Keep it outside the repository, or copy it out first.
  • Flaky threshold boundaries: Setting performance thresholds too close to normal runtime jitter produces wrong verdicts, and the search can’t tell.
  • Returning code 1 for compilation or environment failures: If a commit fails to build, returning code 1 tells Git that the commit contains the target regression. Map compilation errors to exit code 125 so Git skips the commit.
  • Forgetting git bisect reset: Once the run ends, you’re still on a detached HEAD at whichever commit was tested last. git bisect reset takes you back to the branch you started on.
  • Dirty working trees: Uncommitted edits either block the checkouts or ride along into every commit you test. Commit or stash them before you start. Untracked build output is the other half. git clean -fdx removes it, but it also deletes every untracked and ignored file, so put it only in scripts that run in a scratch clone.

Exercises

  1. The demo history is linear, so --first-parent would change nothing. Change make-history.sh so commits 10–20 are made on a topic branch and merged into main with git merge --no-ff. Bisect with and without --first-parent and compare the commits each run reports.

  2. Run git bisect replay ../bisect.log in perf-demo. It replays the recorded verdicts without running any timings and ends on the same first slow commit. Then edit one line of a copy of the log, say marking change 16 slow, replay that, and see where you end up. Run git bisect reset afterwards.

  3. In a Python project with tests, run:

    git bisect run pytest -x tests/test_parser.py

    pytest exits 1 for failed tests, but 2–5 for interruptions, internal errors, usage errors and “no tests collected”. Bisect counts all of those as bad. Write a wrapper that passes 0 and 1 through and turns everything else into 125.

Summary

git bisect run automates binary searching across commit histories using command exit codes. Using custom terms like --term-old and --term-new clarifies non-bug regression searches, while exit code 125 allows Git to bypass unbuildable or untestable commits cleanly. Keep the script outside the repository. Give timing checks a wide margin and repeat them. Then the commit bisect names is one you can trust.
