Pickaxe and –follow

After this page you can use Git’s pickaxe options (-S and -G) to locate commits that introduced, modified, or deleted specific string literals or regular expressions across your entire repository, and pair -S with --follow to track a symbol’s history across file renames.

Thesis

Standard commit history searches rely on path filtering (git log -- path) or commit message searches (git log --grep). However, when hunting for when a specific function, constant, or variable was introduced or removed, path-based filtering fails if the file was renamed or if you do not know which file contained the symbol.

Git’s pickaxe tools (-S and -G) inspect the actual patch diffs created by each commit. When combined with --follow, Git traces line-level changes and path renames backward through time, giving you an exact lineage of code additions and deletions.

Verified below with git 2.47.3.

Pickaxe options: -S vs -G

Git provides two pickaxe flags with distinct matching mechanisms:

Flag Name Match criteria Common use case
-S <string> Exact pickaxe Commits that change the total count of occurrences of <string> in the file. Finding when a symbol was added, deleted, or renamed/replaced.
-G <regex> Regex pickaxe Commits whose diff patch text contains a line added or removed that matches <regex>. Finding any commit whose diff touches lines matching a pattern.

The core difference

The difference between -S and -G lies in how they evaluate commits where a symbol is moved or modified without changing its total count.

  • -S <string> counts occurrences of <string> before and after the commit. If the count changes (for example, going from 0 to 1 upon creation, or 1 to 0 upon deletion), the commit is shown. If a commit merely moves hello from line 10 to line 20 without altering the total number of hello occurrences, -S hello skips that commit.
  • -G <regex> examines the patch diff itself. If any added or removed line in the commit diff matches the regular expression, -G includes the commit—even if the overall count of matching strings remains unchanged.
               -S "hello" vs -G "hello"

  Commit action                -S hello    -G hello
  ───────────────────────────  ──────────  ──────────
  Add 'hello' to empty file      Matches     Matches
  Remove 'hello' from file       Matches     Matches
  Modify line containing 'hello'  Ignored*    Matches
  Move line containing 'hello'    Ignored     Matches

  * -S ignores modifications if the number of 'hello' occurrences
    is identical in preimage and postimage.

History across renames: –follow

By default, git log -- <path> stops traversing history when it reaches the commit where <path> was created or renamed into existence. It does not automatically follow the file’s previous name.

The --follow option instructs git log to follow file renames backwards in time.

[!NOTE] --follow only works when tracking a single file path. It cannot be combined with multiple file paths or directory trees.

When you pair -S with --follow, Git searches for changes in occurrence count for your target string while simultaneously navigating backwards through path renames.

Lab: Pickaxe and –follow in action

The following script constructs a repository history with additions, string modifications, line removals, and a file rename (app.py to greeter.py).

#!/usr/bin/env bash
# Recreate the verified pickaxe / --follow demo (git 2.47.3).
set -euo pipefail
rm -rf /tmp/pickaxe-demo && mkdir /tmp/pickaxe-demo && cd /tmp/pickaxe-demo
git init -b main
git config user.name t
git config user.email t@t

cat > app.py <<'EOF'
def greet(name):
    return "hello " + name
EOF
git add app.py && git commit -m 'add greet'

cat > app.py <<'EOF'
def greet(name):
    return "hello " + name

def farewell(name):
    return "bye " + name
EOF
git commit -am 'add farewell'

git mv app.py greeter.py
git commit -m 'rename app.py to greeter.py'

cat > greeter.py <<'EOF'
def greet(name):
    return "hi " + name

def farewell(name):
    return "bye " + name
EOF
git commit -am 'change hello to hi'

cat > greeter.py <<'EOF'
def greet(name):
    return "hi " + name

def farewell(name):
    return "goodbye " + name
EOF
git commit -am 'bye to goodbye'

echo "=== PICKAXE LAB ==="
echo "--- log --oneline ---"
git log --oneline
echo "--- log -S hello --oneline ---"
git log -S hello --oneline
echo "--- log -S bye --oneline ---"
git log -S bye --oneline
echo "--- log -G \"return .*bye\" --oneline ---"
git log -G 'return .*bye' --oneline
echo "--- log --follow -- greeter.py ---"
git log --follow --oneline -- greeter.py
echo "--- log --oneline -- greeter.py (NO follow) ---"
git log --oneline -- greeter.py
echo "--- log -S hello --follow -- greeter.py ---"
git log -S hello --follow --oneline -- greeter.py

Running bash pickaxe-lab.sh on git 2.47.3 produced this output (hashes will differ on your machine; look for the same commit messages and the same shape):

--- log --oneline ---
e6f5d75 bye to goodbye
79d807e change hello to hi
2958fb8 rename app.py to greeter.py
ffac9b3 add farewell
0aa83cc add greet
--- log -S hello --oneline ---
79d807e change hello to hi
0aa83cc add greet
--- log -S bye --oneline ---
ffac9b3 add farewell
--- log -G "return .*bye" --oneline ---
e6f5d75 bye to goodbye
ffac9b3 add farewell
--- log --follow -- greeter.py ---
e6f5d75 bye to goodbye
79d807e change hello to hi
2958fb8 rename app.py to greeter.py
ffac9b3 add farewell
0aa83cc add greet
--- log --oneline -- greeter.py (NO follow) ---
e6f5d75 bye to goodbye
79d807e change hello to hi
2958fb8 rename app.py to greeter.py
--- log -S hello --follow -- greeter.py ---
79d807e change hello to hi
0aa83cc add greet

Analyzing the results

Understanding how Git evaluates each query across the commit graph explains why specific commits appear in each command output.

1. Exact count change (-S hello)

The query git log -S hello --oneline returns two commits: - 0aa83cc (“add greet”): Introduced hello (count changed from 0 to 1). - 79d807e (“change hello to hi”): Removed hello (count changed from 1 to 0).

The intermediate commits (ffac9b3, 2958fb8, and e6f5d75) did not change the occurrence count of hello and are omitted.

2. Regex diff matching (-G "return .*bye")

The query git log -G 'return .*bye' --oneline returns two commits: - ffac9b3 (“add farewell”): the added line containing return "bye " + name matches the regex. - e6f5d75 (“bye to goodbye”): the removed line still matches return .*bye, so the commit appears even though the replacement text is goodbye.

-S bye did not list e6f5d75. The string bye still occurs once inside goodbye, so the occurrence count did not change. That is the classic pickaxe distinction: -S cares about counts; -G cares about whether the patch text matches.

3. File history without vs. with --follow

Compare path-constrained history queries on greeter.py:

  • git log --oneline -- greeter.py: Traces history backwards and stops at commit 2958fb8 (“rename app.py to greeter.py”), where greeter.py came into existence. Commits ffac9b3 and 0aa83cc are invisible because they operated on app.py.
  • git log --oneline --follow -- greeter.py: Detects the rename at 2958fb8 and continues tracing commits for app.py, revealing the full history back to 0aa83cc.

4. Combining -S with --follow

Running git log -S hello --oneline --follow -- greeter.py combines both capabilities: 1. It tracks greeter.py back through its rename to app.py. 2. It filters the combined history for commits that altered the occurrence count of hello.

This yields 79d807e (modification under name greeter.py) and 0aa83cc (creation under name app.py).

When to reach for which flag

Reach for -S when you care about a concrete token whose presence count changed: a function name that appeared, a constant that vanished, a feature flag string that was deleted. Reach for -G when you care about the shape of the diff: a regex over added or removed lines, including commits that rewrote a line without changing the total occurrence count of a substring.

A practical sequence on an unfamiliar codebase:

# 1. Did this symbol ever exist?
git log -S 'parseConfig' --oneline

# 2. Show the patches so you can see add vs delete
git log -S 'parseConfig' -p

# 3. The file was renamed — keep walking
git log -S 'parseConfig' --follow -p -- current/name.py

If -S returns nothing but you are sure the text lived in history, try -G with a looser regex, or drop --follow and search the whole tree (renames can hide a path-limited -S when you forgot --follow).

Pickaxe and binary files

-S and -G operate on textual diffs. Binary files (images, compiled blobs marked binary via attributes) do not contribute useful patch text; a commit that only changes a binary will usually not match a string pickaxe. Textualized formats (JSON, SVG, source) work normally.

Performance notes

Pickaxe walks every commit in the range and inspects each patch. On large histories that is slower than a message --grep. Narrow the walk first:

git log -S 'TOKEN' --oneline v2.0.0..HEAD -- src/

Path limits and a tag range cut the work dramatically. There is no separate index for pickaxe queries — it is always a history walk.

Common search patterns

# Find when a function signature was introduced or removed
git log -S "def process_payment" -p

# Search for commits altering a configuration key using regex
git log -G "MAX_CONNECTIONS\s*=" -p

# Track a symbol inside a single file across renames with full diffs
git log -S "TOKEN_EXPIRY" --follow -p -- path/to/config.py

# Find when a specific regex pattern was added/removed across all commits
git log -G "^import " --oneline

Pitfalls

  1. Assuming -S matches any commit touching a line. If a commit replaces hello_world with hello_world, or modifies surrounding whitespace without changing the string occurrence count, -S hello_world ignores the commit. Use -G if you want all commits whose diff contains the string.
  2. Using --follow with multiple files or directories. Git’s rename tracking engine for history logs (--follow) is strictly limited to a single file path. Passing multiple paths or directory names causes Git to ignore --follow or raise an error.
  3. Expecting --follow to work without rename detection. Git detects renames dynamically based on content similarity (diff.renames). If a file is renamed and completely rewritten in the same commit, similarity may drop below the threshold, breaking the --follow chain.
  4. Confusing pickaxe history with git blame. Pickaxe searches the git log commit graph for line addition/deletion events. To inspect who last modified each line of a current file version across renames, use git blame -C.

Summary

  • Use git log -S <string> to find commits that introduced or deleted a specific code symbol or literal text string.
  • Use git log -G <regex> to find commits whose patch diff text contains added or removed lines matching a regular expression.
  • Use --follow with git log -- <path> to trace a single file’s history across file renames.
  • Combine -S and --follow to track when a specific symbol was modified or introduced, even if the containing file was renamed.
