gitignore Patterns

After reading this page, you will be able to trace ignore rule evaluation across global, repository, and directory-level sources, debug complex rule collisions using git check-ignore -v, apply pattern anchors and globstar syntax accurately, bypass parent directory negation traps, and untrack files already stored in the Git index so ignore patterns take effect.

Thesis

Git’s ignore mechanism is a prioritized pattern-matching cascade designed to keep build artifacts, secret keys, and temporary files out of repository history. While day-to-day use involves appending basic filenames to a root .gitignore, production engineering requires understanding rule precedence across global, local, and nested scopes.

When Git determines whether to ignore a path, it evaluates rules in a strict hierarchy where the pattern source, directory location, file tracking state, and rule order dictate the outcome. Understanding these mechanics prevents inadvertent credential commits, avoids bloated commits containing intermediate build outputs, and eliminates confusion when tracked files appear immune to ignore rules.

Verified below with git 2.47.3.

Sources of Ignore Rules

Git aggregates ignore patterns from three distinct sources. Patterns defined in higher-priority sources override matching patterns from lower-priority sources.

 Highest Priority   ┌─────────────────────────────────────────────────────────┐
                    │ 1. Direct command-line patterns (e.g. git check-ignore) │
                    ├─────────────────────────────────────────────────────────┤
                    │ 2. .gitignore in current or target directory            │
                    ├─────────────────────────────────────────────────────────┤
                    │ 3. .gitignore in parent directories (up to worktree)    │
                    ├─────────────────────────────────────────────────────────┤
                    │ 4. Repository-local rules: $GIT_DIR/info/exclude        │
                    ├─────────────────────────────────────────────────────────┤
 Lowest Priority    │ 5. Global rules: core.excludesFile                      │
                    └─────────────────────────────────────────────────────────┘
Source Scope Shared with Team? Primary Use Case
Directory .gitignore Directory and subdirectories Yes (Committed to Git) Project-specific rules, build outputs, local dependencies (node_modules/, target/).
$GIT_DIR/info/exclude Single local clone No (Stays in .git/) Local developer tools, personal scratch pads, local virtual environments.
core.excludesFile All repositories for user No (Global configuration) OS metadata (.DS_Store, Thumbs.db), personal editor files (.vscode/, .idea/).

1. Directory-Level .gitignore Files

Patterns defined in .gitignore files apply to the directory where the file resides and all of its subdirectories. You can place .gitignore files in subdirectories to scope rules locally. A .gitignore file located deeper in the directory tree takes precedence over .gitignore files located in higher parent directories for paths within that subtree.

2. Local Repository Excludes: $GIT_DIR/info/exclude

The $GIT_DIR/info/exclude file (typically .git/info/exclude) applies strictly to your local clone. Patterns defined here behave identically to patterns in a root .gitignore, but they are never committed or pushed to remote repositories. Use this for personal workflow artifacts that shouldn’t pollute team configuration files.

3. Global User Excludes: core.excludesFile

The core.excludesFile configuration option defines a global ignore file for all Git repositories on your system. If not explicitly set in your ~/.gitconfig, Git defaults to checking $XDG_CONFIG_HOME/git/ignore or ~/.config/git/ignore. If ~/.gitignore exists, many operating system packages configure core.excludesFile to point there.

# View current global excludes file path
git config --global core.excludesFile

# Set an explicit global excludes file path
git config --global core.excludesFile ~/.config/git/ignore

Pattern Precedence and Resolution Rules

When Git checks whether a path should be ignored, it scans available ignore sources in priority order. Within a single ignore source (such as a single .gitignore file), patterns are evaluated from top to bottom:

  1. Last matching pattern wins: If multiple patterns within the same file match a path, the last matching pattern determines the outcome. A subsequent rule overrides an earlier one.
  2. Closer directory wins: A pattern in a .gitignore file in a deeper subdirectory overrides matching patterns in parent directory .gitignore files.
  3. Repository root equivalent: Rules in $GIT_DIR/info/exclude and core.excludesFile are evaluated as if they were located at the root of the working tree, but at a lower priority than any committed .gitignore file.

Debugging Pattern Matching with git check-ignore

When a file is unexpectedly ignored (or fails to be ignored), do not guess which pattern matched. Use git check-ignore with the -v (verbose) flag to inspect the exact file, line number, and pattern driving the decision.

# Inspect why a specific file is ignored
git check-ignore -v path/to/file.log

# Check non-ignored files (returns exit status 1 if not ignored)
git check-ignore -v path/to/tracked-file.txt || echo "Not ignored"

# Inspect multiple paths at once
git check-ignore -v build/output.o src/main.c

The output format of git check-ignore -v is structured as follows:

<source-file>:<line-number>:<matching-pattern>    <pathname>

For example, .gitignore:12:*.log app.log indicates that line 12 of .gitignore matched app.log with pattern *.log.

Pattern Syntax Reference

Git ignore patterns use shell globbing conventions extended with specific directory-anchoring and recursive matching rules.

  /build/      Anchored to directory containing .gitignore (matches root build/ only)
   build/      Unanchored directory match (matches build/, src/build/, etc.)
  *.log        Matches any file ending in .log in directory or subdirectories
  !important.log  Negation: re-includes important.log if previously ignored
  doc/**/*.pdf Matches doc/a.pdf, doc/sub/b.pdf (globstar recursive match)
Pattern Description Example Matches Non-Matches
name Matches file or directory with name anywhere in subtree name, dir/name, name/file rename, names
/name Anchored: matches name only in the directory of .gitignore /name, /name/file dir/name
name/ Trailing slash: matches directories only name/ (directory) name (regular file)
*.ext Wildcard extension match file.ext, dir/file.ext file.ext.bak
temp? Question mark: matches exactly one non-slash character temp1, tempa temp, temp12
[a-z].txt Character class match a.txt, z.txt 1.txt, ab.txt
logs/**/arch Globstar: matches zero or more directory levels logs/arch, logs/2026/arch other/logs/arch
!file Negation prefix: re-includes a previously excluded path file (if previously ignored) N/A

Leading Slash Anchoring

A leading slash anchors the pattern relative to the location of the .gitignore file containing that rule:

  • In the root .gitignore, /build/ matches /build/ at the workspace root, but does not match src/build/.
  • Without the leading slash, build/ matches build/ at any directory depth (e.g., build/, src/build/, a/b/c/build/).
  • In a subdirectory .gitignore (such as src/.gitignore), /cache/ matches src/cache/, but not src/sub/cache/.

Trailing Slash Filtering

A trailing slash forces Git to test the pattern against directories only. If target/ is specified, Git will ignore a directory named target and all files inside it, but will not ignore a regular file named target.

Double Asterisk Globstar (**)

The double asterisk ** matches zero or more directory segments:

  • **/logs: Matches any directory or file named logs anywhere in the repository (logs, foo/logs, foo/bar/logs).
  • logs/**: Matches everything inside logs/ recursively.
  • a/**/b: Matches a/b, a/x/b, a/x/y/b.

Negation (!) and the Parent Directory Trap

An exclamation mark ! negates a previous pattern, allowing you to ignore all files in a directory except a select few.

# Ignore all log files
*.log

# Except important.log
!important.log
Note

Critical Rule: Git cannot re-include a file if its parent directory is excluded by an earlier pattern. Git does not traverse into ignored directories for performance reasons.

If you ignore an entire directory with logs/, attempting to un-ignore a file inside it with !logs/important.log will fail:

# BROKEN: Git will NOT re-include important.log
logs/
!logs/important.log

To re-include a specific file inside an ignored directory structure, you must ignore the directory’s contents using wildcards rather than the directory itself, or un-ignore the parent directory paths explicitly:

# WORKING: Ignore directory contents, not the directory itself
logs/*
!logs/important.log

Tracked Files Are Never Ignored

A fundamental source of confusion for engineers is expecting .gitignore to hide changes to files already tracked in the index.

Git ignore rules apply exclusively to untracked files.

If a file was staged or committed before a matching ignore rule was added to .gitignore, Git continues tracking modifications to that file. Adding config.json to .gitignore after config.json is in the Git index has zero effect on git status or git diff.

               File Creation & Tracking Lifecycle

 ┌──────────────┐   git add    ┌──────────────┐  .gitignore rule added
 │  Untracked   │ ───────────► │   Tracked    │ ──────────────────────┐
 │   File       │              │  (in index)  │                       │
 └──────────────┘              └──────────────┘                       │
        │                             │                               │
        │ .gitignore                  │ .gitignore                    ▼
        │ rule added                  │ rule added          ┌───────────────────┐
        ▼                             ▼                     │ STILL TRACKED!    │
 ┌──────────────┐              ┌──────────────┐             │ Git ignores .qmd  │
 │   Ignored    │              │  Modifications│            │ rule for indexed  │
 │ (git status  │              │  still show  │             │ files.            │
 │  hides it)   │              │  in status!  │             └───────────────────┘
 └──────────────┘              └──────────────┘

Untracking Files with git rm --cached

To apply ignore rules to a file that is currently tracked, you must remove the file from the index while keeping your working directory copy intact using git rm --cached:

# Untrack a single file (keeps local file in worktree)
git rm --cached debug.log

# Commit the removal from index
git commit -m "Stop tracking debug.log"

# Untrack an entire directory recursively
git rm -r --cached build/

After running git rm --cached, the path transitions from tracked to untracked. Because it matches an active rule in .gitignore, it immediately becomes ignored and disappears from git status.

Commands Reference

Command Purpose
git check-ignore -v <path> Verbose check: shows source file, line number, and rule matching <path>.
git check-ignore -v --non-matching <path> Check paths and report paths that do not match any ignore rule.
git status --ignored Display untracked files with ignored files explicitly listed.
git status -s --ignored Short format status showing ignored files with !! status code.
git rm --cached <path> Remove <path> from index (untrack) while preserving local file.
git add -f <path> Force-stage an ignored file into the index despite .gitignore.

Lab: Comprehensive Ignore Precedence and Untracking

The following shell script builds a reproducible test environment demonstrating global excludes, local repository excludes, nested directory .gitignore rules, negation, and untracking indexed files.

#!/usr/bin/env bash
# Recreate the verified gitignore precedence and untracking demo (git 2.47.x).
set -euo pipefail

LAB_DIR="/tmp/gitignore-lab"
HOME_DIR="/tmp/gitignore-lab-home"

rm -rf "$LAB_DIR" "$HOME_DIR"
mkdir -p "$LAB_DIR" "$HOME_DIR"

# Set up global excludes file
GLOBAL_EXCLUDES="$HOME_DIR/excludes"
printf "*.bak\n*~\n" > "$GLOBAL_EXCLUDES"

export HOME="$HOME_DIR"
cd "$LAB_DIR"

git init -b main
git config user.name "Lab Tester"
git config user.email "tester@example.com"
git config core.excludesFile "$GLOBAL_EXCLUDES"

# 1. Root .gitignore setup
cat <<'EOF' > .gitignore
*.log
!important.log
debug.log

/build/
tmp/
src/cache
obj/
EOF

# 2. Local repo exclude setup ($GIT_DIR/info/exclude)
printf "local-only.dat\n" >> .git/info/exclude

# 3. Create test files across structures
touch keep.txt important.log a.log foo.bak bar~ local-only.dat
mkdir -p build nested/build src/cache tmp obj
touch build/x nested/build/n.o src/cache/x.bin tmp/t.txt obj/o.o was-tracked.log

# 4. Stage tracked files prior to status checks
git add .gitignore keep.txt important.log nested/build/n.o was-tracked.log

echo "=== GITIGNORE LAB ==="
echo "--- status (important.log staged; nested/build tracked; root build ignored) ---"
git status -s

echo "--- check-ignore -v (shows which rule wins) ---"
git check-ignore -v a.log foo.bak bar~ local-only.dat build/x src/cache/x.bin tmp/t.txt obj/o.o was-tracked.log || true

echo "--- important.log not ignored (negation) ---"
git check-ignore -v important.log || echo "exit=$?"

echo "--- was-tracked.log still tracked despite *.log ---"
git check-ignore -v was-tracked.log || echo "check-ignore-exit=$?"

echo "=== TRACKED VS IGNORE ==="
touch debug.log
git add debug.log
git commit -m "initial commit with debug.log tracked" > /dev/null

echo "debug content" >> debug.log
echo "--- status after editing tracked debug.log (ignore does NOT hide it) ---"
git status -s debug.log

echo "--- check-ignore -v debug.log (exit 1: tracked paths are not "ignored") ---"
git check-ignore -v debug.log || echo "exit=$?"

echo "--- after git rm --cached debug.log ---"
git rm --cached debug.log
git status -s debug.log
git check-ignore -v debug.log

Pitfalls

1. Attempting Negation Under Ignored Parent Directories

A common mistake is trying to re-include a file nested inside an ignored directory:

# FAILS: output/ report.pdf will remain ignored!
output/
!output/report.pdf

Because Git skips scanning output/ entirely, !output/report.pdf is never evaluated. To fix this, ignore directory contents using wildcards:

# FIXED: output/ is scanned, allowing report.pdf to be included
output/*
!output/report.pdf

2. Assuming .gitignore Hides Modifies to Tracked Files

Engineers often add sensitive configuration files or database credentials to .gitignore after committing them. Because Git already tracks the file in the index, modifications continue to appear in git status and will be committed. Always run git rm --cached <file> to stop tracking the file.

3. Confusion Between Local Excludes and Committed .gitignore

Putting developer-specific files (e.g., custom editor scripts or local test data) into the shared committed .gitignore clutters team configuration files. Conversely, placing project-required build outputs in .git/info/exclude leaves teammates with unignored build artifacts. Use .gitignore for team standards and .git/info/exclude or core.excludesFile for personal workflows.

4. Over-broad Wildcards Ignoring Source Files

Using recursive patterns like *cache* without path qualifiers can accidentally ignore valid source files (e.g., src/cache_service.c). Prefer directory-anchored paths like /cache/ or extension-specific rules.

5. Escaping Special Characters in Filenames

If a file or directory name contains literal wildcard characters (such as #, !, *, or [), escape them with a backslash \ in .gitignore:

# Ignores a file literally named "#notes.txt#"
\#notes.txt\#

# Ignores a file literally named "!important!.txt"
\!important!.txt

Summary

  • Git ignore precedence operates top-down: directory-level .gitignore files override $GIT_DIR/info/exclude, which overrides global core.excludesFile.
  • Within any single ignore file, the last matching pattern wins.
  • Use git check-ignore -v <path> to diagnose which ignore file, line number, and pattern apply to a given file.
  • Anchoring patterns with a leading slash / restricts matches to the directory containing that .gitignore file.
  • Negation (!) cannot re-include a file if its parent directory was excluded by an earlier rule; use wildcard matching (dir/*) on parent contents instead.
  • Tracked files are never ignored by Git. Use git rm --cached <file> to untrack indexed files so ignore rules take effect.
