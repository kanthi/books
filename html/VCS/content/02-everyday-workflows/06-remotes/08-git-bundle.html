git bundle: sneakernet a repository over a file

After this page, you can package Git commits, branches, and tags into a single portable binary file using git bundle create, verify bundle integrity and prerequisites with git bundle verify, clone or fetch directly from .bundle files across air-gapped network boundaries, and generate incremental update bundles using revision ranges.

Thesis

Network transport protocols like SSH and HTTPS form the backbone of everyday Git collaboration. However, secured production enclaves, classified environments, off-grid field deployments, and strict air-gapped infrastructure prohibit direct socket connections between repositories.

git bundle solves air-gapped repository transfer by packaging packfile data and reference metadata into a single archive file. A .bundle file acts as a read-only transport remote. You can run git clone, git fetch, git ls-remote, or git pull directly against a bundle file on a USB drive, optical disc, or secure file-transfer jumpbox without running a Git server daemon or altering internal history formats.

Mental model

 Source Repository (Network-Connected)           Target Repository (Air-Gapped)
 ┌────────────────────────────────────┐         ┌────────────────────────────────────┐
 │  refs/heads/main                   │         │  refs/heads/main                   │
 │  [Commit C] -> [Commit B] -> [A]   │         │  [Commit A]                        │
 └─────────────────┬──────────────────┘         └─────────────────▲──────────────────┘
                   │                                              │
         git bundle create delta.bundle A..main                   │ git fetch delta.bundle
                   │                                              │
                   ▼                                              │
         ┌────────────────────────────────────────────────────────┴──────────────────┐
         │                        delta.bundle (Portable File)                        │
         │  Prerequisites: [Commit A]                                                │
         │  References:    refs/heads/main -> [Commit C]                             │
         │  Payload:       Packfile containing Commits B and C                       │
         └───────────────────────────────────────────────────────────────────────────┘

A Git bundle file consists of three structural sections:

  1. Header Signature: A magic string identifying the bundle format version (for example, # v2 git bundle or # v3 git bundle).
  2. Prerequisites & References: A text header listing required ancestor commit hashes (prerequisites) followed by the object IDs and names of references included in the payload.
  3. Packfile Data: A standard Git packfile stream containing all compressed objects needed to reconstruct the referenced commits back to the prerequisite boundaries.

When you query or fetch from a bundle, Git reads the reference list in the header exactly as if it were performing a protocol handshake with a remote daemon over SSH or HTTPS.

Subcommand reference

The git bundle interface provides four core operational modes:

Command Primary Use Case Output / Action
git bundle create <file> <rev-list> Package repository references and objects into a file. Creates .bundle file containing specified revisions.
git bundle verify <file> Inspect bundle contents and validate local repository prerequisites. Prints ref heads, hash algorithm, prerequisite status, and exits zero if compatible.
git bundle list-heads <file> [refname...] Inspect available references inside a bundle without reading object data. Lists ref OIDs and matching branch or tag names.
git bundle unbundle <file> [refname...] Unpack object payload into .git/objects/pack/ and print ref list. Populates local object database directly (low-level plumbing command).

Lab: full repository packaging and cloning

To demonstrate full repository packaging, create a source repository with multiple commits, package the complete repository into a bundle file, verify its contents, and clone a new repository directly from the generated bundle file.

#!/usr/bin/env bash
set -euo pipefail

LAB_DIR="/tmp/git-bundle-full-demo"
rm -rf "${LAB_DIR}"
mkdir -p "${LAB_DIR}"
cd "${LAB_DIR}"

# Step 1: Initialize source repository and build commit history
git init -b main source-repo
cd source-repo
git config user.name "Lab Engineer"
git config user.email "engineer@example.com"

echo "version 1.0 architecture" > architecture.txt
git add architecture.txt
git commit -m "a"

echo "version 1.1 update" >> architecture.txt
git commit -am "b"

# Step 2: Package all branches and history into a bundle
git bundle create ../repo.bundle --all
cd ..

# Step 3: Inspect and verify bundle integrity
git bundle verify repo.bundle

# Step 4: Clone target repository from the bundle file
git clone repo.bundle cloned

# Step 5: Verify commit history in cloned repository
cd cloned
git log --oneline

Incremental bundles for updated environments

Transferring a complete repository file on every synchronization cycle becomes impractical when repositories grow into gigabytes. git bundle create supports revision range syntax (<limiter>..<target> or ^<prerequisite> <target>) to generate small, incremental update files containing only new commits.

Creating an incremental update

If an air-gapped target repository already contains commits up to tag v1.0, you can create a bundle containing only commits added after v1.0:

git bundle create release-1.1.bundle v1.0..main

Alternatively, if you know the exact commit hash present on the destination machine, pass that commit as a exclusion requirement:

git bundle create delta.bundle ^2eaf6be963980a17907990fe5bc2c06df5cc07dd main

Applying an incremental bundle

When applying an incremental bundle on the target machine, transport the bundle file into the destination workspace and fetch directly from the file path:

git fetch /media/usb/delta.bundle main:main

If the target repository lacks the prerequisite commit specified inside the bundle header, Git rejects the operation and terminates with an explicit error.

Lab: incremental synchronization across an air gap

The following script simulates an air-gapped workflow: initializing a base repository, exporting an initial full bundle, applying subsequent changes in the source repository, generating a minimal incremental bundle, and updating the air-gapped repository.

#!/usr/bin/env bash
set -euo pipefail

LAB_DIR="/tmp/git-bundle-incremental-demo"
rm -rf "${LAB_DIR}"
mkdir -p "${LAB_DIR}"
cd "${LAB_DIR}"

# 1. Setup origin repository
git init -b main origin-repo
cd origin-repo
git config user.name "Lab Engineer"
git config user.email "engineer@example.com"

echo "base state" > system.conf
git add system.conf
git commit -m "base commit (v1.0)"
git tag -a -m "Release 1.0" v1.0

# 2. Export full initial bundle and clone air-gapped target
git bundle create ../initial.bundle --all
cd ..
git clone initial.bundle airgap-repo

# 3. Develop new features in origin repository
cd origin-repo
echo "patch 1" >> system.conf
git commit -am "feature patch 1"

echo "patch 2" >> system.conf
git commit -am "feature patch 2"
git tag -a -m "Release 1.1" v1.1

# 4. Create incremental bundle containing only delta since v1.0
git bundle create ../update-v1.1.bundle v1.0..v1.1

# 5. Verify incremental bundle against air-gapped repository state
cd ../airgap-repo
echo "=== Pre-update verification ==="
git bundle verify ../update-v1.1.bundle

# 6. Fetch incremental updates from bundle file into air-gapped repo
echo "=== Fetching incremental update ==="
git fetch ../update-v1.1.bundle refs/tags/v1.1:refs/tags/v1.1 main:main

# 7. Display updated commit history
echo "=== Updated airgap repository log ==="
git log --oneline --graph --decorate

Transporting specific refspecs and tags

git bundle create accepts explicit refspecs, allowing precise control over exported branches and tags without bundling experimental local work:

# Package specific release branches and production tags
git bundle create release-2.4.bundle refs/heads/release/2.4 refs/tags/v2.4.0

# Package all tags and main branch
git bundle create production.bundle main --tags

To list all references available within a bundle file without altering local workspace state or reading object streams, run git bundle list-heads:

git bundle list-heads release-2.4.bundle

Common mistakes

Mistake Root Cause Remediation
Missing prerequisites error during git bundle verify The target repository does not contain the base commits required by an incremental bundle. Create a broader bundle using an older ancestor revision, or supply the missing baseline commits to the target first.
Unpackaged uncommitted changes git bundle create only reads committed objects stored in the Git database; uncommitted work tree edits and staged index changes are ignored. Commit work to a temporary branch or stash before generating a bundle.
Dangling commits after git bundle unbundle Using the low-level unbundle plumbing command unpacks objects into .git/objects/pack without updating branch pointers in refs/heads/. Use git fetch <bundle-path> <refspec> or git pull instead of manual unbundling.
Overwriting destination tracking branches Fetching from a bundle file directly into currently checked-out branch heads can cause working tree collisions. Fetch into explicit tracking branches (for example, git fetch bundle.pack main:incoming-main) and merge after reviewing.

Pitfalls

  1. Hash algorithm mismatches (SHA-1 vs. SHA-256): Git bundles inherit the object format of the source repository. A bundle created from a SHA-256 repository cannot be verified or unpacked in a legacy SHA-1 repository.
  2. Shallow repository boundaries: Creating a bundle from a shallow clone (git clone --depth) can result in unexpected prerequisite dependencies or invalid bundle generation if required parent objects are missing locally.
  3. Refspec ambiguity when fetching: If a bundle contains HEAD alongside branch names, running git fetch bundle.pack without refspecs may update remote tracking branches (FETCH_HEAD) rather than local branch heads. Always specify explicit refspecs when updating target branches.
  4. Large bundle file handling: Because a bundle is a single monolithic binary file, network dropouts during file copy operations (over jumpboxes or web portals) can corrupt the entire archive. Run git bundle verify on the destination machine immediately after copy operations.

Summary

  • git bundle creates portable, file-backed Git remotes suitable for air-gapped, offline, or secure environment synchronization.
  • git bundle create supports full repository exports (--all) and incremental deltas using Git revision ranges (such as v1.0..main).
  • git bundle verify checks archive structural integrity and confirms the destination repository possesses all prerequisite baseline commits.
  • Standard Git commands (git clone, git fetch, git pull, git ls-remote) operate directly on .bundle file paths without requiring daemon processes or network sockets.
