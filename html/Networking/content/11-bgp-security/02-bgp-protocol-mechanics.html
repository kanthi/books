BGP Protocol Mechanics Relevant to Security

Security controls attach to specific bytes in the session. This chapter walks the finite state machine, the four message types, the attributes that policy trusts, the decision process, and the ways iBGP is scaled. BGP Basics builds a session. BGP Route Reflectors builds a reflector lab. Here the question is which of those mechanics an attacker or a bad filter can bend.

Learning goals

  • Read a session failure as a state-machine event, not as “BGP is down”
  • Know which attributes are transitive, and which ones your policy must strip or overwrite
  • Place local preference, AS-path length, and MED in the order the decision process actually uses
  • Explain why iBGP split horizon, reflectors, and confederations change visibility inside an AS and do not authenticate the path

The BGP Finite State Machine and Session Establishment

A neighbour moves Idle → Connect or Active → OpenSent → OpenConfirm → Established (RFC 4271). Only Established exchanges routes. Security-relevant events on the way up:

  • The TCP connection to port 179 is the identity of the speaker unless you add TCP-AO (RFC 5925), the older TCP MD5 option (RFC 2385), or GTSM (RFC 5082) so off-path packets are harder to inject.
  • OPEN carries the AS number, the hold time, the BGP identifier, and capabilities. A capability mismatch (for example, an unexpected ADD-PATH or a role capability from RFC 9234) produces a NOTIFICATION and a return to Idle. That is a change-management failure more often than an attack, and it drops the routes.
  • The hold timer is what a silent peer looks like. Keepalives refresh it. A peer that stops sending, or a path that blackholes TCP 179 only, expires the session and withdraws the table that peer sent. That is a control-plane availability event. Size it as one.

After a reset, the peer re-advertises. A flap is a full table event on a transit session. Max-prefix and dampening in chapter 13 exist because of that reload.

BGP Message Types: Open, Update, Notification, Keepalive

Message Security reading
OPEN Negotiates identity, timers, and capabilities. Log the remote AS and the capabilities you did not expect
UPDATE The only message that changes forwarding. Contains withdrawn routes, path attributes, and NLRI
NOTIFICATION Tears the session down with a code. Treat a cease subcode for max-prefix as an incident, not as a log line
KEEPALIVE Proves the TCP session is still served. Absence is the hold-timer failure

An UPDATE is not authenticated as a whole. Optional transitive attributes travel to networks that do not understand them. That is how a community, a large community, or a future attribute crosses the Internet and lands on a router whose policy matches it by accident. Chapter 11 is that hazard. Malformed UPDATEs that reset the session are a control-plane denial-of-service tool. Modern implementations treat many attribute errors as treat-as-withdraw (RFC 7606) so one bad route does not kill the session. Know which release you run. A network that still session-resets on an optional attribute is one crafted UPDATE away from withdrawing a full table.

Path Attributes and Their Security-Relevant Properties

Attributes are either well-known or optional, and transitive or non-transitive.

Attribute Why it matters
ORIGIN Well-known. IGP, EGP, or incomplete. Easy to ignore in policy and easy to forget when comparing paths
AS_PATH Well-known. Loop detection and a coarse trust signal. The neighbour can prepend, strip, or splice before you see it
NEXT_HOP Forwarding target. eBGP normally rewrites it to the neighbour. A peer that sends an unreachable next hop installs a route you cannot use, or, with reckless policy, a route you resolve via someone else
MULTI_EXIT_DISC Non-transitive. A hint from the neighbour about which of their links you should use. Comparing MED across different neighbouring ASes needs a deliberate configuration and is a classic foot-gun
LOCAL_PREF Not sent to eBGP peers. Your ranking of exits. If a customer session can set it, the customer steers your entire AS
ATOMIC_AGGREGATE and AGGREGATOR Say that information was lost in an aggregate. An aggregate is also how a more-specific hijack hides beside a covering prefix
COMMUNITY, EXTENDED COMMUNITY, LARGE COMMUNITY Optional transitive policy signals. Chapter 11
OTC (Only-to-Customer) RFC 9234. A role-aware leak check. It works only on sessions that negotiated the role capability

Local preference and communities that you honour from outside are privileges. They belong on internal sessions and on customer sessions you explicitly designed, not on the full table from transit.

Route Selection and Path Preference Logic

RFC 4271 section 9.1 is an ordered list. Implementations add steps (local preference is the important one, and it comes first). A usable security summary, highest priority first:

  1. Highest local preference (your policy)
  2. Shortest AS path
  3. Lowest origin type (IGP before incomplete)
  4. Lowest MED, with the caveats above
  5. eBGP over iBGP
  6. Lowest IGP cost to the next hop
  7. Older tie breaks: router ID, peer address, and, with reflection, originator ID and cluster-list length

Two consequences dominate incidents. A longer prefix is a different destination in the forwarding table, so it is chosen before any of the steps above: the YouTube more-specific did not need a shorter AS path. And local preference sits above AS-path length, so a customer-tagged route beats a transit route even when the customer path looks worse. That is what you want for your own customers. It is also how a leaked customer session steals traffic if the tag is wrong.

IBGP, EBGP, Confederations, and Route Reflectors

eBGP runs between AS numbers and is where import and export policy must live. iBGP runs inside one AS. An iBGP speaker does not re-advertise a route learned from one iBGP peer to another iBGP peer, which prevents loops that AS_PATH cannot catch because the path does not grow inside the AS. The operational price is a full mesh, or a substitute.

Route reflection (RFC 4456) lets a reflector re-advertise client routes and adds ORIGINATOR_ID and CLUSTER_LIST so the relaxed rule can still detect loops. Confederations (RFC 5065) split an AS into sub-AS numbers that use eBGP rules internally and present one AS externally. Both are visibility tools. A reflector advertises only its own best path, so clients can lose an exit the reflector did not prefer. A security policy that exists only on the reflector does not exist on a client that also has an eBGP session. Apply import policy on every eBGP session, including clients of reflectors.

NEXT_HOP is unchanged by default across iBGP. A border router that does not set next-hop-self, or that does not share the edge link into the IGP, leaves internal speakers with a next hop they cannot resolve. The route is present and the traffic is not forwarded. That looks like a security filter failure and is often a resolution failure. The policy chapter’s missing next-hop-self drill is the lab form.

Summary

  • Routes exist only in Established, and a NOTIFICATION withdraws what that peer sent
  • Treat-as-withdraw beats session reset for a bad attribute, when the release implements it
  • Local preference and communities accepted from outside are authority. MED is a hint
  • More-specifics win before the path-selection steps
  • Reflection and confederations scale iBGP. They are not authentication
