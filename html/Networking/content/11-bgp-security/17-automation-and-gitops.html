Automation and Infrastructure-as-Code for Routing Security

Hand-edited route-maps are how filters rot. This chapter is the pipeline that generates them from the contract, the IRR, and the RPKI, and that refuses to push a bad build. Automation & Lab-as-Code is the lab-topology version of the same habit. Here the artifact is production policy.

Learning goals

  • Name the inputs and outputs of a routing-policy build
  • Fail a build that would install an empty filter or a sudden full table
  • Roll back a bad push by returning to the previous commit, including on the router
  • Keep humans on the exception path, with an expiry, instead of on the routine path

Configuration Management for BGP Policies

Store policy as data plus a generator, not as six vendor-specific files edited by hand.

Input Owner
Neighbour inventory: address, AS, class, quotas The peering database, reviewed like any other change
Prefixes you originate One list, also used to build ROAs
Customer and peer AS-sets The contract
Community catalogue The routing team, in the same repository
Bogon source A named feed or an IANA snapshot, with a date
Output Consumer
Prefix lists and AS-path sets Edge routers, via the stack-specific template in chapter 16
ROA requests The hosted portal API or the delegated CA
Expected origin file The monitor in chapter 18
A human-readable diff The reviewer

The generator is deterministic. Two runs on the same inputs produce the same config. Non-determinism (a live IRR query during the push, with no saved snapshot) means you cannot review what you are about to install. Query first, commit the snapshot, generate from the snapshot.

Generating Filters from RPKI and IRR Data

Chapter 8 and chapter 12 define the intersection. The automation rules that keep it safe:

  • Record the raw IRR responses and the VRP snapshot beside the generated lists
  • Abort if an IRR query fails or returns an empty expansion for a neighbour that had prefixes yesterday
  • Abort if a list shrinks or grows past a threshold (start around 20 percent, then tune) unless the change request says so
  • Abort if the list contains a bogon, a default, or a prefix longer than the class allows
  • Where a ROA marks the IRR origin Invalid, drop that IRR prefix from the allow-list and emit a review item. Do not silently prefer the IRR
  • Where a ROA marks a contracted prefix Valid and the IRR is missing, keep the prefix if the contract lists it explicitly, and open a task to fix the IRR object
  • Produce the FRR, BIRD, OpenBGPD, and vendor forms from one intermediate list so the stacks cannot drift apart

A SLURM exception is an output too. It is generated from a reviewed file of local overrides, deployed to every validator, and alarmed when it is non-empty. An unreviewed SLURM on one cache is a second Internet.

GitOps for Routing Security

Git is the source of the intended policy. A router is a rendered copy. The workflow:

  1. A change request edits data (a new customer prefix, a quota, a community row)
  2. Continuous integration runs the generator and the table tests
  3. A human reviews the diff of the generated config, not a prose promise
  4. Merge to the branch that is allowed to deploy
  5. A deployer installs the config and reports the applied revision back as a tag or a status file
  6. A drift job compares the running config to that revision

Table tests are small and mandatory. For a fixture of ten routes (customer prefix, customer leak of a transit prefix, bogon, RPKI Invalid, blackhole /32 inside the cone, blackhole /16, peer cone, peer full-table prefix, your own prefix learned externally, NotFound customer prefix), assert accept or reject. The tests run without a router. They catch a term-order bug before the deploy.

Branch protection matters as much as the tool. The deploying identity cannot push to the main branch by rewriting a router directly. Break-glass is a logged role that still commits, even if the commit is retrospective within the hour. A break-glass that never commits is the real configuration.

Safe Deployment: Testing and Rollback Strategies

Deploy policy like you deploy software, with a smaller blast radius.

  • Push to one route reflector or one edge router first when the change is inbound policy for the global table. Compare accepted-prefix counts and a list of newly rejected routes against the lab expectation
  • Customer-list updates can go to that customer’s routers first
  • ROA publishes are staged ahead of announcement changes. Publish the ROA, wait until your validators see the VRP, then announce the prefix. The reverse order makes you Invalid in the gap
  • Rollback is the previous commit, regenerated and pushed. Do not hand-edit the router back and leave git on the bad commit
  • Keep the last known-good rendered config on the router host so a deployer outage does not prevent a local rollback
  • A push that cannot withdraw itself (a ROA you published, a community a customer is still sending) needs an explicit undo step in the change request. Git revert of the router config will not un-publish a ROA

Change windows still matter for export-policy changes and for anything that can reset sessions. Max-prefix changes that lower a limit can reset a live session the moment they commit. The diff should show the old and new numbers in the review, not only the rendered blob.

Automation with Ansible, Terraform, and Custom Tools

Use the tool that fits the artifact.

Tool Fits Poor fit
Ansible Pushing a rendered config, checking it, reloading a daemon Being the database of prefix sets
Terraform The validator hosts, their addresses, and the RTR listeners as infrastructure Per-prefix policy, which wants data files and a generator, not thousands of resources
A small generator (Python or another language you will still read in two years) IRR, RPKI, and catalogue to vendor configs and tests SSH-ing to routers itself. Hand that to the deployer
The RIR’s API or your CA’s API Publishing ROAs and ASPAs from the originated-prefix list Inventing policy the list does not contain

Avoid a second source of truth in the automation tool’s state file. Terraform state should not be the only place the customer prefix list exists. The git repository is that place. Terraform or Ansible applies it.

Idempotence is required. Running the deployer twice does not flap sessions and does not duplicate communities. A reload that clears BGP because the tool rewrites a harmless comment is not idempotent. Compare the semantic config.

Preventing Configuration Drift and Unsafe Changes

Drift is any running statement the last deploy did not put there. Causes include break-glass edits, a platform adding defaults you did not pin, and a generator that does not manage a stanza another team edits.

  • Pin the managed blocks. A clearly delimited section, or a daemon whose entire config is generated, beats a file where humans and tools interleave
  • The drift job pages when the running revision differs from git, and it does not auto-repair a production router without a deploy. Auto-repair at 03:00 reintroduces the bug you just hot-fixed
  • Unsafe-change lint runs in CI: permit any, an empty prefix-list referenced as an allow, max-prefix above the global table on a customer, a blackhole policy without a length match, a new neighbour with no import policy, a ROA maxLength wider than the announced prefix without a waiver field
  • Waivers are data with an owner and an expiry date. The linter accepts them only while they are in date
  • Separate duties for the ROA publisher and the session deployer if the team is large enough. One pipeline may still perform both, with two reviews, when the team is small. Write down which model you use

The metric that matters is time-to-rollback and the fraction of neighbour configs that were generated. A network that generates 90 percent and hand-edits the largest peers has put the risk in the ungenerated 10 percent. Those peers get templates too.

Summary

  • Policy inputs live in git. Routers render them
  • The generator aborts on empty, shocking size changes, bogons, and IRR-versus-ROA contradictions
  • Review the generated diff. Test it with a fixture of routes
  • Roll back by commit. Stage ROA publishes ahead of announcements
  • Ansible and Terraform apply the repository. They do not replace it
  • Drift is paged. Lint rejects permit-any, missing limits, and wide maxLength unless a waiver is in date
