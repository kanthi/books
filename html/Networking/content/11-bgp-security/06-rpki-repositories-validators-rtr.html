RPKI Repositories, Validators, and RTR Protocol

Routers should not walk the RPKI. A relying party fetches the repositories, checks the signatures, and hands a flat table to routers over the RPKI-to-Router protocol. This chapter is that split, including how to run it so one host cannot quietly disable ROV.

Learning goals

  • Describe what a publication point serves and why RRDP replaced rsync as the preferred fetch
  • Explain what a validator is trusted for, and what it is not trusted for
  • Compare the caches this syllabus names, and choose two implementations you will actually run
  • Connect a router as an RTR client without making the cache a single point of failure

RPKI Repositories: RIR Architecture and Availability

Each CA publishes a repository: certificates, ROAs, ASPA objects where they exist, CRLs, and a manifest. Historically the fetch protocol was rsync. The RPKI Repository Delta Protocol (RRDP, RFC 8182) carries the same objects over HTTPS as a snapshot plus deltas. Production validators prefer RRDP and fall back to rsync where they must. RRDP is cacheable and easier to operate. It is also a normal HTTPS dependency: TLS interception, a broken notification file, or a stalled delta turns into stale VRPs.

RIR hosted repositories are highly available until they are not. Your design assumes one trust anchor’s publication point can fail or serve a stale snapshot. The symptom on your side is a validator log line and a VRP count that stops moving for that RIR, not a BGP session reset. Chapter 18 alarms on serial numbers and object counts per trust anchor for that reason.

Delegated repositories add your own availability problem. If your publication point is down, the world keeps the last objects it fetched until those objects expire. Budget the expiry so a bad weekend does not invalidate your address space, and budget it so a compromised key does not stay trusted for months.

RPKI Validators: How They Build the Trust Anchored View

A validator (relying party) does five things. It loads the TALs for the RIR trust anchors. It fetches each repository via RRDP or rsync. It checks the certificate chain, the signatures, the manifests, and the CRLs. It emits VRPs, and ASPA payloads or BGPsec router keys if it supports them and you enabled them. It serves that result to routers or to files.

The validator is now in the trust path. A compromised validator can feed your routers a VRP table the RPKI did not sign. Mitigations are operational: run software you can update, do not expose the RTR port to the Internet, and run a second implementation so a bug in one parser is not the only view. Local exceptions (SLURM files) let you add or remove VRPs on purpose. A SLURM file is an unsigned override. Treat it as a change-controlled break-glass, not as a second ROA database.

The ROV lab uses StayRTR as the RTR speaker in front of a validated cache. That pattern, a relying party plus an RTR server, is the production shape even when one binary does both jobs.

The RTR Protocol: Format, Flow, and Behavior

The RPKI to Router protocol (RFC 8210, which superseded RFC 6810) is a small session. The router is the client. The cache is the server. The router asks for the current serial. The cache sends the VRP table as a full dump or as a delta, plus an end-of-data marker. The router refreshes, retries, and eventually expires the data if the cache stays silent.

Those three timers are the availability policy:

Timer Meaning if you set it badly
Refresh How quickly a new ROA can affect forwarding. Too long and you are slow. Too short and you hammer the cache
Retry How soon you reconnect after a refusal. Too aggressive and a restarting cache gets a herd
Expire How long VRPs survive a dead cache. Too short and a cache reboot fail-opens the whole table to NotFound. Too long and you enforce a table the holder has already revoked

RTR version 1 carries the payloads routers needed for origin validation and for BGPsec router keys. ASPA payloads need a later RTR version (version 2 in current implementations) and router code that asks for them. A router that only speaks version 0 or 1 will do ROV and will not see ASPA, even if Routinator has the objects. Confirm the version on the session, not in the marketing note.

RTR is not authenticated in the base specification. Run it on a management network, or behind IPsec or a similar transport you already operate. An attacker who can speak RTR to your router can mark your routes Invalid.

Running a Validator in Production: Resilience and Redundancy

Run at least two caches, on separate hosts, fed by separate implementations if you can staff the updates. Point every border router at both, with a preference. Geographic spread matters when the failure is a site, not a process.

Operational habits that keep the control honest:

  • Ship validator logs and the VRP count, per address family and per trust anchor, to the same place you watch BGP
  • Page on “zero caches connected” and on a sharp drop in VRPs, not on every RRDP retry
  • Pin software versions and read the changelog. A validator upgrade that changes Invalid handling is a routing change
  • Keep TALs current. A rotated RIR trust anchor that you did not install looks like that RIR’s ROAs vanished
  • Time sync matters. Expired objects and not-yet-valid objects follow the validator’s clock
  • Do not let routers fall back to a public cache you do not operate. A last-resort cache is a last-resort trust

The ROV chapter’s deployment table is the same sequence: two caches, monitor-only, then drop Invalid.

Validator Comparison: Routinator, Falcon, BGP Tools RPKI Server

The syllabus names three things. They are not three copies of the same job.

Name What it is Use it for
Routinator (NLnet Labs) A relying party and an RTR server in one process. Fetches RRDP and rsync, validates, serves VRPs, and can serve ASPA payloads over RTR v2. Packaged, documented, and the usual first production cache. Also writes CSV, JSON, and RPSL-shaped output The cache your routers use
Falcon In the public RPKI work visible in 2026, Falcon-512 is a post-quantum signature experiment on RPKI objects, with research validators that check those objects. It is not a second production RTR cache you add beside Routinator for software diversity A lab for algorithm agility. Keep it off the router RTR port
BGP Tools RPKI view bgp.tools (and similar looking glasses) show RPKI state next to observed BGP paths. That is an investigation and monitoring surface. It reflects someone else’s collected table and someone else’s validation Checking a prefix during an incident. Not as the RTR server your edge trusts

Software diversity still wants a second relying party. The production pair this book already points at in the ROV chapter is Routinator and rpki-client (OpenBSD’s validator, which emits VRPs, BGPsec router keys, and ASPA payloads, and is often placed behind StayRTR or a native RTR listener). FORT is the other independent implementation operators use when they want a third codebase. Pick two you will patch. A comparison that stops at product names without a second parser is one bug away from a shared failure.

What to compare when you evaluate any new cache: TAL handling, RRDP and rsync behaviour, manifest and CRL strictness, RTR versions, ASPA and router-key support, SLURM, how it expires data, how it logs a dropped repository, and whether your distribution actually ships security updates for it.

RTR Client Integration in Major Router Platforms

The router-side object is small and similar everywhere. You name one or more cache addresses, a port (3323 is the familiar Routinator default; the lab’s StayRTR listener is 8282), and the refresh, retry, and expire timers. You then attach a policy that matches the validation state. Until that policy exists, the platform may label routes and still forward the Invalids. The ROV lab shows this on FRR. Chapter 16 lists the same object for FRR, BIRD, GoBGP, IOS-XR, Junos, and OpenBGPD.

Platform differences that cause outages:

  • Some daemons need an explicit module or package before the RTR client exists at all (FRR’s RPKI support is the example the ROV chapter installs)
  • Some re-evaluate import policy when VRPs change, and some label the route and wait for a soft clear. Know which one you run
  • A platform that supports only RTR v1 will ignore ASPA records your cache is ready to send
  • Preference and “ignore this cache” flags differ. Two caches at equal preference can flap the chosen table. Set the order on purpose

Summary

  • Repositories publish signed objects over RRDP, with rsync as the legacy fetch
  • Validators reduce that tree to VRPs. Routers consume VRPs over RTR
  • Refresh, retry, and expire are the fail-open policy
  • Routinator is a production cache. Falcon-512 work is a signature experiment. BGP Tools is a looking glass
  • Run two implementations, and attach them to policy or the labels do nothing
