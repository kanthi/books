Implementing BGP Security: End-to-End Configurations

A complete BGP security configuration is the same checklist on every stack. The syntax changes. This chapter is the checklist, and the objects each stack uses to satisfy it. Commands this book has already executed stay in the lab chapters named below. The other stacks are the production map, so you know what to look up in that vendor’s manual and what a generated config must contain. Do not paste an untested stanza from memory into a live session and call it this chapter.

Learning goals

  • Walk the same ten-point checklist against any BGP speaker
  • Find the FRR, BIRD, and platform equivalents of filter, ROV, max-prefix, and communities
  • Know which stacks speak RTR natively and which ones consume a generated file
  • Refuse a configuration that labels Invalid and still installs it

The checklist every stack has to answer

Apply this list to every external neighbour. Internal reflectors inherit tagged routes and do not invent a second policy.

  1. Session identity: peer address, remote AS, and either GTSM or TCP-AO/MD5 as the platform allows
  2. Import default reject
  3. Bogon and maximum-length reject
  4. Allow-list where the neighbour is a customer or a peer
  5. ROV state attached to policy, Invalid rejected where you enforce
  6. AS-path constraint for the neighbour class
  7. Community strip, catalogue accept, ingress tag
  8. Export default reject, announce only the tagged cone
  9. Max-prefix with a warning threshold and an explicit overflow action
  10. Logs and counters you can find in chapter 18

If a platform cannot do a row, write down the compensating control. “Cannot” is a design input. Silence is how the row gets skipped.

FRRouting: Complete BGP Security Configuration

FRR is the reference stack in this book. The labs already contain the pieces:

Checklist row Where it is exercised
Session and advertise BGP Basics, A First BGP Lab with netlab
Prefix lists and route-maps Policy & Filters
Well-known communities BGP no_export and Well-Known Communities
RTR client, states, drop Invalid RPKI — Route Origin Validation
Tight maxLength RPKI ROAs and the maxLength Trap
Reflection BGP Route Reflectors
Control-plane policing around the daemon Control-Plane Protection

A production FRR neighbour template is those pieces on one neighbor block: a prefix-list or a route-map in and out, maximum-prefix, a password or AO if you use one, ttl-security hops on single-hop sessions, and rpki cache at the BGP process with the route-map matching rpki invalid. The ROV chapter records a real FRR behaviour you have to design around: validation state can update when VRPs change while inbound policy does not re-run until a soft clear. A generated config for FRR includes the operational step, or a release that fixed it, and does not assume the lab is the current daemon.

Keep bgpd from accepting TCP 179 on interfaces that face hosts. That is host firewall and the control-plane chapter, not an FRR route-map.

BIRD: Security-Focused BGP Daemon Setup

BIRD expresses the checklist as protocols and functions rather than route-maps. A bgp protocol per neighbour holds the remote AS, the password, the multihop or TTL security knob, and import / export filter functions. import none; and export none; are the safe defaults. ROV is a roa_check() (or the successor function in the release you run) against a roa table filled by the RPKI protocol that speaks RTR, or filled by a file rpki-client emits. Max-prefix is the neighbour’s import limit. Communities are matched in the filter language and deleted with an explicit clear before you add your tag.

BIRD will happily install an Invalid route if the filter never calls the ROA check. Review the filter, not the fact that an RPKI protocol block exists. Generate filters from the same catalogue and prefix data as FRR. Do not maintain a second hand-written copy of the customer list in BIRD syntax.

GoBGP: Programmatic BGP Security

GoBGP is an API-driven speaker. The checklist lives in the process that programs it, not in a text file someone edits on the router. That is an advantage if the process is the generator from chapter 17, and it is a hazard if a controller can AddPath faster than review.

Require the controller to send, for each peer: import policy default reject, the allow-list, the RTR-informed validation result or a policy that asks the RPKI server, max-prefix, and an export policy built from tags. Store the intended policy in git and make the controller reconcile toward it. A peer that exists in the live daemon and not in git is drift, same as a surprise line on an FRR box.

GoBGP is also a good lab speaker when you want to inject a malformed or hostile UPDATE on purpose. Keep that function out of the production binary’s configuration path. Test tools and production speakers do not share a policy repository entry.

Cisco IOS-XR: Production BGP Security

IOS-XR implements the checklist with neighbour groups, route-policies, prefix-sets, and an RPKI cache configuration under the BGP process. A neighbour group per class (customer, peer, transit) attaches the route-policy in and out, the maximum-prefix, the password or TCP-AO, and TTL security. Route-policies match RPKI state (validation-state) only after the caches are configured and the session is up. As on every other stack, a cache with no policy is a label.

Operational points that matter at this scale: apply policies with neighbour groups so a new customer cannot be a bare neighbor statement, use prefix-set objects generated from chapter 17 rather than inline lists, and confirm whether a VRP change re-evaluates the route-policy or waits for a soft reset. Put that answer in the runbook. Keyring and management-plane ACLs are part of row 1 and row 10. A route-policy does not protect the RP CPU by itself. Control-plane protection on the platform still has to admit TCP 179 only from configured peers.

Juniper Junos: Enterprise-Grade BGP Security

Junos uses groups, import and export policy-statements, prefix-lists, and maximum-prefixes. RPKI is a validation session toward a cache and a policy condition that matches validation state. The safe pattern is a group per neighbour class with import and export set to a reject policy at the group level, overridden only by the statements the generator owns.

Junos policy is first-match. A term that accepts communities before the term that rejects RPKI Invalid will accept the Invalid. Order the terms in the generated policy: bogon reject, Invalid reject, allow-list accept, default reject. Test that order with a table of routes, not by reading the term list once. TTL security, authentication, and firewall filters that protect the routing engine are the session and control-plane rows. The firewall filter and the policy-statement are different objects and you need both.

OpenBGPD and Lightweight Deployments

OpenBGPD uses a compact configuration with allow from and deny from style rules, prefix sets, and RPKI as a roa-set that rpki-client can refresh on a timer. That file-based handoff is a feature. The validator and the daemon update independently, and a failed validator run must not replace the roa-set with an empty file. The refresh script keeps the previous set when the new one fails the sanity check from chapter 6 (non-zero, not a shocking drop).

Lightweight deployments (a branch router, an appliance, a small FRR or OpenBGPD box) still run the full checklist. They often take a default rather than a full table, which makes the inbound ROV row small and makes the outbound ROA and prefix list the important rows. Do not “simplify” by deleting the export filter because the router only has one upstream. One upstream is still a path by which you can leak a downstream.

OpenBGPD’s rule order is the policy. Read it top to bottom in review. A generated file with a final allow any for debugging is a failed build.

What this chapter refuses to be

It is not a paste-bin of six complete production configurations. Those rot, and the ones for IOS-XR and Junos have not been executed in this book’s lab. The next writing pass that adds a configuration should add it the way the ROV chapter did: a topology, the commands, the observed state, and a failure drill. Until then, generate config from the checklist, review the diff, and run it on the stack you can actually watch.

Summary

  • Ten rows define a secure external neighbour on every platform
  • FRR’s rows are already labs in this book. Match the other stacks to those rows
  • A cache without a policy that rejects Invalid does not implement ROV
  • BIRD functions, GoBGP controllers, IOS-XR route-policies, Junos terms, and OpenBGPD rules are the same filter in different syntax
  • Empty validator output must not become the new allow-list or the new VRP table
