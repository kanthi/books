RPKI Cryptographic Architecture

RPKI is a certificate hierarchy for number resources, not a certificate hierarchy for websites. This chapter is the object model: who signs, what a certificate binds, what a ROA claims, and how revocation is published. The lab that turns those claims into forwarding decisions is RPKI — Route Origin Validation. The maxLength failure mode is RPKI ROAs and the maxLength Trap.

Learning goals

  • Trace a ROA from an RIR trust anchor to an end-entity certificate
  • Read a ROA as prefix, origin AS, and max length
  • Apply the validity rule without a router
  • Explain why revocation in RPKI is a manifest and a CRL, not an online status check

The RPKI Hierarchy: RIRs, LIRs, and End Entities

The five regional registries (AFRINIC, APNIC, ARIN, LACNIC, RIPE NCC) each publish a trust anchor locator (TAL). A relying party starts there and walks down. An RIR issues a certificate to a national registry or to a local registry (LIR / NIR), which issues a certificate to a member, which issues an end-entity certificate used to sign published objects. The chain mirrors address allocation. A member cannot sign a ROA for space the parent certificate did not grant.

Two operating modes matter in production:

  • Hosted. The RIR holds the member’s keys and offers a web portal that publishes ROAs. Most networks should start here. The RIR is inside the operational trust boundary for those keys.
  • Delegated. The member runs a certificate authority (commonly Krill, or an RIR-provided delegated setup) and publishes through its own repository. Use this when you need automation, business-unit separation, or ROAs that the portal cannot express. You now run a CA, and chapter 20 applies to you in full.

A broken parent certificate hides every object under it. Monitoring “is my ROA visible?” without monitoring “is my parent’s publication point reachable?” misses the usual outage.

Resource Certificates: Binding Cryptography to IP Addresses and AS Numbers

Resource certificates are X.509 certificates with extensions defined for IP addresses and AS numbers (RFC 3779) under the RPKI certificate profile (RFC 6487). The important property is the binding. The certificate says “the holder of this key is the registrant of these prefixes and these ASNs,” as delegated by the parent. It does not say anything about BGP by itself.

Parents constrain children. A certificate that covers 203.0.113.0/24 cannot issue a child for 203.0.113.0/23. Over-claiming objects fail validation and never become VRPs. That is why a fat-fingered ROA for space you do not hold does not show up as Valid on the Internet. It shows up as an invalid object in your validator logs.

Cryptographic Algorithms and Key Management in RPKI

RPKI signed objects use a certificate profile and a signed-object format (CMS). The algorithm suite is part of the profile and has changed over time by RFC, so validators and CAs have to overlap on a suite or objects fail closed. Operationally you care about three key classes:

Key Lives where If it leaks or expires
Trust anchor The RIR Every object under that RIR fails until relying parties install a new TAL. This is rare and global
CA key (hosted or delegated) RIR HSM, or your CA An attacker can sign ROAs for your resources. Rotation is a planned event
End-entity key for one object Issued per ROA or per ASPA, often automatically Short-lived. Re-issuance is normal. Loss means that object disappears at the next publication

Routers never see these keys. They see VRPs. Algorithm agility is a validator and CA problem. When a suite is retired, the failure mode is a sudden drop in VRP count for one trust anchor, which is why chapter 18 alerts on that count per RIR and not only on the total.

Post-quantum signature experiments exist, including work that signs RPKI objects with Falcon-512. They are not the suite production relying parties require on the public RPKI in 2026. Do not point a production router at an experimental cache and call it diversity.

Route Origin Authorizations: Structure, Semantics, and Max-Length Semantics

A ROA (RFC 9582, which superseded RFC 6482) is a signed object under an end-entity certificate. Its payload authorises one AS number to originate one or more prefixes, each with a maximum length. The semantics are narrow on purpose.

  • The origin in the ROA is the only origin that becomes Valid for that prefix, up to the length.
  • maxLength is optional in the sense that it defaults to the prefix length when omitted. Omitted is the tight choice.
  • A ROA does not authorise the AS path, the neighbour, or the next hop.
  • Multiple ROAs may cover the same prefix for different origins (multi-origin, or a planned move). Any listed origin is Valid.
  • A ROA for an aggregate does not cover a more-specific unless maxLength reaches that length or a separate ROA exists.

RFC 9319 is the operational rule: set maxLength to the prefix length you actually announce. A ROA for 203.0.113.0/22 with maxLength 24 authorises every /24 inside it for that origin. Anyone who can originate as that AS, or any mistake that leaks those more-specifics from that AS, is Valid. The maxlength chapter shows this with a lab prefix.

AS0 in a ROA means “this space should not be originated on the global Internet.” It is a deliberate Invalid for every real origin. Use it for unallocated or internal space you publish so that an accidental announcement is Invalid rather than NotFound. Do not sprinkle AS0 ROAs on space you will announce next week.

ROA Validation Logic: What “Valid” Actually Means

Relying parties reduce the tree to validated ROA payloads: triples of (prefix, maxLength, ASN). RFC 6811 then classifies one BGP route:

  1. Find VRPs that cover the announced prefix (the VRP prefix is equal or less specific).
  2. If none cover it, the state is NotFound.
  3. If a covering VRP has the same origin AS and the announced length is between the VRP prefix length and maxLength inclusive, the state is Valid.
  4. Otherwise the state is Invalid.

Valid means “some resource holder signed that this origin may announce this length.” It does not mean “this path is the path the holder wanted” or “this neighbour is allowed to transit it.” Invalid means “a covering VRP exists and this announcement contradicts it.” NotFound means “no covering VRP.” Networks that speak loosely about “RPKI valid so it is safe” have collapsed those three sentences into one.

Overlapping VRPs are allowed. One Valid covering VRP is enough for Valid, even if another VRP would have made a different origin Valid too. A route is Invalid only when every covering VRP rejects it.

Revocation, CRLs, and Manifest Files

RPKI does not call back to an online status server during routing. Publication points hand out three kinds of freshness:

  • CRLs list revoked certificates. A validator that accepts a revoked certificate will keep trusting objects that the holder tried to kill.
  • Manifests (RFC 9286) list every object the publisher currently intends, with hashes. A missing object, or an object that is not on the manifest, is a publication failure. Manifests stop a relying party from silently accepting a stale subset.
  • Validity intervals on certificates and objects. An expired ROA falls out of the VRP set. The BGP route then becomes NotFound, or Invalid if another ROA still covers it and disagrees. Expiry is a common self-inflicted outage when a delegated CA stops renewing.

Hosted RPKI hides most of this behind the portal. Delegated operation has to alarm on manifest age, CRL expiry, and repository reachability. A ROA you “deleted” in a database and failed to publish is still a VRP until the manifest that omits it is fetched.

Summary

  • Trust flows from five RIR anchors down the allocation tree
  • Certificates bind keys to prefixes and ASNs. ROAs bind an origin and a max length
  • Tight maxLength is the default. Wide maxLength authorises more-specifics
  • Valid is an origin statement. Invalid is a contradiction. NotFound is silence
  • Revocation is published as CRLs, manifests, and expiry, and it only helps if validators fetch it
