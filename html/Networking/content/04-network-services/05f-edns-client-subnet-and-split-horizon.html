EDNS Client Subnet: Geo-Answers, Cache Scope, Privacy and Split-Horizon Pitfalls

A CDN’s authoritative nameserver picks an answer by asking “where is this query coming from?”. For years the only clue was the source address of the query, which is the recursive resolver, not the user. That works when the resolver sits next to its users, as an ISP’s resolver usually does. It fails for large public resolvers, whose users may be a continent away from the resolver instance that happens to serve them. EDNS Client Subnet (ECS, RFC 7871) lets the resolver pass a truncated piece of the client’s address to the authoritative server, and lets the server say how widely its answer may be reused.

That one option touches three things operators care about. Performance: users get the nearby edge. Caching: one name can now have many cached answers. Privacy: part of the user’s address leaves the resolver in clear text. It also invites a dangerous shortcut, using ECS to choose an internal or external split-horizon view. This chapter takes the option apart on the wire. The lab builds a toy geo authoritative server and an RFC 7871 caching resolver and measures what scope does to cache size and correctness. It then shows how an ECS-keyed view leaks internal answers, and finally asks two public resolvers what they actually send.

Learning goals

  • Encode and decode the ECS option (FAMILY, SOURCE PREFIX-LENGTH, SCOPE PREFIX-LENGTH, truncated ADDRESS) and reject malformed ones.
  • Explain the difference between SOURCE and SCOPE and how a resolver caches by scope (RFC 7871 section 7.3.1).
  • Compute a correct SCOPE for an answer that has more specific exceptions, and show what a wrong one does to everyone else’s answers.
  • Weigh the cost of ECS: cache fragmentation, privacy, and the spoofing amplification of section 11.2.
  • Explain why choosing split-horizon views by ECS is a security bug, and build split-horizon safely.
  • Check what ECS your resolver sends with a public probe name.

Version note

The lab ran on Linux 6.12.94 with Python 3.13.5, standard library only. The offline part runs in an unprivileged network namespace (unshare -urn) on loopback, with real DNS messages over UDP. The live part queries the public DNS-over-HTTPS JSON interfaces of Google Public DNS and Cloudflare with urllib, and masks the box’s own egress prefix in the output. Unbound, PowerDNS Recursor, dnsdist and BIND configurations in “In production” were checked against their current documentation but not run here.

Why the resolver’s address is not enough

user in Chennai --> public resolver instance in Singapore --> cdn.example authoritative
                    (source address the auth sees)              "Singapore? use the SG edge"

Without ECS the authoritative server geolocates the resolver. With anycast public resolvers, the instance a user reaches depends on routing, not geography. ISPs that centralise resolvers in one city create the same problem at a smaller scale. ECS adds the user’s network, truncated, to the query the resolver sends:

resolver -> auth:   cdn.example A?   OPT: ECS family 1, source /24, scope 0, address 49.207.48
auth -> resolver:   cdn.example A 203.0.113.10   OPT: ECS family 1, source /24, scope /20, address 49.207.48
                    "this answer is right for 49.207.48.0/20; cache it for that range"

The option on the wire

ECS is EDNS option code 8 inside the OPT pseudo-record (RFC 7871 section 6):

+0 (MSB)                            +1 (LSB)
+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
|                          OPTION-CODE = 8                      |
+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
|                          OPTION-LENGTH                        |
+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
|                            FAMILY  (1 = IPv4, 2 = IPv6)       |
+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
|     SOURCE PREFIX-LENGTH      |     SCOPE PREFIX-LENGTH       |
+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
|                           ADDRESS...  (ceil(SOURCE/8) octets) |
+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+---+
  • SOURCE PREFIX-LENGTH: how many leading bits of the client address the sender reveals.
  • SCOPE PREFIX-LENGTH: 0 in queries. In responses, how many leading bits the answer depends on.
  • ADDRESS: truncated to SOURCE bits and padded with zeros only to the end of the last octet. Sending too many or too few octets, or non-zero bits beyond SOURCE, should get FORMERR. An unknown FAMILY must.

Recommended truncation is /24 for IPv4 and /56 for IPv6 (section 11.1). An ISP that knows a whole /20 is one location should send /20: better privacy and better caching. A SOURCE of 0 means “do not use my address”. A resolver that receives SOURCE 0 from a client must not add client address information upstream (section 7.5).

SCOPE and caching

The authoritative server answers with the same FAMILY, SOURCE and ADDRESS it received and its own SCOPE. The resolver caches the answer for the client’s network truncated to the scope (section 7.3.1):

  • If SCOPE is not longer than SOURCE, cache it for that SCOPE-bit network. Any client inside can be answered from it.
  • If SOURCE was already the longest the resolver is willing to send, cache for the SOURCE network even if SCOPE is longer.
  • If SOURCE was shorter than the resolver’s maximum and SCOPE is longer, the answer may only be reused for queries with the same SOURCE; the server is saying “tell me more and I can do better” (section 7.2.1).
  • A response without ECS is treated as SCOPE 0: one answer for everyone.

This is where the server’s choice matters. Section 7.2.1 gives the example of a /20 that maps to A with one /24 exception mapping to B. The server must not answer A with scope /20 for a client outside the exception, because a resolver would then serve A to the exception’s clients too. It must pick a scope that excludes the exception: 1.2.0/23, 1.2.2/24, 1.2.4/22 or 1.2.8/21, depending on where the client is. The lab computes exactly that and shows what happens when a server gets it wrong.

The price

  • Cache fragmentation. One name now has one cache entry per scope network. RFC 7871 says ECS “SHOULD be disabled in all default configurations” of recursive resolvers and should be enabled only where the benefit is clear. Resolvers should also limit how many networks they keep per name (section 11.3).
  • More upstream queries. Every cache miss in a new network is another query to the authoritative server.
  • Privacy. The client’s network travels in clear text to every authoritative server that gets ECS and across every network on the way (section 11.1). Many resolvers only send ECS to authoritative servers that are known to use it.
  • Spoofing. With ECS a resolver may have several queries for the same name in flight, one per network. That gives an off-path spoofer more targets, and a forged reply with SCOPE 0 would be cached for everyone. The ECS option in a response must echo the query’s FAMILY, ADDRESS and SOURCE, and resolvers should discard responses that do not match (section 11.2).

Split-horizon and ECS

Split-horizon DNS returns different answers to different clients: internal addresses to the office, public addresses to the Internet. Classic implementations, such as BIND views with match-clients or separate internal and external servers, choose the view by the packet’s source address or a TSIG key. Those are things a remote attacker cannot easily fake for a TCP query or a signed one.

ECS is different: it is a claim inside the packet, written by whoever sent the query. An authoritative server that picks the internal view because the ECS address is in 10.0.0.0/8 hands internal names and addresses to anyone who writes 10.1.2.3 into the option. RFC 7871 section 10 says a public authoritative server receiving a private ADDRESS should ignore it, answer based on the resolver’s address, and return a scope covering the whole private range (10.0.0.0/8, for example). It must not treat the address as proof of anything. The lab shows the leak in four lines.

The lab

ecs-lab.py has four parts:

  • an ECS encoder and decoder working on real DNS messages over UDP;
  • GeoAuth, a toy authoritative server for cdn.example. It maps 198.51.100.0/24 to edge A (203.0.113.10), the rest of 198.51.0.0/16 to edge B (.20) and everything else to edge C (.30). It can compute a correct scope, use a naive per-row scope, ignore ECS, or act as a split-horizon server keyed on either the source address or ECS;
  • Resolver, a caching resolver that sends ECS with a configurable SOURCE and caches by min(SCOPE, SOURCE);
  • a deterministic set of 2000 client addresses drawn from four networks.

live-ecs.py asks Google Public DNS for the TXT record o-o.myaddr.l.google.com, which echoes the resolver’s address and the ECS it forwarded, with and without an explicit edns_client_subnet=0.0.0.0/0 opt-out. It asks the same through Cloudflare, then resolves www.google.com with three explicit client subnets. Your own prefix is replaced by <your-egress-prefix>.

Run sh lab-ecs.sh in a folder with the three files. The offline part needs unshare -urn, which most current distributions allow for ordinary users; the live part needs outbound HTTPS.

lab-ecs.sh:

#!/bin/sh
# Offline part in a private network namespace (no root needed), live part on the real network.
set -e
unshare -urn sh -c 'ip link set lo up; python3 ecs-lab.py'
echo
python3 live-ecs.py

ecs-lab.py:

#!/usr/bin/env python3
"""EDNS Client Subnet (RFC 7871): wire format, a toy geo authoritative over
UDP, a resolver cache that honours SCOPE, and ECS misused for split views."""
import ipaddress as ip, random, socket, struct, threading

def ecs_option(addr, source_len):
    a = ip.ip_address(addr)
    fam = 1 if a.version == 4 else 2
    net = ip.ip_network(f"{addr}/{source_len}", strict=False)
    nbytes = (source_len + 7) // 8
    body = struct.pack("!HBB", fam, source_len, 0) + net.network_address.packed[:nbytes]
    return struct.pack("!HH", 8, len(body)) + body

def parse_ecs(opt):
    code, olen, fam, src, scope = struct.unpack("!HHHBB", opt[:8])
    raw = opt[8:4 + olen]
    width = 4 if fam == 1 else 16
    addr = ip.ip_address(raw + b"\0" * (width - len(raw)))
    return fam, src, scope, addr, raw

def query(qname, ecs=None, qid=None):
    qid = qid if qid is not None else random.randrange(65536)
    q = struct.pack("!HHHHHH", qid, 0x0100, 1, 0, 0, 1)
    q += b"".join(bytes([len(l)]) + l.encode() for l in qname.rstrip(".").split(".")) + b"\0" + struct.pack("!HH", 1, 1)
    rdata = ecs or b""
    q += b"\0" + struct.pack("!HHIH", 41, 1232, 0, len(rdata)) + rdata
    return q

def split(msg):
    """Return id, rcode, qname, answer IPv4 list, ECS option bytes (or None)."""
    qid, flags, qd, an, ns, ar = struct.unpack("!HHHHHH", msg[:12])
    pos, labels = 12, []
    while msg[pos]:
        labels.append(msg[pos + 1:pos + 1 + msg[pos]].decode()); pos += 1 + msg[pos]
    pos += 5
    answers, ecs = [], None
    for _ in range(an + ns + ar):
        if msg[pos] & 0xc0 == 0xc0: pos += 2
        else:
            while msg[pos]: pos += 1 + msg[pos]
            pos += 1
        typ, cls, ttl, rdlen = struct.unpack("!HHIH", msg[pos:pos + 10]); pos += 10
        rd = msg[pos:pos + rdlen]; pos += rdlen
        if typ == 1: answers.append(socket.inet_ntoa(rd))
        if typ == 41 and rd[:2] == b"\x00\x08": ecs = rd
    return qid, flags & 0xf, ".".join(labels), answers, ecs

def reply(q, answers, ecs_echo=None, scope=None, rcode=0):
    qid = struct.unpack("!H", q[:2])[0]
    qend = 12
    while q[qend]: qend += 1 + q[qend]
    qend += 5
    r = struct.pack("!HHHHHH", qid, 0x8400 | rcode, 1, len(answers), 0, 1) + q[12:qend]
    for a in answers:
        r += b"\xc0\x0c" + struct.pack("!HHIH", 1, 1, 60, 4) + socket.inet_aton(a)
    rdata = b""
    if ecs_echo is not None:
        rdata = ecs_echo[:7] + bytes([scope]) + ecs_echo[8:]
    return r + b"\0" + struct.pack("!HHIH", 41, 1232, 0, len(rdata)) + rdata

class GeoAuth(threading.Thread):
    """cdn.example: answer by client subnet. Returns SCOPE as configured."""
    MAP = [(ip.ip_network("198.51.100.0/24"), "203.0.113.10", 24),   # edge-a, a /24 exception
           (ip.ip_network("198.51.0.0/16"), "203.0.113.20", 16),     # edge-b for the rest of the /16
           (ip.ip_network("0.0.0.0/0"), "203.0.113.30", 0)]          # edge-c default
    def __init__(self, port, use_ecs=True, views=None, naive_scope=False):
        super().__init__(daemon=True)
        self.s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); self.s.bind(("127.0.0.1", port))
        self.use_ecs, self.views, self.seen, self.count = use_ecs, views, [], 0
        self.naive = naive_scope
    @classmethod
    def truth(cls, addr):
        return next(ans for net, ans, _ in cls.MAP if ip.ip_address(addr) in net)
    def scope_for(self, addr, row_net, row_scope):
        """Shortest prefix around addr that stays inside row_net and does not
        overlap any more-specific row (RFC 7871 section 7.2.1)."""
        if self.naive:
            return row_scope
        for plen in range(row_net.prefixlen, 33):
            n = ip.ip_network(f"{addr}/{plen}", strict=False)
            if not any(n.overlaps(other) for other, _, _ in self.MAP if other.prefixlen > row_net.prefixlen):
                return plen
    def run(self):
        while True:
            q, peer = self.s.recvfrom(4096); self.count += 1
            qid, _, name, _, ecs = split(q)
            if ecs and not self.views:
                fam, src, scope, addr, raw = parse_ecs(ecs)
                if ip.ip_address(addr) != ip.ip_network(f"{addr}/{src}", strict=False).network_address or len(raw) != (src + 7) // 8:
                    self.s.sendto(reply(q, [], rcode=1), peer); continue          # FORMERR
                self.seen.append(f"{peer[0]} says client is {addr}/{src}")
                if self.use_ecs:
                    for net, ans, sc in self.MAP:
                        if addr in net:
                            self.s.sendto(reply(q, [ans], ecs, self.scope_for(addr, net, sc)), peer); break
                else:
                    self.s.sendto(reply(q, ["203.0.113.30"], ecs, 0), peer)
            elif self.views:
                client = parse_ecs(ecs)[3] if (ecs and self.views == "ecs") else ip.ip_address(peer[0])
                internal = client in ip.ip_network("10.0.0.0/8")
                self.s.sendto(reply(q, ["10.20.30.40" if internal else "203.0.113.99"], ecs, 0 if ecs is None else 24), peer)
            else:
                self.seen.append(f"{peer[0]} (no ECS)")
                self.s.sendto(reply(q, ["203.0.113.30"]), peer)

class Resolver:
    """Cache keyed by (name, network at the returned scope), RFC 7871 7.3.1."""
    def __init__(self, auth_port, source_len=24, send_ecs=True):
        self.port, self.source_len, self.send_ecs = auth_port, source_len, send_ecs
        self.cache, self.upstream = [], 0
        self.sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); self.sock.settimeout(1)
    def resolve(self, name, client):
        c = ip.ip_address(client)
        for nm, net, ans in self.cache:
            if nm == name and c in net:
                return ans, "hit"
        ecs = ecs_option(client, self.source_len) if self.send_ecs else None
        self.sock.sendto(query(name, ecs), ("127.0.0.1", self.port)); self.upstream += 1
        r, _ = self.sock.recvfrom(4096)
        _, rcode, _, ans, recs = split(r)
        if recs:
            fam, src, scope, addr, _ = parse_ecs(recs)
            plen = min(scope, src)
            net = ip.ip_network(f"{client}/{plen}", strict=False)
        else:
            net = ip.ip_network("0.0.0.0/0")
        self.cache.append((name, net, tuple(ans)))
        return tuple(ans), f"miss, cached for {net}"

    out = []

        p = rnd.choice(pools)
        out.append(str(p.network_address + rnd.randrange(p.num_addresses)))
    return out

Reading the output

1. Option bytes

00 08 is the option code, then the length. For 198.51.100.77/24 the body is family 00 01, source 18 (24), scope 00 and three address octets c6 33 64. The fourth octet is not sent at all, so the authoritative server never sees .77. At /20 the third octet becomes 60 (96): bits beyond the source are zeroed, not just hidden. The IPv6 /56 sends 7 octets. A source of 0 sends no address octets, the explicit “do not use my address” signal.

2. Scopes that respect exceptions

The mapping has one exception inside a /16. The client in the /24 exception gets edge A with scope /24. The client at 198.51.7.9 gets edge B, but the scope is /18, not /16: 198.51.0.0/18 is the largest block around it that does not contain 198.51.100.0/24. The client at 192.0.2.50 gets the default edge with scope /6: 192.0.0.0/6 is the largest block around it that does not overlap 198.51.0.0/16, so a /0 would have been wrong. The malformed option, four address octets for a /24, gets FORMERR. Then look at what the server learned: only the three /24s the resolver chose to reveal, and nothing about the hosts.

3. Cache size against correctness

2000 queries from clients in four networks, one cache per row:

  • No ECS, and ECS sent but ignored by the server: one upstream query, one cache entry, and 1019 clients (about half) sent to the wrong edge. Everyone gets whatever the first client got.
  • Naive scopes (/24, /16 or /0 straight from the mapping table) look identical, and that is the trap. The first client happened to be in the default region, the server answered with scope /0, and the resolver correctly reused that answer for everyone, including the clients that should have gone to A and B. A wrong scope is not a local mistake: it overrides the server’s own exceptions for every resolver that caches the answer.
  • Correct scopes: 11 upstream queries and 11 cache entries, every client on the right edge. Eleven is the number of blocks needed to tile the four networks around the exception, not 2000; that is how much fragmentation a well-behaved server causes.
  • Resolver revealing only /16: 3 entries, but 506 clients (the quarter in 198.51.100.0/24) get edge B, because the resolver never revealed enough bits to tell them apart. That is section 7.3.1 working as written: privacy and cache size bought with accuracy.

The last three lines show the cache keys the correct server produced: 192.0.0.0/6, 198.51.0.0/18 and 198.51.100.0/24.

4. Opting out

With SOURCE 0 the server learns 0.0.0.0/0 and answers from its default. A client or stub that wants its network kept private can ask for this, and a conforming resolver must not substitute the client’s real address.

5. Split-horizon keyed on ECS leaks

The server keyed on the packet source gives the outside client the public answer whether or not it claims an internal subnet. The server keyed on ECS gives the same outside client the internal address 10.20.30.40 as soon as it writes 10.1.2.0/24 into the option. Nothing else was needed: no spoofed packet source and no access to the internal network.

6. What public resolvers send

  • Through Google Public DNS, Google’s own authoritative server saw the resolver’s address and edns0-client-subnet <prefix>/56. The box egresses over IPv6, so it got the recommended /56; an IPv4 client would see /24.
  • With edns_client_subnet=0.0.0.0/0 the ECS line disappears.
  • Through Cloudflare’s resolver only the resolver’s own address comes back, so it sent no ECS for this name.
  • For www.google.com with three explicit subnets the answer carried scopes /20, /19 and /16. The scope is the server telling the resolver how far each answer may be reused; here the addresses were the same, but the cache entries are not.

    max-ecs-tree-size-ipv6: 100

PowerDNS Recursor

Recursor sends ECS only for netmasks and domains in edns-subnet-allow-list (YAML: outgoing.edns_subnet_allow_list) and truncates to ecs-ipv4-bits and ecs-ipv6-bits (defaults 24 and 56). ecs-add-for decides which clients’ own addresses are used, and use-incoming-edns-subnet decides whether an ECS option received from a client or forwarder is passed on. Leave that off unless the sender is trusted.

dnsdist in front of a resolver farm

A load balancer between clients and resolvers hides the client address; dnsdist can add ECS (useClientSubnet=true on the backend, prefix lengths set with setECSSourcePrefixV4 and setECSSourcePrefixV6) so the resolvers can pass it on. That is ECS used inside your own network. Make sure the resolvers trust it only from dnsdist.

Split-horizon done safely

  • Choose views by packet source address for TCP or for queries from your own resolvers, or better, by TSIG key, as in BIND view blocks with match-clients { key internal-key; };. Never by ECS.
  • Give internal clients an internal resolver that sends no ECS, and run the external view on servers that hold no internal data. A server that does not have the internal zone cannot leak it.
  • If an authoritative server receives a private ECS address, ignore it and answer as if ECS were absent, with a scope covering the whole private block (RFC 7871 section 10).
  • BIND’s query log prints any ECS option as [ECS address/source/scope]. Grep for private ranges arriving from outside to find probes.

Checking a resolver

Query o-o.myaddr.l.google.com TXT through the resolver you want to check. The answer shows the resolver egress address Google saw and any ECS it forwarded. Run it from a client on IPv4 and on IPv6, and through every forwarding layer (home router, corporate forwarder, public resolver).

Gotchas

  • Scope 0 echoes. Some servers echo unknown EDNS options back. With ECS that is mostly harmless: SCOPE comes back 0 and the answer is cached for everyone, exactly as if ECS were absent.
  • A server that answers SCOPE 0 for a default while having exceptions breaks its own exceptions (lab section 3, naive row). Compute scopes that exclude more specific entries.
  • ECS and DNSSEC are independent. Tailored answers can be signed. The RRSIG is per answer, and the cache keeps each tailored RRset with its own signatures.
  • Forwarders multiply truncation. A forwarder that sends /24 to a resolver that is configured for /20 produces /20 upstream. A forwarder that passes its own address as ECS makes every user look like the forwarder.
  • REFUSED with ECS means “retry without it”. An ECS-aware resolver that gets REFUSED from an authoritative server must retry the query without ECS (section 7.3), because REFUSED also commonly means “not authoritative for this name”.
  • Logs become personal data. Authoritative servers that log ECS now hold client network information, so treat them like access logs.
  • Mismatch checking matters. Validate that the response echoes FAMILY, SOURCE and ADDRESS. A resolver that accepts any SCOPE-0 response for an in-flight query widens the window for spoofing.
