Negative Answers in DNS: NXDOMAIN, NODATA, Negative Caching and Compact Denial

DNS operational incidents frequently stem from a common misconception: assuming that failure to fetch a record implies that the authoritative server is unreachable or misconfigured. In production environments, the culprit is often a negative answer that was generated correctly, transmitted with valid headers, and subsequently stored in a recursive resolver cache. When an engineer provisioning infrastructure tests a name before the record is created in control planes or route53/Cloudflare zones, the resulting negative response gets cached across global resolvers. Subsequent queries fail silently for minutes or hours, even after the record is published to authoritative servers.

Understanding negative DNS responses requires analyzing wire format semantics, caching rules, and modern DNSSEC extensions. A failure to distinguish between a missing name (NXDOMAIN) and a missing type (NODATA) leads to subtle application issues. Furthermore, modern zone-signing implementations—such as Cloudflare’s online signers—introduce synthetic responses like Compact Denial of Existence (RFC 9824), altering traditional wire characteristics and breaking legacy monitoring metrics.

This chapter walks through the wire-level details of negative answers, exploring RFC 2308 negative caching mechanics, resolver TTL caps, empty non-terminals, RFC 8020 (“NXDOMAIN: There Really Is Nothing Underneath”), RFC 9520 resolution failure caching, and DNSSEC compact denial.

Learning goals

  • Differentiate wire responses for NXDOMAIN (RCODE 3) versus NODATA (NOERROR with empty answer section and SOA in authority).
  • Analyze Empty Non-Terminals (ENTs) and explain why querying an intermediate node returns NODATA rather than NXDOMAIN.
  • Trace RFC 2308 negative TTL calculation using min(SOA TTL, SOA MINIMUM) and observe resolver TTL countdowns in practice.
  • Diagnose the “record added after a miss” failure mode and evaluate mitigation strategies across Unbound, BIND, and systemd-resolved.
  • Evaluate RFC 8020 (harden-below-nxdomain) tree pruning and explain why resolvers restrict this optimization to DNSSEC-validated signals.
  • Measure RFC 9520 resolution failure caching to understand how resolvers protect authoritative targets during outages.
  • Identify DNSSEC negative evidence paradigms (NSEC range proofs, NSEC3 hashed ranges, RFC 9824 compact denial with type 128 NXNAME) from wire-level JSON and dig output.

Wire Semantics of Non-Existence: NXDOMAIN vs NODATA

A DNS server communicates non-existence in two fundamental ways: telling the client that the queried domain name does not exist at all, or telling the client that the name exists but holds no records of the requested type.

NXDOMAIN (Name Error)

When an authoritative DNS server receives a query for a name that has no Resource Records (RRs) and is not an ancestor of any existing name, it returns a response with the Header Response Code set to NXDOMAIN (RCODE 3).

+-------------------------------------------------------------------+
| HEADER: RCODE = 3 (NXDOMAIN), ANCOUNT = 0, NSCOUNT = 1            |
+-------------------------------------------------------------------+
| QUESTION SECTION:                                                 |
|   nope.lab.test.                IN    A                           |
+-------------------------------------------------------------------+
| ANSWER SECTION: (empty)                                           |
+-------------------------------------------------------------------+
| AUTHORITY SECTION:                                                |
|   lab.test.   4   IN   SOA   ns1.lab.test. hostmaster.lab.test. ...|
+-------------------------------------------------------------------+

Key characteristics of an NXDOMAIN response: 1. RCODE: Set to 3 (NXDOMAIN). 2. Answer Section: Empty (ANCOUNT = 0). 3. Authority Section: Contains the zone’s Start of Authority (SOA) record (NSCOUNT = 1). 4. Scope: An NXDOMAIN response applies to the entire name. If nope.lab.test returns NXDOMAIN for an A query, it guarantees that no AAAA, TXT, MX, or any other record type exists at nope.lab.test.

NODATA (Empty Answer)

When a name exists in the zone but does not possess the specific type requested by the query, the server returns a NODATA response. Note that NODATA is an operational state, not an explicit protocol RCODE.

+-------------------------------------------------------------------+
| HEADER: RCODE = 0 (NOERROR), ANCOUNT = 0, NSCOUNT = 1             |
+-------------------------------------------------------------------+
| QUESTION SECTION:                                                 |
|   mail.lab.test.                IN    A                           |
+-------------------------------------------------------------------+
| ANSWER SECTION: (empty)                                           |
+-------------------------------------------------------------------+
| AUTHORITY SECTION:                                                |
|   lab.test.   4   IN   SOA   ns1.lab.test. hostmaster.lab.test. ...|
+-------------------------------------------------------------------+

Key characteristics of a NODATA response: 1. RCODE: Set to 0 (NOERROR). 2. Answer Section: Empty (ANCOUNT = 0). 3. Authority Section: Contains the zone’s SOA record. 4. Scope: A NODATA response applies only to the specific type requested. If mail.lab.test returns NODATA for type A, the name itself exists (for instance, holding an MX record).

Property NXDOMAIN NODATA
Wire RCODE 3 (NXDOMAIN) 0 (NOERROR)
Answer Count 0 0
Authority Section Zone SOA Record Zone SOA Record
Meaning Name does not exist for any record type Name exists, but requested type does not
Caching Scope Caches non-existence of entire name Caches non-existence of (name, type) tuple
Subtree Impact Implies no records exist below this name Subtree below name may contain active records

Empty Non-Terminals (ENTs)

DNS domain names exist within a hierarchical tree structure. An Empty Non-Terminal (ENT) is a domain name that has no resource records of its own, but has domain names beneath it that do contain resource records.

Consider a zone file with a single record at x.b.lab.test:

x.b.lab.test.  30  IN  A  192.0.2.20

Because x.b.lab.test exists, the domain tree implicitly contains the parent nodes b.lab.test and lab.test. Even if no records (such as A, TXT, or MX) are assigned directly to b.lab.test, the name exists in the domain hierarchy.

       lab.test. (Zone Apex)
           |
        b.lab.test (Empty Non-Terminal: NOERROR / NODATA)
           |
       x.b.lab.test (Record present: 192.0.2.20)

If a client queries b.lab.test A, the server cannot return NXDOMAIN, because b.lab.test exists as an ancestor to x.b.lab.test. Returning NXDOMAIN would assert that the entire sub-tree under b.lab.test is non-existent. Therefore, the server MUST return NOERROR with an empty answer section (NODATA).

RFC 2308: Negative Caching Mechanics

Before RFC 2308, caching resolvers handled negative responses inconsistently, often leading to query floods against root and authoritative servers. RFC 2308 standardized how resolvers cache NXDOMAIN and NODATA responses.

The Negative TTL Calculation

When an authoritative server constructs a negative response (NXDOMAIN or NODATA), it attaches its SOA record in the Authority section. The standard RFC 883/1035 format for an SOA record contains seven fields:

MNAME RNAME SERIAL REFRESH RETRY EXPIRE MINIMUM

RFC 2308 repurposed the seventh field—historically named MINIMUM—to mean the Default Negative Caching TTL.

RFC 2308 section 5 puts the calculation on the authoritative side: the server sets the TTL of the SOA copy it places in the authority section to the lower of the SOA’s own TTL and the MINIMUM field. The resolver caches the negative answer for that TTL and counts it down like any other:

\[\text{Negative TTL} = \min(\text{SOA Record TTL}, \text{SOA MINIMUM field})\]

+------------------------------------------------------------------+
| Authoritative Response                                           |
| SOA Record TTL = 3600s                                           |
| SOA MINIMUM    = 300s                                            |
+------------------------------------------------------------------+
                                 |
                                 v
          Authoritative sends the SOA in AUTHORITY with
               TTL = min(3600, 300) = 300 seconds
                                 |
                                 v
+------------------------------------------------------------------+
| Resolver Cache Entry                                             |
| Key: nope.lab.test (NXDOMAIN)                                    |
| Expires in: 300 seconds                                          |
+------------------------------------------------------------------+

If the SOA record itself has a TTL of 3600 seconds, but the SOA MINIMUM field is set to 4 seconds, the cached negative response expires in 4 seconds.

Caching Scope Differences

The scope of a cached negative response depends on whether it is an NXDOMAIN or a NODATA answer:

  1. NXDOMAIN Caching: Cached per domain name. If a query for ghost.lab.test A returns NXDOMAIN, the resolver caches the non-existence of ghost.lab.test. Subsequent queries for ghost.lab.test MX, ghost.lab.test TXT, or ghost.lab.test AAAA during the negative TTL window are answered locally with NXDOMAIN without querying the authoritative server.
  2. NODATA Caching: Cached per (name, type) tuple. If a query for mail.lab.test A returns NODATA, the resolver caches that mail.lab.test has no A record. However, if the client immediately queries mail.lab.test MX, the resolver MUST query the authoritative server, because other types may exist at that name.

The “Record Added After a Miss” Problem

A frequent operational failure mode occurs when deploying new endpoints or services:

  1. An engineer or deployment script attempts to connect to new.lab.test.
  2. The client performs a DNS lookup for new.lab.test A.
  3. The authoritative server has not yet received the new record (or propagation is pending). It returns NXDOMAIN with a 3600-second negative TTL.
  4. The resolver caches this NXDOMAIN response for 3600 seconds.
  5. The engineer publishes the new.lab.test A -> 192.0.2.30 record to the authoritative server 10 seconds later.
  6. For the remaining 3590 seconds, all client queries routed through that resolver continue to receive the cached NXDOMAIN response.

Mitigation Strategies

To reduce the impact of negative cache pinning:

  1. Query Avoidance: Do not test or poll domain names before automation completes record creation.
  2. Low SOA MINIMUM: Set the zone SOA MINIMUM field to a small value (e.g., 5 to 60 seconds) for zones with frequent record updates.
  3. Resolver TTL Capping: Configure recursive resolvers to cap the maximum negative TTL (cache-max-negative-ttl in Unbound, max-ncache-ttl in BIND).
  4. Targeted Cache Flushing: Execute targeted cache clear operations on recursive resolvers when records are updated (unbound-control flush_negative, rndc flushname).

Resolver Negative TTL Caps

Recursive resolvers do not blindly trust arbitrarily high negative TTL values provided by authoritative servers. To protect against long-lasting negative cache poisoning or configuration errors, modern resolvers enforce strict upper caps on negative caching.

Unbound defaults cache-max-negative-ttl to 3600 seconds (1 hour), overriding higher authoritative TTL values. Operators can lower this parameter for environments with dynamic record provisioning:

# Unbound resolver configuration snippet
server:
    cache-max-negative-ttl: 60
    cache-min-negative-ttl: 5

BIND 9 defaults max-ncache-ttl to 10800 seconds (3 hours):

# BIND 9 named.conf configuration snippet
options {
    max-ncache-ttl 60;
};

When a resolver applies an upper cap, the negative TTL is calculated as:

\[\text{Effective Cache TTL} = \min(\text{SOA Record TTL}, \text{SOA MINIMUM}, \text{Resolver Max Negative TTL})\]

If an authoritative server returns an SOA MINIMUM of 86400 seconds (24 hours), but the resolver is configured with a maximum negative TTL of 60 seconds, the resolver discards the negative cache entry after 60 seconds.

RFC 8020: “NXDOMAIN: There Really Is Nothing Underneath”

Historically, recursive resolvers treated NXDOMAIN strictly on a per-query basis. If a resolver cached an NXDOMAIN for gone.lab.test, and a client subsequently queried a.gone.lab.test, old resolvers would send a new query upstream for a.gone.lab.test.

RFC 8020 (“NXDOMAIN: There Really Is Nothing Underneath”) states that an NXDOMAIN denies the name and every name below it. A resolver that caches an NXDOMAIN for gone.lab.test SHOULD treat all names at or below it as non-existent and answer later queries for them from the cache. The RFC uses SHOULD, not MUST, precisely because of broken servers like the one in lab section 5.

Subtree Pruning Semantics

Under RFC 8020, a cached NXDOMAIN for gone.lab.test allows the resolver to synthesize NXDOMAIN responses for: - a.gone.lab.test - deep.a.gone.lab.test - any.sub.domain.gone.lab.test

This optimization prevents query leaks to authoritative servers for invalid subdomains beneath a known non-existent node.

Cached: gone.lab.test -> NXDOMAIN
           |
   ---------------------------------
   |                               |
a.gone.lab.test             deep.a.gone.lab.test
(Synthesized NXDOMAIN)      (Synthesized NXDOMAIN)
[No Upstream Query Sent]    [No Upstream Query Sent]

The Legacy Server Problem & DNSSEC Requirement

RFC 8020 relies on authoritative servers correctly implementing Empty Non-Terminals. However, non-compliant or legacy authoritative DNS implementations historically returned NXDOMAIN when queried for an ENT (such as b.lab.test), even though a child record (x.b.lab.test) existed.

If a resolver blindly applied RFC 8020 to such a broken server: 1. Client queries b.lab.test A. 2. Broken server incorrectly returns NXDOMAIN (instead of NOERROR / NODATA). 3. Resolver caches NXDOMAIN for b.lab.test. 4. Client queries x.b.lab.test A. 5. Resolver applies RFC 8020, synthesizes NXDOMAIN for x.b.lab.test, and blocks access to a record that actually exists!

Because of this risk, Unbound’s harden-below-nxdomain (default yes) is applied only to DNSSEC-secure NXDOMAINs; its manual explains that the old software which returns NXDOMAIN for empty non-terminals does not do DNSSEC. A signed NXDOMAIN comes with NSEC or NSEC3 proof that was generated from the real zone contents, so an empty non-terminal cannot be denied by accident.

Caching Resolution Failures (RFC 9520)

NXDOMAIN and NODATA describe responses where an authoritative server was successfully reached and returned a valid DNS message. A different class of failures occurs when the resolver cannot obtain a response due to network timeouts, server crashes, unreachable IP addresses, or misconfigured glue records.

RFC 9520 (“Negative Caching of DNS Resolution Failures”, December 2023) requires resolvers to cache resolution failures: timeouts, unreachable servers, and DNSSEC validation failures.

Failure Cache Rules

  1. Minimum Duration: Resolvers MUST cache resolution failures for at least 1 second.
  2. Maximum Duration: Resolvers MUST NOT cache resolution failures for longer than 5 minutes (300 seconds).
  3. Protection Objective: Without failure caching, an application launching dozens of concurrent threads querying a failing domain will cause the recursive resolver to launch an upstream query burst, amplifying Denial of Service (DoS) traffic against authoritative infrastructure.
Client Burst (10 Queries)       Resolver                     Failing Upstream

    |-- Query 1 ------------------>|-- Upstream Query 1 ----------->|
    |                              |   (Timeout: 300ms)             |

    |<- SERVFAIL ------------------|                                |

DNSSEC Denial of Existence Dynamics

In an unsigned zone, an authoritative server returns plain NXDOMAIN or NODATA text blocks. An attacker in the network path could forge these responses to block communication. DNSSEC prevents forgery by providing cryptographic proofs of non-existence.

NSEC (RFC 4035)

Next Secure (NSEC) records prove non-existence by linking existing records in alphabetical order like a canonical linked list.

If a zone contains records for a.example and c.example, the NSEC record for a.example states: > “The next name in this zone is c.example. Between a.example and c.example, no names exist.”

[ Record: a.example ] ------ NSEC ------> [ Record: c.example ]
        |                                       |
        +--- Proves non-existence of b.example -+

When a client queries b.example, the server returns NXDOMAIN with the signed NSEC record owned by a.example, proving that b.example does not exist, plus a second NSEC proving there is no wildcard (*.example) that could have synthesised an answer. Each NSEC also carries a type bitmap listing the types that do exist at its owner name.

NSEC3 (RFC 5155)

Because plain NSEC records allow an attacker to traverse (“walk”) an entire zone by following the chain of next-names, RFC 5155 introduced NSEC3.

NSEC3 hashes domain names (using salted SHA-1) before sorting them:

[ Hash(a.example): 5JH0... ] --- NSEC3 ---> [ Hash(c.example): GTB1... ]

An NSEC3 denial of existence response provides signed hashes proving that no domain name in the zone hashes to a value between 5JH0... and GTB1.... RFC 9276 provides operational guidance to set iteration counts to zero and avoid custom salt strings to minimize CPU overhead on resolvers.

RFC 8198: Aggressive Use of DNSSEC-Validated Cache

Because NSEC and NSEC3 records cover ranges of non-existent names, a validating resolver with RFC 8198 support can synthesise NXDOMAIN for names it has never asked about. Once it holds a validated NSEC saying “after m.example the next name is p.example” (and the wildcard proof), a query for n.example or o.example is answered from the cache. This is a strong defence against random-subdomain floods, and it only works for zones that publish real ranges; compact denial (below) deliberately gives none.

RFC 9824: Compact Denial of Existence (“Black Lies”)

Offline-signed zones carry a pre-computed NSEC or NSEC3 chain. Online signers, which sign answers as they are generated, cannot keep such a chain for zones that change constantly. Earlier schemes (“white lies”, RFC 4470) generated minimally covering NSEC records around the queried name, but still needed two of them for an NXDOMAIN.

RFC 9824 formalizes Compact Denial of Existence (historically termed “Black Lies”).

Compact denial answers a query for a non-existent name as if the name existed with no data for the queried type: NOERROR, empty answer, and one NSEC owned by the queried name whose next name is the name with a \000 label prepended (the immediate successor in canonical order). One signature per answer, no zone contents disclosed.

Query: no-such-name-0625.ietf.org A

Response:
Header: RCODE = 0 (NOERROR)
Answer: (empty)
Authority:
  no-such-name-0625.ietf.org. 1800 IN NSEC \000.no-such-name-0625.ietf.org. RRSIG NSEC NXNAME
Traditional NSEC (Range Proof)           Compact Denial (RFC 9824)
------------------------------           -------------------------
RCODE: 3 (NXDOMAIN)                      RCODE: 0 (NOERROR)
Proves: Nothing exists between           Proves: Name exists, but requested
        NameA and NameB                          type is missing
Uses:   Pre-signed static chains         Uses:   On-the-fly dynamically
                                                 generated NSEC records

The Wire Mechanism of Compact Denial

  1. RCODE manipulation: The server returns RCODE 0 (NOERROR) instead of RCODE 3 (NXDOMAIN).
  2. Synthetic NSEC record: owned by the queried name, with next name \000.<queried name>, so it covers nothing but the name itself.
  3. The NXNAME Signal: The NSEC type bitmap contains a special assignment: type 128 (NXNAME).

The presence of NXNAME (type 128) in the NSEC bitmap signals to a DNSSEC-aware resolver that the host name does not actually exist, despite the NOERROR RCODE in the response header.

Operational Consequences

  • Dashboard and Metric Skew: Monitoring systems or SIEM tools that count NXDOMAIN events by parsing DNS header RCODEs will completely undercount non-existent domain queries for zones using compact denial. These queries appear in network logs as NOERROR.
  • RFC 8020 Breakdown: Resolvers that do not implement RFC 9824 cannot apply RFC 8020 subtree pruning to compact denial zones, because the header carries RCODE 0 (NOERROR) rather than NXDOMAIN.
  • Restoring NXDOMAIN with EDNS: RFC 9824 section 5.1 defines the Compact Answers OK (CO) flag, the second bit of the EDNS flags field. A resolver that sets it tells the server it understands NXNAME; a supporting server then sets RCODE 3 on such answers while keeping the compact proof. Without CO the RCODE stays NOERROR. A validating resolver may also restore NXDOMAIN itself for downstream clients that did not set DO.
  • No range, no aggressive caching: a compact proof covers only the queried name, so RFC 8198 synthesis gains nothing from it. Random-subdomain floods against such zones always reach the online signer.

wire.py:

"""Minimal DNS wire format helpers (RFC 1035), enough for A, MX, SOA, TXT."""
import struct
TYPES = {"A": 1, "NS": 2, "SOA": 6, "MX": 15, "TXT": 16, "AAAA": 28}
NAMES = {v: k for k, v in TYPES.items()}
RCODES = {0: "NOERROR", 2: "SERVFAIL", 3: "NXDOMAIN"}

def enc_name(n):
    out = b""
    for label in n.rstrip(".").split("."):
        if label:
            out += bytes([len(label)]) + label.encode()
    return out + b"\0"

def dec_name(buf, off):
    labels, jumped, end = [], False, None
    while True:
        ln = buf[off]
        if ln & 0xC0 == 0xC0:
            if not jumped:
                end = off + 2
            off, jumped = struct.unpack("!H", buf[off:off + 2])[0] & 0x3FFF, True
            continue
        off += 1
        if ln == 0:
            break
        labels.append(buf[off:off + ln].decode()); off += ln
    return ".".join(labels).lower() + ".", (end if jumped else off)

def query(qid, name, qtype):
    return struct.pack("!HHHHHH", qid, 0x0100, 1, 0, 0, 0) + enc_name(name) + struct.pack("!HH", TYPES[qtype], 1)

def rr(name, rtype, ttl, rdata):
    return enc_name(name) + struct.pack("!HHIH", TYPES[rtype], 1, ttl, len(rdata)) + rdata

def rdata(rtype, value):
    if rtype == "A":
        return bytes(int(x) for x in value.split("."))
    if rtype == "NS":
        return enc_name(value)
    if rtype == "MX":
        pref, host = value.split(); return struct.pack("!H", int(pref)) + enc_name(host)
    if rtype == "SOA":
        m, r, *nums = value.split(); return enc_name(m) + enc_name(r) + struct.pack("!IIIII", *map(int, nums))
    if rtype == "TXT":
        return bytes([len(value)]) + value.encode()
    raise ValueError(rtype)

def response(qid, qname, qtype, rcode, answers=(), authority=(), ra=False):
    flags = 0x8400 | (0x0080 if ra else 0) | rcode       # QR, AA (RA when a resolver answers)
    if ra:
        flags &= ~0x0400                                  # resolvers do not set AA
    return (struct.pack("!HHHHHH", qid, flags, 1, len(answers), len(authority), 0)
            + enc_name(qname) + struct.pack("!HH", TYPES[qtype], 1) + b"".join(answers) + b"".join(authority))

def parse(buf):
    qid, flags, qd, an, ns, ar = struct.unpack("!HHHHHH", buf[:12])
    off = 12; qname, off = dec_name(buf, off); qtype = struct.unpack("!H", buf[off:off + 2])[0]; off += 4
    secs = []
    for count in (an, ns):
        sec = []
        for _ in range(count):
            name, off = dec_name(buf, off)
            t, _c, ttl, rdlen = struct.unpack("!HHIH", buf[off:off + 10]); off += 10
            rd = buf[off:off + rdlen]
            if t == 6:
                _m, o = dec_name(buf, off); _r, o = dec_name(buf, o)
                val = struct.unpack("!IIIII", buf[o:o + 20])      # serial refresh retry expire minimum
            elif t == 1:
                val = ".".join(map(str, rd))
            elif t == 15:
                val = f"{struct.unpack('!H', rd[:2])[0]} {dec_name(buf, off + 2)[0]}"
            else:
                val = rd.hex()
            off += rdlen
            sec.append((name, NAMES.get(t, t), ttl, val))
        secs.append(sec)
    return {"id": qid, "rcode": flags & 0xF, "aa": bool(flags & 0x0400), "qname": qname,
            "qtype": NAMES.get(qtype, qtype), "answer": secs[0], "authority": secs[1]}

"""Toy authoritative server for lab.test. Re-reads zone.txt on every query.
usage: auth.py PORT [--broken-ent]   (--broken-ent: answer NXDOMAIN for empty non-terminals, like very old servers)"""
import socket, sys
from wire import parse, response, rr, rdata
ZONE = "lab.test."
def load():
    recs = []
    for line in open("zone.txt"):
        if line.strip() and not line.startswith(";"):
            name, ttl, rtype, value = line.split(None, 3)
            recs.append((name.lower(), int(ttl), rtype, value.strip()))
    return recs
def main():
    port, broken = int(sys.argv[1]), "--broken-ent" in sys.argv
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.bind(("127.0.0.1", port))
    while True:
        buf, peer = s.recvfrom(512); q = parse(buf); name, qt = q["qname"], q["qtype"]
        recs = load()
        soa = next(r for r in recs if r[2] == "SOA")
        neg_ttl = min(soa[1], int(soa[3].split()[-1]))          # RFC 2308 section 5
        soa_rr = rr(ZONE, "SOA", neg_ttl, rdata("SOA", soa[3]))
        exact = [r for r in recs if r[0] == name]
        below = [r for r in recs if r[0].endswith("." + name)]
        hits = [rr(r[0], r[2], r[1], rdata(r[2], r[3])) for r in exact if r[2] == qt]
        if hits:
            out = response(q["id"], name, qt, 0, hits)
        elif exact or (below and not broken):
            out = response(q["id"], name, qt, 0, authority=[soa_rr])      # NODATA
        else:
            out = response(q["id"], name, qt, 3, authority=[soa_rr])      # NXDOMAIN
        s.sendto(out, peer)
main()

resolver.py:

"""Toy caching resolver in front of one authoritative server (no delegation walk).
usage: resolver.py PORT UPSTREAM_PORT [--rfc8020] [--neg-max N] [--fail-cache S]
Prints one line per upstream query so the lab can count them."""
import socket, sys, time
from wire import parse, query, response, rr, rdata, TYPES
args = sys.argv[1:]
port, up = int(args[0]), int(args[1])
rfc8020 = "--rfc8020" in args
neg_max = int(args[args.index("--neg-max") + 1]) if "--neg-max" in args else 3600
fail_cache = float(args[args.index("--fail-cache") + 1]) if "--fail-cache" in args else 0
T0 = time.monotonic()
pos, nodata, nxdomain, failed = {}, {}, {}, {}   # key -> (expiry, payload)
def now(): return time.monotonic()
def log(msg): print(f"  [resolver t={now() - T0:5.1f}s] {msg}", flush=True)
def soa_rr(soa, ttl):
    return rr(soa[0], "SOA", ttl, rdata("SOA", "ns.lab.test. hostmaster.lab.test. " + " ".join(map(str, soa[3]))))
def lookup_cache(name, qt):
    t = now()
    if (name, qt) in pos and pos[(name, qt)][0] > t:
        exp, rrs = pos[(name, qt)]; return 0, [rr(n, ty, int(exp - t), rdata(ty, v)) for n, ty, v in rrs], []
    cands = [name] + ([name.split(".", k)[-1] for k in range(1, name.count(".") - 1)] if rfc8020 else [])
    for c in cands:                                   # RFC 8020: an NXDOMAIN ancestor covers the subtree
        if c in nxdomain and nxdomain[c][0] > t:
            exp, soa = nxdomain[c]; return 3, [], [soa_rr(soa, int(exp - t))]
    if (name, qt) in nodata and nodata[(name, qt)][0] > t:
        exp, soa = nodata[(name, qt)]; return 0, [], [soa_rr(soa, int(exp - t))]
    if (name, qt) in failed and failed[(name, qt)] > t:
        return 2, [], []
    return None
def ask(name, qt):
    u = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); u.settimeout(0.3)
    u.sendto(query(7, name, qt), ("127.0.0.1", up))
    try:
        r = parse(u.recvfrom(4096)[0])
    except socket.timeout:
        log(f"upstream {name} {qt} -> timeout"); return None
    t = now()
    if r["answer"]:
        ttl = min(a[2] for a in r["answer"])
        pos[(name, qt)] = (t + ttl, [(a[0], a[1], a[3]) for a in r["answer"]])
    elif r["authority"]:
        soa = r["authority"][0]; ttl = min(soa[2], neg_max)
        (nxdomain.__setitem__(name, (t + ttl, soa)) if r["rcode"] == 3 else nodata.__setitem__((name, qt), (t + ttl, soa)))
    if r["answer"]:
        what = "NOERROR"
    else:
        what = ("NXDOMAIN" if r["rcode"] == 3 else "NOERROR (NODATA)") + f", negative TTL {min(r['authority'][0][2], neg_max)}s"
    log(f"upstream {name} {qt} -> {what}")
    return r
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); s.bind(("127.0.0.1", port))
while True:
    buf, peer = s.recvfrom(512); q = parse(buf); name, qt = q["qname"], q["qtype"]
    hit = lookup_cache(name, qt)
    if hit is None:
        r = ask(name, qt)
        if r is None:
            if fail_cache:
                failed[(name, qt)] = now() + fail_cache
            hit = (2, [], [])
        else:
            hit = lookup_cache(name, qt) or (r["rcode"], [], [])
    s.sendto(response(q["id"], name, qt, hit[0], hit[1], hit[2], ra=True), peer)

Gotchas

  • NODATA for one type says nothing about the others: an empty AAAA answer is cached for AAAA only. Applications that treat “no AAAA” as “host unknown” (instead of falling back to A) turn a normal IPv4-only name into an outage.
  • SOA MINIMUM field repurposing: The last number in an SOA record is NOT the minimum TTL for positive records; RFC 2308 explicitly redefined it as the negative caching TTL limit.
  • Public anycast TTL skew: Consecutive queries to public recursive resolvers (1.1.1.1, 8.8.8.8) often land on different edge nodes, making TTL countdown values appear non-sequential or static.
  • ENTs break RFC 8020 on legacy auth servers: Misconfigured authoritative servers that return NXDOMAIN for Empty Non-Terminals cause RFC 8020-compliant resolvers to mistakenly block valid downstream child names.
  • Compact Denial masks NXDOMAIN in dashboards: RFC 9824 zones respond with RCODE 0 (NOERROR). Security dashboards filtering strictly for RCODE 3 will undercount missing domain lookups.
  • DNSSEC validation is required for aggressive caching: RFC 8198 synthesis needs validated NSEC/NSEC3, and Unbound applies RFC 8020 only to DNSSEC-secure NXDOMAINs.
  • A failing authoritative server is a load problem for everyone: without RFC 9520 failure caching every client retry becomes an upstream query (lab section 7). Check that your resolver caches SERVFAIL and how long.
  • Short SOA MINIMUM increases authoritative load: Reducing SOA MINIMUM to extremely low values (e.g., 1s) mitigates cache pinning, but significantly increases query volume against authoritative DNS servers during miss storms.
