network-xray: see why BGP picked that path in containerlab

After reading this chapter, you can run network-xray alongside Containerlab or Netlab to inspect BGP path selection decisions and routing state directly in your web browser.

Understanding why a router selected one BGP path over competing candidates usually requires manually logging into individual nodes, executing multiple diagnostic show commands, and evaluating path attributes step-by-step against standard decision rules. network-xray automates this process by polling live router state from FRRouting (FRR), Nokia SR Linux, and Cisco IOL nodes running inside Containerlab or Netlab, visualizing topology links and path selection logic in real time.

Architectural Overview

network-xray functions as a read-only live-state visualizer. It operates as a local HTTP server that reads container metadata and topology structures from Containerlab or Netlab, issues standard diagnostic show commands to participating router instances, and renders the compiled state in an interactive web interface.

  +-------------------------------------------------------------------+
  |                           Browser UI                              |
  |             http://127.0.0.1:8600/ (or recorded demo)             |
  +-------------------------------------------------------------------+
                                    ^
                                    | HTTP / Web Sockets
                                    v
  +-------------------------------------------------------------------+
  |                       network-xray container                      |
  |      Reads clab topology & polls routers via show commands        |
  +-------------------------------------------------------------------+
             |                                           |
             | /var/run/docker.sock                      | CLI Execution
             v                                           v
  +-----------------------+                 +-------------------------+
  |  Docker Engine Host   |                 | Containerlab Router     |
  |  (Reads container ID) |                 | Nodes (FRR, SRL, IOL)   |
  +-----------------------+                 +-------------------------+

Rather than modifying routing engine logic or inserting proprietary telemetry agents, network-xray uses non-disruptive inspection. It queries nodes for control-plane data—such as show bgp detail or show ip ospf neighbor—and parses the raw text or JSON outputs into structured graph visualizers.

Supported Routing Platforms and Protocols

network-xray supports live state visual extraction for three main network operating systems running within Containerlab environments:

Operating System Supported Protocols Inspection Mechanism
FRRouting (FRR) BGP (IPv4/IPv6), OSPF vtysh -c 'show ...' queries
Nokia SR Linux BGP, OSPF sr_cli JSON state queries
Cisco IOL BGP, OSPF Standard CLI show outputs

The tool captures key control-plane characteristics, including: - BGP Best-Path Decision logic: Highlighting why a specific prefix candidate won (e.g., Local Preference, AS-Path length, Origin, MED, eBGP vs. iBGP, IGP metric, or Router ID). - OSPF Adjacency states: Real-time inspection of neighbor states (e.g., Full, 2-Way, Init) across active topology interfaces.

Running network-xray with Containerlab

Note

Not run here. Running network-xray requires access to a local Docker daemon and a running Containerlab environment. Because this environment does not run containerlab or host a Docker socket, execution steps below illustrate local workstation commands.

To launch network-xray alongside a running Containerlab topology, execute the official Docker container inside your lab directory.

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$(pwd)":/lab:ro -p 127.0.0.1:8600:8600 ghcr.io/rclab-dev/network-xray:1 --topo /lab/topology.clab.yml
Note

Security note from upstream: Mounting /var/run/docker.sock gives the container root-equivalent privileges on the host system. network-xray requires read access to execute docker exec commands into running lab nodes. Run network-xray only on isolated development workstations or dedicated lab machines.

Image Pinning and Security Digest

In production automation or stable testing environments, pin the container image using its exact SHA256 digest rather than a floating tag like :1. Refer to the upstream release page to obtain the exact digest string:

docker run --rm -v /var/run/docker.sock:/var/run/docker.sock -v "$(pwd)":/lab:ro -p 127.0.0.1:8600:8600 ghcr.io/rclab-dev/network-xray@sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855 --topo /lab/topology.clab.yml

Once launched, navigate to http://127.0.0.1:8600/ in a browser to interact with the topology graph and route decision panels.

Integration with Netlab

Netlab allows declarative lab deployment across multiple virtualization drivers. network-xray can be integrated directly into Netlab configurations using standard tool definitions.

To enable network-xray within Netlab, declare the tool inside your topology file (topology.yml) and reference the extra defaults loader provided by the tool package:

---
provider: clab
defaults.device: frr
defaults.sources.extra:
  - docker/netlab-defaults.yml

module: [ bgp, ospf ]

nodes:
  r1:
    bgp.as: 65001
  r2:
    bgp.as: 65002
  r3:
    bgp.as: 65003

links:
  - r1:
    r2:
  - r1:
    r3:

tools:
  network_xray:

When you start the lab environment via netlab up, Netlab parses the network_xray tool declaration, loads the configuration from docker/netlab-defaults.yml, and automatically starts the visualizer container attached to the lab topology.

Example Scenario: Live BGP Best-Path Decision Tracking

Consider a standard dual-homed topology where router r1 receives updates for prefix 8.8.8.0/24 from two separate upstream peers: r2 (via Local Preference 100) and r3 (via Local Preference 100 default).

Diagnostic Script for State Verification

To verify that FRR state changes dynamically when attributes are altered, the following script modifies Local Preference on r1 for updates arriving from r3, causing the best path selection to change without tearing down the underlying session.

import subprocess
import time


def exec_vtysh(node: str, command: str) -> str:
    """Execute a vtysh command inside a container host."""
    cmd = ["docker", "exec", node, "vtysh", "-c", command]
    result = subprocess.run(cmd, capture_output=True, text=True, check=True)
    return result.stdout


def main():
    node = "clab-bgp-demo-r1"

    print("Checking initial BGP route table for 8.8.8.0/24...")
    output_before = exec_vtysh(node, "show ip bgp 8.8.8.0/24")
    print(output_before)

    print("Updating Local Preference for peer r3 (10.0.13.3) to 150...")
    config_cmds = (
        "configure terminal\n"
        "route-map SET_LP_150 permit 10\n"
        " set local-preference 150\n"
        "exit\n"
        "router bgp 65001\n"
        " neighbor 10.0.13.3 route-map SET_LP_150 in\n"
        "end\n"
        "clear ip bgp 10.0.13.3 soft in\n"
    )
    exec_vtysh(node, config_cmds)

    time.sleep(2)

    print("Checking updated BGP route table for 8.8.8.0/24...")
    output_after = exec_vtysh(node, "show ip bgp 8.8.8.0/24")
    print(output_after)


if __name__ == "__main__":
    main()

Run the script to execute the Local Preference change inside the lab node:

The following command runs the path modification test script:

<<OUTPUT:run1>>

Visualizing the Decision in network-xray

After changing the configuration: 1. Open the network-xray interface at http://localhost:8600/. 2. Click on router node r1 to view its routing state. 3. In the BGP inspection table, observe candidate entries for 8.8.8.0/24. 4. Check the Best-Path Decision panel. The UI highlights that the winner candidate changed from via r2 (LocPref 100) to via r3 (LocPref 150) due to Local Preference evaluation, reflecting FRR’s re-calculated state without requiring a full container restart.

Pitfalls

Mistake Consequence Remedy
Forgetting to mount /var/run/docker.sock network-xray cannot query container details or execute show commands Always include -v /var/run/docker.sock:/var/run/docker.sock in the docker run command
Specifying incorrect relative path to --topo file Container fails to load topology map Mount the current directory using -v "$(pwd)":/lab:ro and provide --topo /lab/<filename>.clab.yml
Running on public or un-sanitised host interfaces Exposing Docker host control socket to host networks Bind published port strictly to localhost using -p 127.0.0.1:8600:8600
Using floating latest image tags in persistent automation Unintended upstream container version drift Pin specific digest hashes using ghcr.io/rclab-dev/network-xray@sha256:<digest>

Summary

  • network-xray offers live, read-only visualization of BGP path selection and OSPF neighbor states in Containerlab and Netlab environments.
  • It parses diagnostic output from FRR, Nokia SR Linux, and Cisco IOL without requiring agent installation inside router nodes.
  • Execution requires Docker socket access to poll running container state.
  • Netlab integration can be configured declaratively via the tools: network_xray: section in topology.yml.
