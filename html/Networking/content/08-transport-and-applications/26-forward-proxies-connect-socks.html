Forward Proxies: HTTP CONNECT, SOCKS5 and the Proxy Environment Variables

For network operators and system engineers, forward proxies are a fundamental mechanism for controlling outbound traffic, enforcing security policies, and bridging distinct network segments. Unlike reverse proxies—which sit in front of servers to perform load balancing or SSL termination—forward proxies sit in front of clients. They act as intermediaries for requests directed to external origins, providing a central point where outbound traffic can be filtered, audited, logged, or authenticated.

Understanding client-side forward proxy behavior is essential for troubleshooting connectivity failures in enterprise networks, containerized environments, and CI/CD pipelines. When an application fails to connect to an external API, the root cause often traces back to subtle differences in how client HTTP libraries handle proxy environment variables, how domain name resolution is delegated, or how HTTP CONNECT tunnels interact with TLS handshakes. A misconfiguration can lead to security risks such as credential leaks over unencrypted proxy links or privacy breaches via DNS leaks.

This chapter covers the mechanisms of client-side forward proxies. We examine plain HTTP proxying using absolute-form URLs, transport-layer tunneling using the HTTP CONNECT method, and SOCKS protocol proxying. We also analyze the environment variables standard across Unix environments (http_proxy, https_proxy, no_proxy), detailing implementation differences between common clients like curl, Python’s standard urllib, and the requests library. Note that this chapter focuses exclusively on client-side forward proxies; server-side mechanisms such as the PROXY protocol (HAProxy headers passed from load balancers to backend servers) are out of scope.

Learning goals

  • Differentiate between plain HTTP proxying (absolute-form requests), HTTP CONNECT tunneling, and SOCKS4/5 proxying.
  • Explain how domain name resolution differs between local client resolution and proxy-side resolution across HTTP and SOCKS protocols.
  • Analyze the HTTP CONNECT method, including proxy port restriction ACLs and the visibility of TLS Server Name Indication (SNI) to intermediary proxies.
  • Evaluate security implications of proxy authentication headers (Proxy-Authorization) and transport security (http:// vs https:// proxy endpoints).
  • Identify and mitigate environment variable edge cases, including HTTP_PROXY security considerations (CGI/httpoxy) and implementation inconsistencies in NO_PROXY pattern matching.
  • Troubleshoot forward proxy connection failures using command-line diagnostic tools and standard logging patterns.

Absolute-Form HTTP Requests

When an HTTP client connects directly to an origin server, it opens a TCP connection to the origin’s IP address and issues an origin-form request:

GET /index.html HTTP/1.1
Host: origin.lab:8080

When configured to use an unencrypted HTTP forward proxy for HTTP traffic, the client opens a TCP connection to the proxy server instead of the origin server. The client then issues an absolute-form request containing the complete scheme, host, port, and path, as specified in RFC 9112 section 3.2.2:

GET http://origin.lab:8080/index.html HTTP/1.1
Host: origin.lab:8080

Upon receiving an absolute-form request, the proxy: 1. Performs DNS resolution for origin.lab if necessary. 2. Opens a TCP connection to origin.lab:8080. 3. Rewrites the request line to origin-form (GET /index.html HTTP/1.1). 4. Appends or updates the Via HTTP header field (RFC 9110 section 7.6.3) to track request routing and prevent loops (e.g., Via: 1.1 labproxy). 5. Forwards the request to the origin server.

Because the client sends the destination hostname in the absolute-form URI directly to the proxy, the client does not need to perform a local DNS query.

The HTTP CONNECT Method

Plain absolute-form HTTP proxying cannot handle TLS-encrypted traffic (https://) without breaking the end-to-end security model, as the proxy would need to read and rewrite HTTP headers in cleartext. To proxy encrypted traffic or arbitrary binary protocols, HTTP clients use the CONNECT method (RFC 9110 section 9.3.6).

The CONNECT process works as follows:

Client                         Proxy                         Origin
  |                              |                             |
  |--- CONNECT origin.lab:8443 ->|                             |
  |    HTTP/1.1                  |                             |
  |                              |--- TCP Connect ------------>|
  |                              |<-- Connected ---------------|
  |<-- HTTP/1.1 200 ------------ |                             |
  |    Connection Established    |                             |
  |                              |                             |
  |================ TLS Handshake / Ciphertext ===============|

  1. Tunnel Request: The client connects to the proxy and sends a CONNECT request using authority-form targeting the desired destination host and port:

    CONNECT origin.lab:8443 HTTP/1.1
Host: origin.lab:8443

  2. Proxy Setup: The proxy establishes a TCP connection to origin.lab on port 8443.

  3. Tunnel Confirmation: If the connection succeeds, the proxy returns an HTTP 2xx status code (typically 200 Connection Established).

  4. Opaque Data Transfer: From this point forward, the proxy stops parsing HTTP data. It functions as a bi-directional TCP stream relay, forwarding raw bytes back and forth between the client and origin.

SNI Visibility and ECH

Even though payload data within a CONNECT tunnel is encrypted via TLS, standard TLS 1.3 handshakes send the Server Name Indication (SNI) extension inside the ClientHello message in cleartext. An intermediary HTTP proxy parsing initial bytes after a CONNECT 200 response can inspect the ClientHello to extract the target SNI domain name (origin.lab). Encrypted Client Hello (ECH) encrypts the SNI payload, preventing the proxy from identifying the destination hostname beyond what was requested in the CONNECT target string.

Port Restriction ACLs

Because an unrestricted CONNECT proxy can be abused as an open TCP relay to attack internal network services (such as SSH, SMTP, or database ports), production proxies enforce strict access control lists (ACLs). For example, Squid proxies restrict CONNECT targets using rules like http_access deny CONNECT !SSL_ports, limiting connections to approved ports (typically 443). If a client issues a CONNECT request for an unauthorized port (such as port 22), the proxy rejects the request with an HTTP 403 Forbidden status line, and the client aborts with a tunnel failure error.

Once the tunnel is established, the origin server receives a standard TCP connection from the proxy’s IP address. The origin server cannot inspect the HTTP headers to determine if the connection passed through a CONNECT tunnel, because no Via or forwarding headers are injected into the encrypted TLS stream.

Proxy Authentication

Proxies can enforce authentication before forwarding traffic or establishing tunnels (RFC 9110 sections 11.7.1 and 11.7.2).

  1. Challenge: When an unauthenticated request reaches an authenticating proxy, the proxy responds with HTTP status 407 Proxy Authentication Required and includes a Proxy-Authenticate header specifying supported schemes (e.g., Basic realm="Proxy").
  2. Credentials: The client re-issues the request, adding a Proxy-Authorization header containing credentials (e.g., Proxy-Authorization: Basic bGFiOnNlY3JldA== for RFC 7617 HTTP Basic authentication).
  3. Consumed by the proxy: Proxy-Authorization is meant for the proxy that asked for it (RFC 9110 section 11.7.2). The proxy checks the credentials and does not pass them on; in the lab the origin’s header dump in scenario 5 contains no Proxy-Authorization.

Transport Security of Proxy Credentials

When contacting an HTTP proxy URL (http://proxy.lab:3128), proxy authentication headers are transmitted over an unencrypted TCP connection to the proxy. Anyone with network access to the path between client and proxy can capture these base64-encoded credentials.

To protect proxy credentials, modern environments use HTTPS proxies (https://proxy.lab:8443), where the client establishes a TLS session with the proxy server itself before transmitting HTTP commands or Proxy-Authorization headers. Support for secure HTTPS proxy endpoints was added in curl 7.52.0.

SOCKS Protocol and DNS Resolution (SOCKS5 vs SOCKS5h)

SOCKS (RFC 1928) operates at a lower networking layer than HTTP proxying, relaying raw TCP/UDP streams without interpreting application-layer protocols.

During a SOCKS5 handshake: 1. The client sends a version and authentication method selection message. 2. The proxy responds with the selected method (0x00 for no authentication, 0x02 for username/password as defined in RFC 1929). 3. The client sends a connection request specifying the Address Type (ATYP): - ATYP 0x01: IPv4 address (4 bytes) - ATYP 0x03: Domain name (1-byte length followed by domain string) - ATYP 0x04: IPv6 address (16 bytes)

Local vs Remote DNS Resolution

The distinction between socks5:// and socks5h:// in client configuration defines where DNS resolution occurs:

  • socks5:// (Local Resolution): The client resolves the origin domain name to an IP address using its local DNS resolver before communicating with the proxy. It then sends an ATYP 0x01 (IPv4) or ATYP 0x04 (IPv6) request to the SOCKS proxy.
    • Risk: If the destination domain is on an isolated internal network accessible only by the proxy, local resolution fails (returning NXDOMAIN). Additionally, sending local DNS queries for destination domains can cause DNS leaks, exposing intent to local network observers.
  • socks5h:// (Remote Resolution): The client defers domain resolution to the proxy by sending an ATYP 0x03 request containing the unresolved hostname string. The proxy resolves the name on its own network interface and establishes the TCP connection.

A similar distinction exists between socks4:// (IPv4 address only) and socks4a:// (supports domain strings).

Proxy Environment Variables

Command-line applications and standard software libraries rely on environment variables to configure proxy routing behavior dynamically:

  • http_proxy / HTTP_PROXY: Specifies the proxy server for plain HTTP requests.
  • https_proxy / HTTPS_PROXY: Specifies the proxy server for HTTPS requests (via CONNECT).
  • all_proxy / ALL_PROXY: Specifies a fallback proxy for all traffic schemes (commonly used for SOCKS proxies, e.g., socks5h://127.0.0.1:1080).
  • no_proxy / NO_PROXY: Specifies comma-separated patterns for hosts that must bypass the proxy and connect directly.

Lowercase vs Uppercase (httpoxy Security)

A security vulnerability known as httpoxy (CVE-2016-5385 family) affects Web server software running in CGI or CGI-like environments. In standard CGI specifications, incoming HTTP request headers are converted into environment variables prefixed with HTTP_. An attacker sending an HTTP header named Proxy: http://attacker.com causes the web server to set HTTP_PROXY=http://attacker.com within the execution context of the script.

If the underlying application library automatically reads HTTP_PROXY, outgoing HTTP requests made by the server application are hijacked and redirected to the attacker’s proxy.

To mitigate this risk: - curl: for plain HTTP it reads only lowercase http_proxy and ignores uppercase HTTP_PROXY, for exactly this reason. The other variables (HTTPS_PROXY, ALL_PROXY, NO_PROXY) are accepted in either case. - Python (urllib / requests): Reads uppercase HTTP_PROXY, but includes a runtime safety check: if the REQUEST_METHOD environment variable is present (indicating execution within a CGI process), Python ignores HTTP_PROXY.

NO_PROXY Implementation Inconsistencies

There is no formal RFC defining the syntax for no_proxy. As a result, parsing rules differ across HTTP implementations:

  • Suffix Matching: Most implementations perform suffix matching. A rule such as origin.lab matches origin.lab and subdomains such as www.origin.lab.
  • Leading Dots: Leading dots (e.g., .origin.lab) are supported across implementations to match subdomains, though behavior regarding the exact apex domain can vary.
  • Wildcards: The wildcard string * is supported as a global bypass flag by curl, urllib, and requests. However, partial domain wildcards such as *.origin.lab are not supported standard syntax in curl or standard Python libraries; they fail to match target hosts and result in requests being proxied.
  • IP Literals vs Hostnames: Matching is strictly string-based in most libraries. An entry of 127.0.0.10 in NO_PROXY bypasses the proxy when connecting to http://127.0.0.10:8080/, but does not bypass the proxy when connecting to http://origin.lab:8080/, even if origin.lab resolves to 127.0.0.10.
  • CIDR Block Support: CIDR notation (e.g., 127.0.0.0/8) is supported in curl (since version 7.86.0) and Python’s requests library (via urllib3), but is not supported by standard Python urllib.request.
  • Port Matching: Specifying host:port (e.g., origin.lab:8080) is supported in Python’s urllib and requests, but is unsupported in curl 8.14.1 (where port specifiers cause matching failures).

PAC Files and WPAD

In modern desktop operating systems and web browsers, proxy settings are often managed dynamically via Proxy Auto-Configuration (PAC) and Web Proxy Auto-Discovery Protocol (WPAD):

  • PAC Files: JavaScript files defining a function FindProxyForURL(url, host) that returns a string indicating which proxy to use (e.g., "PROXY proxy1.lab:3128; DIRECT").
  • WPAD Protocol: Discovers the PAC file URL automatically via DHCP Option 252 or local DNS queries targeting wpad.domain.lab.

Command-line utilities such as curl and standard runtime libraries for languages like Python, Go, and Rust do not embed JavaScript execution engines and do not process PAC files or perform WPAD resolution natively. Operating system settings relying on PAC/WPAD must be manually translated into static environment variables for command-line tool compatibility.

so we can see which names a client resolved itself."""
import socket, struct, sys

TABLE = {"origin.lab": "127.0.0.10", "www.origin.lab": "127.0.0.10"}   # intranet.lab is NOT here

while True:
    q, peer = s.recvfrom(512)
    qid, flags, qd = struct.unpack("!HHH", q[:6])
    i, labels = 12, []
    while q[i]:
        labels.append(q[i + 1:i + 1 + q[i]].decode()); i += 1 + q[i]
    qtype = struct.unpack("!H", q[i + 1:i + 3])[0]

    if name in TABLE and qtype == 1:
        ans = b"\xc0\x0c" + struct.pack("!HHIH", 1, 1, 60, 4) + socket.inet_aton(TABLE[name])

"""Origin web server on 127.0.0.10: HTTP on 8080, HTTPS on 8443 (cert for
origin.lab). Logs the request line and the headers that tell us how the
request arrived."""
import http.server, ssl, sys, threading

class H(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        seen = {k: self.headers.get(k) for k in ("Host", "Via", "Proxy-Authorization", "X-Forwarded-For") if self.headers.get(k)}
        self.server.log.write(f"origin:{self.server.server_port}: {self.requestline!r} from {self.client_address[0]} {seen}\n")
        body = (b"via-proxy" if self.headers.get("Via") else b"direct") + b"\n"
        self.send_response(200); self.send_header("Content-Length", str(len(body))); self.end_headers()
        self.wfile.write(body)
    def log_message(self, *a):
        pass

#!/usr/bin/env python3
"""A small forward proxy that logs what it is told.

127.0.0.20:3128  HTTP proxy: absolute-form requests and CONNECT (no auth)
127.0.0.20:3129  same, but requires Proxy-Authorization: Basic (lab:secret)
127.0.0.20:1080  SOCKS5 (RFC 1928), no auth

The proxy resolves names from its own table (it sits in "another network"),
so intranet.lab resolves here even though the client's DNS has no record.
CONNECT is only allowed to ports 443 and 8443, like Squid's SSL_ports ACL.
"""
import base64, socket, struct, sys, threading

PROXY_DNS = {"origin.lab": "127.0.0.10", "www.origin.lab": "127.0.0.10", "intranet.lab": "127.0.0.10"}
CONNECT_PORTS = {443, 8443}
log = open(sys.argv[1], "a", buffering=1)

def resolve(host):
    return PROXY_DNS.get(host.lower(), host)

def pipe(a, b):
    def one(x, y):
        try:
            while (d := x.recv(65536)):
                y.sendall(d)
        except OSError:
            pass
        for s in (x, y):
            try: s.shutdown(socket.SHUT_RDWR)
            except OSError: pass
    t = threading.Thread(target=one, args=(b, a), daemon=True); t.start()
    one(a, b); t.join()

def sni(hello):
    """Server name from a TLS ClientHello (RFC 8446 4.1.2, RFC 6066 3)."""
    try:
        if hello[0] != 0x16 or hello[5] != 1:
            return None
        i = 9 + 2 + 32
        i += 1 + hello[i]                                   # session id
        i += 2 + struct.unpack("!H", hello[i:i + 2])[0]     # cipher suites
        i += 1 + hello[i]                                   # compression
        end = i + 2 + struct.unpack("!H", hello[i:i + 2])[0]; i += 2
        while i < end:
            et, el = struct.unpack("!HH", hello[i:i + 4])
            if et == 0:
                n = struct.unpack("!H", hello[i + 7:i + 9])[0]
                return hello[i + 9:i + 9 + n].decode()
            i += 4 + el
    except (IndexError, struct.error):
        return None

def read_head(c):
    data = b""
    while b"\r\n\r\n" not in data:
        d = c.recv(4096)
        if not d:
            return None, b""
        data += d
    head, rest = data.split(b"\r\n\r\n", 1)
    return head.decode("latin-1").split("\r\n"), rest

def http_proxy(c, need_auth, port):
    lines, rest = read_head(c)
    if not lines:
        return c.close()
    method, target, ver = lines[0].split(" ")
    hdrs = [l for l in lines[1:]]
    auth = next((l.split(":", 1)[1].strip() for l in hdrs if l.lower().startswith("proxy-authorization:")), None)
    who = ""
    if auth and auth.lower().startswith("basic "):
        who = " user=" + base64.b64decode(auth[6:]).decode().split(":")[0] + " (password visible to anyone on the path to the proxy)"
    log.write(f"proxy:{port}: {lines[0]!r}{who}\n")
    if need_auth and auth != "Basic " + base64.b64encode(b"lab:secret").decode():
        c.sendall(b'HTTP/1.1 407 Proxy Authentication Required\r\nProxy-Authenticate: Basic realm="lab"\r\nContent-Length: 0\r\nConnection: close\r\n\r\n')
        log.write(f"proxy:{port}: -> 407\n"); return c.close()
    if method == "CONNECT":
        host, p = target.rsplit(":", 1)
        if int(p) not in CONNECT_PORTS:
            c.sendall(b"HTTP/1.1 403 Forbidden\r\nContent-Length: 0\r\nConnection: close\r\n\r\n")
            log.write(f"proxy:{port}: -> 403 (CONNECT to port {p} not allowed)\n"); return c.close()
        u = socket.create_connection((resolve(host), int(p)))
        c.sendall(b"HTTP/1.1 200 Connection established\r\n\r\n")
        first = c.recv(4096)
        log.write(f"proxy:{port}: tunnel to {host}:{p} opened; ClientHello SNI={sni(first)!r}; everything after this is opaque TLS\n")
        u.sendall(first); return pipe(c, u)
    # absolute-form: http://host[:port]/path (RFC 9112 3.2.2)
    assert target.startswith("http://"), target
    hostport, _, path = target[7:].partition("/")
    host, _, p = hostport.partition(":")
    u = socket.create_connection((resolve(host), int(p or 80)))
    keep = [l for l in hdrs if l.split(":")[0].lower() not in ("proxy-authorization", "proxy-connection", "connection")]
    req = [f"{method} /{path} {ver}"] + keep + ["Via: 1.1 labproxy", "Connection: close"]
    u.sendall(("\r\n".join(req) + "\r\n\r\n").encode() + rest)
    pipe(c, u)

def socks5(c):
    ver, n = c.recv(2); c.recv(n); c.sendall(b"\x05\x00")             # no authentication
    req = c.recv(4)
    if len(req) < 4:
        log.write("socks:1080: client sent the greeting, then closed without a CONNECT request\n")
        return c.close()
    ver, cmd, _, atyp = req
    if atyp == 1:
        host = socket.inet_ntoa(c.recv(4)); kind = "IPv4 address (client resolved the name itself)"
    elif atyp == 3:
        host = c.recv(c.recv(1)[0]).decode(); kind = "domain name (proxy resolves)"
    else:
        host = socket.inet_ntop(socket.AF_INET6, c.recv(16)); kind = "IPv6 address"
    port = struct.unpack("!H", c.recv(2))[0]
    log.write(f"socks:1080: CONNECT ATYP={atyp} {kind}: {host}:{port}\n")
    u = socket.create_connection((resolve(host), port))
    c.sendall(b"\x05\x00\x00\x01" + socket.inet_aton("127.0.0.20") + struct.pack("!H", 1080))
    pipe(c, u)

def listen(port, handler):
    l = socket.socket(); l.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    l.bind(("127.0.0.20", port)); l.listen(16)
    while True:
        c, _ = l.accept()
        threading.Thread(target=handler, args=(c,), daemon=True).start()

threading.Thread(target=listen, args=(3128, lambda c: http_proxy(c, False, 3128)), daemon=True).start()
threading.Thread(target=listen, args=(3129, lambda c: http_proxy(c, True, 3129)), daemon=True).start()
listen(1080, socks5)

Key takeaways from the test matrix:

  1. Domain Suffix Matching (origin.lab, .origin.lab): All three clients match domain suffixes consistently. Setting no_proxy=origin.lab or no_proxy=.origin.lab bypasses the proxy for both origin.lab and www.origin.lab.
  2. IP Matching vs Hostname Matching (127.0.0.10): If no_proxy=127.0.0.10, requests to http://127.0.0.10:8080/ go direct. However, requests to http://origin.lab:8080/ go via-proxy across all clients. Matching is strictly string-based; clients do not resolve origin.lab to check if its IP matches NO_PROXY.
  3. Wildcard Prefixes (*.origin.lab): Glob wildcard prefixes fail across all clients. When no_proxy=*.origin.lab, all requests go via-proxy. Wildcard globs are invalid syntax in standard NO_PROXY parsing implementations.
  4. CIDR Notation (127.0.0.0/8): When targeting http://127.0.0.10:8080/, curl and requests evaluate the CIDR range and go direct. Python’s urllib fails to parse CIDR notation, treating it as a literal string mismatch, and routes the request via-proxy.
  5. Port Specificity (origin.lab:8080): Python’s urllib and requests parse host-port combinations in NO_PROXY, successfully routing requests to origin.lab:8080 direct. curl 8.14.1 does not support port specifiers in no_proxy; it fails to match origin.lab:8080 and routes the request via-proxy.
  6. Catch-All Wildcard (*): Setting no_proxy=* acts as a universal bypass flag across all three implementations.

Operational notes

  • Long-Lived Connections (WebSockets & gRPC): HTTP CONNECT tunnels support persistent bi-directional protocols like WebSockets and gRPC. However, network operators must ensure intermediary proxy idle timeouts (timeout tunnel in HAProxy or read_timeout in NGINX) are tuned appropriately or TCP keepalives are enabled to prevent silent session termination.
  • Proxy Idle Timeouts: Intermediary proxies enforce read/write idle timeouts on inactive TCP connections. Applications utilizing long-lived HTTP/1.1 connections or TCP tunnels must transmit periodic application-layer pings or transport keepalives to prevent proxies from dropping idle sockets.
  • Proxy Visibility Limits:
    • For plain HTTP, the proxy can inspect full URLs, request headers, query parameters, and payload bodies.
    • For HTTPS via CONNECT, the proxy can inspect only the destination target IP/port and cleartext TLS SNI domain names during setup. Payload content and path parameters remain end-to-end encrypted.
  • TLS Interception Proxies (SSL Bumping): Forward proxies configured to perform deep packet inspection (DPI) on HTTPS traffic break the TLS connection by acting as a Man-in-the-Middle (MitM). The proxy terminates TLS with the client using a dynamically generated certificate signed by a custom internal Certificate Authority (CA).
    • Operational Impact: Clients must install the internal proxy CA root into their system and runtime trust stores. TLS interception breaks applications that pin certificates or ship their own CA bundle (many language runtimes and container images do).

Gotchas

  • DNS Leaks via socks5://: Configuring socks5:// instead of socks5h:// causes clients to resolve domain names using local DNS. This can leak private internal hostnames to local DNS servers and fail when resolving internal-only domain names.
  • Invalid NO_PROXY Wildcards: Placing wildcard domain patterns like *.example.com in no_proxy fails across curl, urllib, and requests. Standard implementations treat the asterisk as a literal character, causing bypass rules to fail. Use domain suffixes (e.g., .example.com or example.com) instead.
  • Case Sensitivity in http_proxy: curl ignores uppercase HTTP_PROXY to mitigate httpoxy security risks. Scripts relying only on uppercase HTTP_PROXY work in Python but go direct under curl. Use lowercase http_proxy, which every client reads; for the other variables, setting both cases is harmless.
  • CIDR Incompatibility in Python urllib: Standard Python urllib.request does not support CIDR ranges (such as 192.168.0.0/16) in NO_PROXY. It evaluates CIDR entries as literal string comparisons, causing connections to bypass rules and route through the proxy.
  • Hostname vs IP Mismatch in NO_PROXY: NO_PROXY string matching does not perform DNS resolution. If NO_PROXY contains 10.0.0.5, connecting to http://10.0.0.5 bypasses the proxy, but connecting to http://internal.lab (which resolves to 10.0.0.5) routes through the proxy.
  • Port Specifiers in curl no_proxy: Adding port numbers to no_proxy entries (e.g., example.com:8080) works in Python libraries but fails in curl, causing curl to ignore the rule and forward requests through the proxy.
  • Unencrypted Proxy Credentials: Passing proxy credentials in an http:// proxy URL (http://user:pass@proxy:3128) transmits credentials in base64-encoded cleartext. Protecting them needs an https:// proxy URL (TLS to the proxy itself), supported by curl since 7.52.0.
  • Silent change of route under CGI: Running Python HTTP applications in CGI environments automatically disables uppercase HTTP_PROXY processing. If environment configuration relies solely on uppercase HTTP_PROXY, outgoing requests switch from proxied to direct connections without warning.
