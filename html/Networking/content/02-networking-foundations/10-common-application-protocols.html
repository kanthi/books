Common Application Protocols

Application protocols give meaning to payloads. Operators still need a working vocabulary: DNS, DHCP, HTTP, SSH, and TLS appear in almost every network design.

Learning goals

  • Place common apps on TCP/UDP and well-known ports
  • Describe DNS resolution flow at a high level
  • Describe DHCP DORA and where relays fit
  • Separate HTTP from TLS and from TCP failures
  • Know what SSH needs from the network

Map (operator cheat sheet)

Protocol Transport Port(s) Role
DNS UDP/TCP 53 Name → address (and more)
DHCP UDP 67/68 IPv4 host config
DHCPv6 UDP 546/547 IPv6 host config
HTTP TCP 80 Web (cleartext)
HTTPS TCP 443 HTTP over TLS
SSH TCP 22 Secure shell / SFTP
NTP UDP 123 Time
BGP TCP 179 Routing (control plane app)
SNMP UDP 161/162 Legacy management

TLS in one paragraph

TLS provides encryption and authentication above TCP (classically). Network engineers care when: MTU/PMTUD breaks large records, middleboxes interfere, or certificates expire. Crypto suite deep-dives are optional here.

NTP and time

Broken time breaks auth (Kerberos, cert validation) and log correlation. Lab VMs often need chrony/ntp or host sync.

Lab sketch

  1. DNS: break /etc/resolv.conf; compare ping by name vs by IP
  2. HTTP: capture TCP/80 three-way + first GET
  3. SSH: confirm LISTEN on 22; ACL drop and observe client timeout

A name-to-response walkthrough

A name such as www.example.com is not an IP address. A resolver checks its configured sources and caches, then may ask a recursive DNS server. That server follows delegation from the root toward authoritative servers as necessary; cached answers can avoid repeated queries. A DNS record’s TTL limits how long it may be cached, but caches and clients can have their own behavior. A DNS answer can contain multiple IPv4 and IPv6 addresses; the client decides which connection attempts to make.

For an HTTPS request the client selects an address, establishes a transport connection, negotiates TLS, verifies the server certificate against its trust configuration and the requested name, and then exchanges HTTP messages. HTTP/3 uses QUIC over UDP rather than a TCP connection. Name resolution success does not prove connectivity, a TCP handshake does not prove certificate validity, and a valid TLS connection does not prove an application returns the desired response.

A practical sequence is getent ahosts example.com, ip route get <address>, and curl -v https://example.com/. Record what each step proves. curl may use proxies or local configuration; its verbose output helps identify the endpoint actually contacted. DNS queries may use UDP or TCP; avoid treating port 53 or UDP as a universal description of every resolver path.

DNS answers, delegation, and caching

A recursive resolver takes responsibility for finding an answer on a client’s behalf; an authoritative server answers for data in a zone it serves. Delegation connects the hierarchy: a parent supplies information about a child zone’s authoritative servers, and the resolver can then query them. A zone is an administrative portion of the name hierarchy; it is not necessarily identical to a domain name and all descendants, because children can be delegated separately.

A and AAAA records carry IPv4 and IPv6 addresses; CNAME indicates an alias; NS identifies name servers; SOA describes zone authority and parameters; MX identifies mail exchangers. A resolver may answer from cache, so a repeated query is not proof that the authoritative server was contacted again. A record’s TTL is a caching lifetime, not a guarantee that every client observes an update at exactly the same instant.

A response of NXDOMAIN indicates that the queried name does not exist according to the answering authority, subject to aliases and resolver behavior. A NODATA answer means the name exists but the requested record type is absent. SERVFAIL signals a resolution failure, not that the name does not exist. Negative answers can also be cached: creating a record after a cached negative response may not make every resolver show it immediately. See RFC 2308.

Investigate: compare dig example.com A and dig example.com AAAA; inspect the response code, answer section, TTL, and server. For a lab zone, query the recursive resolver and authoritative server separately with dig @<server> <name> <type>. A direct authoritative answer and a cached recursive answer can legitimately differ during a change. Use only lab-controlled names when intentionally creating or removing records.
