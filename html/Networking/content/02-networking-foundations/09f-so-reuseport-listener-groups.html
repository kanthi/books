SO_REUSEPORT: Many Listeners on One Port

After reading this chapter, you will be able to design and operate multi-process network services using SO_REUSEPORT, explain how the Linux kernel hashes incoming TCP handshakes and UDP datagrams across distinct listening sockets, diagnose queue draining and connection reset risks during server reloads, and contrast kernel-level load balancing with traditional single-listener architectures.

Version note: All code listings and socket behaviors in this chapter were verified on an unprivileged Linux 6.12 system over the loopback interface using the Python 3.14 standard library.

The Scaling Limits of a Single Listener

High-concurrency network servers running on multi-core systems must distribute incoming connection handling across multiple CPU cores. In traditional Unix socket programming, services achieved this through one of two models:

  1. Single-process event loop with worker threads: A single listening socket is managed by one thread or event loop, which accepts connections and passes accepted client file descriptors to worker threads. The single accept queue and its associated socket lock quickly become a bottleneck at high connection rates.
  2. Shared listening socket across processes: A parent process opens and binds a socket, calls listen(), and then calls fork() to spawn worker processes that inherit the listening file descriptor. Each worker independently adds the shared descriptor to its own event loop (such as epoll) and calls accept().

While the inherited-socket approach distributes worker execution, it creates severe kernel-level contention. When a new TCP connection completes the three-way handshake, the kernel wakes up waiting processes. Historically, this caused a thundering herd, where every worker process woke up to call accept(), but only one succeeded while the others received EAGAIN or EWOULDBLOCK.

Linux introduced the EPOLLEXCLUSIVE flag (Linux 4.5) for epoll_ctl to wake only one worker per event. However, all workers still contend on a single underlying kernel listening socket lock (struct sock::sk_lock) and compete for entries in the same listen queue (icsk_accept_queue). Under heavy connection churn, lock contention in inet_csk_accept() limits scalability across NUMA nodes and multiple CPU cores.

The SO_REUSEPORT Architecture

Introduced in Linux 3.9, the SO_REUSEPORT socket option fundamentally alters listener architecture. Rather than forcing worker processes to share a single listening socket data structure in the kernel, SO_REUSEPORT allows completely independent sockets—each with its own file descriptor, its own listen backlog queue, and its own lock—to bind to the exact same IP address and port combination.

Traditional Shared Listener (Inherited FD):
                           ┌─ Worker 1 (accepts from queue)
Incoming SYN ──> [ Shared Listen Socket ] ─┼─ Worker 2 (accepts from queue)
                 [ Single Accept Queue  ] ─┼─ Worker 3 (accepts from queue)
                 [ Single Spinlock      ] └─ Worker 4 (accepts from queue)

SO_REUSEPORT Listener Group:
                 ┌─> [ Socket 1 / Backlog Queue ] ──> Worker 1 (isolated)
Incoming SYN ──> ┼─> [ Socket 2 / Backlog Queue ] ──> Worker 2 (isolated)
  (4-tuple hash) ┼─> [ Socket 3 / Backlog Queue ] ──> Worker 3 (isolated)
                 └─> [ Socket 4 / Backlog Queue ] ──> Worker 4 (isolated)

When an incoming connection arrives, the kernel selects which socket in the reuseport group will receive it:

  • TCP distribution: During the initial SYN packet handling, the kernel computes a hash of the connection’s 4-tuple (source IP, source port, destination IP, destination port). The kernel scales that hash onto the group (reciprocal_scale(hash, N), which behaves like a modulo) to pick the receiving socket. The connection’s three-way handshake and subsequent accept() occur entirely on that specific socket.
  • UDP distribution: For SOCK_DGRAM sockets, the kernel computes the 4-tuple hash for every incoming datagram, distributing packets among the bound sockets in the group.
  • Lock isolation: Because each worker process operates on its own socket, there is zero cross-worker spinlock contention on accept queues.

Group Security Requirements

Allowing arbitrary processes to bind to an already open port would present an obvious security vulnerability: an unprivileged local attacker could bind to port 80 or 443 and hijack a portion of incoming traffic.

To prevent port hijacking, the kernel enforces strict security constraints:

  1. Explicit opt-in: Every socket participating in the group must set the SO_REUSEPORT socket option before calling bind(). If a socket attempts to bind without the option set, the call fails with EADDRINUSE.
  2. Effective UID matching: All sockets binding to the same address and port with SO_REUSEPORT must share the same effective user ID (euid). A process running under a different user ID cannot join an existing reuseport group.

SO_REUSEPORT vs SO_REUSEADDR

Network engineers frequently conflate SO_REUSEADDR and SO_REUSEPORT. Although their names sound similar, they solve distinct problems.

Feature SO_REUSEADDR SO_REUSEPORT
Primary purpose Rebind to a port currently in TIME_WAIT state Distribute load across multiple active listeners
Simultaneous active listeners No (only one active listening socket on a specific IP:port) Yes (multiple listening sockets on the exact same IP:port)
Kernel distribution None Hash-based 4-tuple load balancing
Security barrier Any process with bind privileges to that port Enforces matching effective UID across all group sockets
Linux introduction Historic BSD / Linux 1.0+ Linux 3.9

SO_REUSEADDR permits a server to restart immediately after a crash while previous connections linger in the kernel’s TIME_WAIT state. It does not allow multiple processes to listen concurrently on 127.0.0.1:8080. Attempting to bind a second active listener using only SO_REUSEADDR will fail immediately with EADDRINUSE.

Lab: Default Binding Behavior

To observe the baseline kernel restriction, attempt to bind two independent sockets to the same address and port without enabling SO_REUSEPORT.

The following script requests an ephemeral port from the kernel on loopback (127.0.0.1:0), reads the assigned port, and then attempts to bind a second socket to the identical address and port.

import errno
import socket

def main():
    s1 = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    s1.bind(("127.0.0.1", 0))
    s1.listen(128)
    addr, port = s1.getsockname()
    print(f"Socket 1 bound to {addr}:{port}")

    s2 = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    try:
        s2.bind((addr, port))
        s2.listen(128)
        print("Socket 2 bound successfully")
    except OSError as err:
        print(f"Socket 2 failed to bind: {err.strerror} (errno {err.errno} == EADDRINUSE: {err.errno == errno.EADDRINUSE})")
    finally:
        s1.close()
        s2.close()

if __name__ == "__main__":
    main()

The following command executes the script:

python3 without.py

Running without.py attempts to bind a second socket to the same address and port, raising an address-in-use error:

Socket 1 bound to 127.0.0.1:33855
Socket 2 failed to bind: Address already in use (errno 98 == EADDRINUSE: True)

Notice that the second bind() call fails immediately with OSError: [Errno 98] Address already in use. Without explicit socket options, the network stack strictly forbids duplicate bindings to prevent port collision.

Inspecting Listener Groups with ss

When SO_REUSEPORT is active, multiple listening sockets coexist on the same address. You can observe all sockets in the reuseport group using the Linux iproute2 utility ss.

ss -ltnp 'sport = :PORT'

(Not captured in the labs below, which use ephemeral ports.) When run against a service configured with four reuseport workers, ss reports four distinct socket inodes and separate receive queues (Recv-Q) and send queues (Send-Q), each mapped to a distinct worker process ID.

Lab: Distributing TCP Connections Across Workers

To demonstrate how SO_REUSEPORT distributes traffic, we construct a multi-process server.

The master process locates an available port, forks four worker processes, and directs each worker to create its own socket, apply SO_REUSEPORT, and bind to that exact port. The master process then initiates 400 separate TCP client connections, reads the responding worker’s identifier from each, and tallies the result into a histogram.

import collections
import multiprocessing
import os
import socket
import sys
import time

def worker_process(worker_id: int, port: int, ready_event: multiprocessing.Event, stop_event: multiprocessing.Event):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
    sock.bind(("127.0.0.1", port))
    sock.listen(128)
    sock.settimeout(0.2)

    ready_event.set()

    while not stop_event.is_set():
        try:
            conn, _ = sock.accept()
        except socket.timeout:
            continue
        except OSError:
            break
        with conn:
            conn.sendall(f"worker-{worker_id}\n".encode("ascii"))

    sock.close()

def find_free_port() -> int:
    temp_sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    temp_sock.bind(("127.0.0.1", 0))
    port = temp_sock.getsockname()[1]
    temp_sock.close()
    return port

def main():
    multiprocessing.set_start_method("fork", force=True)
    port = find_free_port()
    num_workers = 4
    num_connections = 400

    stop_event = multiprocessing.Event()
    workers = []

    for wid in range(num_workers):
        ready = multiprocessing.Event()
        p = multiprocessing.Process(
            target=worker_process,
            args=(wid, port, ready, stop_event),
        )
        p.start()
        ready.wait()
        workers.append(p)

    counts = collections.Counter()

    for _ in range(num_connections):
        with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as client:
            client.connect(("127.0.0.1", port))
            response = client.recv(64).decode("ascii").strip()
            counts[response] += 1

    stop_event.set()
    for p in workers:
        p.join()

    print(f"Total connections handled: {sum(counts.values())}")
    for worker, count in sorted(counts.items()):
        print(f"  {worker}: {count} connections ({count / num_connections * 100:.1f}%)")

if __name__ == "__main__":
    main()

The following command runs the listener group:

python3 group.py

Running group.py distributes 400 TCP handshakes across all four workers:

Total connections handled: 400
  worker-0: 111 connections (27.8%)
  worker-1: 85 connections (21.2%)
  worker-2: 106 connections (26.5%)
  worker-3: 98 connections (24.5%)

When reviewing the output, observe that all four workers receive and service a share of the 400 connections. Because the kernel assigns sockets using a hash of the 4-tuple, connections arriving from changing ephemeral source ports distribute across the workers. Variations between worker totals reflect natural statistical variance in 4-tuple hashing rather than an equal round-robin counter.

Lab: 4-Tuple Hashing and Connection Stickiness

The default socket selection mechanism in Linux is deterministic: it computes a seeded Jenkins hash (jhash, via inet_ehashfn) over the connection 4-tuple and maps it onto the \(N\) sockets. Conceptually:

\[\text{index} = \text{hash}(\text{src\_ip}, \text{src\_port}, \text{dst\_ip}, \text{dst\_port}) \pmod N\]

where \(N\) is the number of sockets in the group. If the 4-tuple does not change, the hash does not change, and the incoming connection routes to the exact same listening socket every time.

We can verify this property directly. In standard TCP implementations, closing a connection leaves the local endpoint in the TIME_WAIT state for two Maximum Segment Lifetimes (typically 60 seconds), which prevents reusing the same source port. However, by enabling SO_REUSEADDR and setting SO_LINGER to an abortive zero-second timeout (l_onoff = 1, l_linger = 0), the client forces an immediate RST teardown, bypassing TIME_WAIT. This permits the client to rebind immediately to the exact same source port.

import collections
import multiprocessing
import os
import socket
import struct
import time

def worker_process(worker_id: int, port: int, ready_event: multiprocessing.Event, stop_event: multiprocessing.Event):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
    sock.bind(("127.0.0.1", port))
    sock.listen(128)
    sock.settimeout(0.2)

    ready_event.set()

    while not stop_event.is_set():
        try:
            conn, _ = sock.accept()
        except socket.timeout:
            continue
        except OSError:
            break
        with conn:
            conn.sendall(f"worker-{worker_id}\n".encode("ascii"))

    sock.close()

def find_free_port() -> int:
    temp = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    temp.bind(("127.0.0.1", 0))
    port = temp.getsockname()[1]
    temp.close()
    return port

def main():
    multiprocessing.set_start_method("fork", force=True)
    server_port = find_free_port()
    client_port = find_free_port()
    num_workers = 4
    num_trials = 20

    stop_event = multiprocessing.Event()
    workers = []

    for wid in range(num_workers):
        ready = multiprocessing.Event()
        p = multiprocessing.Process(
            target=worker_process,
            args=(wid, server_port, ready, stop_event),
        )
        p.start()
        ready.wait()
        workers.append(p)

    counts = collections.Counter()
    linger_struct = struct.pack("ii", 1, 0)  # l_onoff=1, l_linger=0 (send RST)

    for _ in range(num_trials):
        client = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
        client.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
        client.setsockopt(socket.SOL_SOCKET, socket.SO_LINGER, linger_struct)
        client.bind(("127.0.0.1", client_port))
        client.connect(("127.0.0.1", server_port))
        
        reply = client.recv(64).decode("ascii").strip()
        counts[reply] += 1
        client.close()
        time.sleep(0.01)

    stop_event.set()
    for p in workers:
        p.join()

    print(f"Fixed client 4-tuple trials: {num_trials}")
    for worker, hits in sorted(counts.items()):
        print(f"  {worker}: {hits} hits")

if __name__ == "__main__":
    main()

The following command runs the stickiness test:

python3 sticky.py

Running sticky.py connects 20 times from the exact same source port, showing that all attempts route to the same worker:

Fixed client 4-tuple trials: 20
  worker-1: 20 hits

Notice that across all 20 connection cycles, exactly one worker receives 100% of the connections, while the other three workers receive none. Because the 4-tuple (127.0.0.1, client_port, 127.0.0.1, server_port) remains constant, the kernel’s hash function computes the identical group index every time.

Lab: UDP Datagram Load Balancing

For UDP sockets, SO_REUSEPORT works on individual datagrams rather than TCP handshakes. This enables multi-threaded or multi-process DNS, syslog, or media servers to read from independent UDP queues on the same port.

In the following script, three worker processes form an SO_REUSEPORT UDP group. A test client sends 300 datagrams, creating a fresh ephemeral client socket for each datagram.

import collections
import multiprocessing
import os
import socket
import time

def udp_worker(worker_id: int, port: int, ready_event: multiprocessing.Event, stop_event: multiprocessing.Event, results_queue: multiprocessing.Queue):
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEPORT, 1)
    sock.bind(("127.0.0.1", port))
    sock.settimeout(0.2)

    ready_event.set()
    handled = 0

    while not stop_event.is_set():
        try:
            data, addr = sock.recvfrom(1024)
            handled += 1
        except socket.timeout:
            continue
        except OSError:
            break

    sock.close()
    results_queue.put((worker_id, handled))

def find_free_udp_port() -> int:
    temp = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    temp.bind(("127.0.0.1", 0))
    port = temp.getsockname()[1]
    temp.close()
    return port

def main():
    multiprocessing.set_start_method("fork", force=True)
    port = find_free_udp_port()
    num_workers = 3
    num_packets = 300

    stop_event = multiprocessing.Event()
    results_queue = multiprocessing.Queue()
    workers = []

    for wid in range(num_workers):
        ready = multiprocessing.Event()
        p = multiprocessing.Process(
            target=udp_worker,
            args=(wid, port, ready, stop_event, results_queue),
        )
        p.start()
        ready.wait()
        workers.append(p)

    for i in range(num_packets):
        with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as client:
            client.sendto(f"msg-{i}".encode("ascii"), ("127.0.0.1", port))

    time.sleep(0.1)
    stop_event.set()

    worker_counts = {}
    for _ in range(num_workers):
        wid, count = results_queue.get()
        worker_counts[f"worker-{wid}"] = count

    for p in workers:
        p.join()

    print(f"Total UDP datagrams received: {sum(worker_counts.values())}")
    for worker, count in sorted(worker_counts.items()):
        print(f"  {worker}: {count} datagrams ({count / num_packets * 100:.1f}%)")

if __name__ == "__main__":
    main()

The following command executes the UDP load test:

python3 udp_group.py

Running udp_group.py transmits 300 datagrams from distinct ephemeral ports, distributing them across the three UDP sockets:

Total UDP datagrams received: 300
  worker-0: 86 datagrams (28.7%)
  worker-1: 105 datagrams (35.0%)
  worker-2: 109 datagrams (36.3%)

Notice that all three workers process datagrams, with each worker handling roughly one-third of the total volume. Unlike TCP, where hashing occurs once per connection during SYN reception, UDP evaluates the 4-tuple hash on every individual packet.

Operational Caveats and Edge Cases

While SO_REUSEPORT provides lock-free concurrency, it introduces specific operational hazards during dynamic resizing, process restarts, and rolling reloads.

The Accept Queue Drain Problem

When a worker process closes its listening socket—either during a graceful shutdown or after a process crash—any established TCP connections sitting in that socket’s accept backlog queue that have not yet been accepted via accept() are immediately discarded by the kernel, sending TCP RST packets to the connected clients.

Furthermore, any half-open connections in the SYN backlog associated with that specific socket fail completion during the handshake.

To solve this, Linux 5.14 introduced the net.ipv4.tcp_migrate_req sysctl. When enabled:

sysctl -w net.ipv4.tcp_migrate_req=1   # needs root; not run here

If a listening socket in an SO_REUSEPORT group closes while requests remain in its child queues, the kernel automatically migrates those pending requests to another active listening socket within the same reuseport group instead of resetting them.

Hash Reshuffling on Group Resizing

Since the selection is effectively \(\text{hash} \bmod N\), adding or removing a socket changes which listener most 4-tuples map to.

For TCP this matters less than it looks:

  • Established connections no longer touch the listener at all.
  • Since Linux 4.4, handshakes in flight are stored as request sockets in the established hash table. The client’s final ACK finds its request socket by direct lookup. It isn’t hashed across the group again.

The real TCP hazard is removing a listener, as described in the previous section. Its queued requests and unaccepted connections go with it, unless tcp_migrate_req is enabled.

For UDP, resizing matters a great deal. Every datagram is hashed again, so a “flow” that stayed on worker 2 (a QUIC connection, or a DNS client retrying from the same port) can land on a different worker as soon as \(N\) changes. Protocols that keep per-flow state in the worker need BPF steering, or another way to find the owner, to survive scaling.

Advanced Steering: BPF and CPU Affinity

The standard 4-tuple modulo hash treats all worker processes identically and ignores CPU cache locality. The Linux kernel provides two mechanisms to override or tune this behavior.

CPU Locality with SO_INCOMING_CPU

When workers run bound to specific CPU cores, setting the SO_INCOMING_CPU socket option informs the kernel which CPU core handles the socket:

int cpu = worker_cpu_id;
setsockopt(fd, SOL_SOCKET, SO_INCOMING_CPU, &cpu, sizeof(cpu));

When packets arrive on a network interface card (NIC) configured with Receive Side Scaling (RSS) or Receive Packet Steering (RPS), the kernel directs the connection to the SO_REUSEPORT socket whose configured CPU matches the CPU servicing the packet’s network interrupt, maximizing L1/L2 CPU cache hits.

Programmable Steering with eBPF

Note

Not run here. Loading custom BPF programs onto socket reuseport groups requires the CAP_BPF or CAP_NET_ADMIN capability and specialized BPF toolchains, which are not configured in this unprivileged lab environment.

According to the kernel documentation and primary sources, applications requiring precise connection dispatch can attach a BPF program to the reuseport group using the socket options:

  • SO_ATTACH_REUSEPORT_CBPF (classic BPF)
  • SO_ATTACH_REUSEPORT_EBPF (extended BPF)

In modern kernels, you write a program of type BPF_PROG_TYPE_SK_REUSEPORT. Instead of the kernel evaluating a 4-tuple hash, the kernel invokes your BPF program on each incoming packet. The program can inspect packet headers, check NUMA topology, look up worker load metrics in a BPF map, and explicitly return the array index of the target worker socket. If a worker is overloaded, the BPF program steers new connections to less busy workers, avoiding queue buildup.

Production Implementations: Nginx, HAProxy, and Envoy

Note

Not run here. Production reverse proxies like Nginx, HAProxy, and Envoy require external daemon management, production configurations, and root privileges to bind privileged ports (such as 80 and 443), which are unavailable in this container.

Modern edge proxies leverage SO_REUSEPORT to scale across multi-core systems:

  • Nginx: Configured via the reuseport directive on the listen directive:

    http {
    server {
        listen 80 reuseport;
        server_name example.com;
    }
}

    Per the Nginx documentation, setting reuseport creates an individual listening socket for each worker process rather than inheriting a shared socket descriptor. The kernel then spreads handshakes across worker event loops instead of having workers compete for one shared listener. NGINX’s own 1.9.1 socket-sharding benchmark reported lower and more consistent latency with reuseport. Measure on your workload before assuming similar gains.

  • HAProxy: Historically relied on SO_REUSEPORT during reloads, so the new process could bind the same ports while the old one still held them. Because of the accept-queue drain problem above, modern HAProxy instead hands the existing listening sockets to the new process over its master/stats socket (expose-fd listeners, -x), which avoids the reset window.

  • Envoy: The listener’s enable_reuse_port setting gives each worker thread its own socket on the same port, so the kernel balances connections across workers.

Common Pitfalls

Understanding these common mistakes prevents subtle production outages:

  1. Setting the option after bind(): SO_REUSEPORT must be applied using setsockopt() before invoking bind(). Setting the option on an already bound socket has no effect on group registration, and subsequent bind() calls by other processes will raise EADDRINUSE.
  2. Assuming round-robin distribution: SO_REUSEPORT does not use round-robin scheduling. It uses a 4-tuple hash. When testing with synthetic benchmark tools (such as load generators running from a single client machine with a narrow port range), traffic may land disproportionately on a subset of workers due to hash collisions.
  3. Uneven load from long-lived connections: Because distribution occurs strictly at connection establishment time, a worker that accepts a handful of heavy, long-running connections (such as WebSocket or gRPC streams) will experience high CPU usage, while adjacent workers handling short-lived HTTP/1.1 requests sit idle. Application-level balancing or BPF steering is needed to balance persistent streams.
  4. Neglecting the accept queue on shutdown: If a worker receives SIGTERM and immediately terminates its listening socket, clients with handshakes completed in the kernel accept queue receive connection resets. Production code must first stop accepting new connections while continuing to drain existing backlog descriptors, or rely on net.ipv4.tcp_migrate_req.
  5. Mixing differing UIDs: Attempting to bind a worker process running as a non-privileged user (e.g., www-data) to an existing reuseport group created by a process running under another user ID fails with EADDRINUSE, even if the socket option is set on both.

Key Takeaways

  • SO_REUSEPORT allows multiple independent listening sockets on the exact same IP and port, provided every socket sets the option before binding and all processes share the same effective UID.
  • Unlike single-socket architectures where workers compete for a shared accept queue lock or suffer from thundering herd wakeups, SO_REUSEPORT gives each worker an independent socket, an independent accept queue, and independent lock state.
  • For TCP, incoming connections are assigned during SYN processing using a deterministic 4-tuple hash. Fixed client-server 4-tuples always map to the same worker socket.
  • For UDP, every datagram is independently hashed by its 4-tuple across the group sockets.
  • Closing a listener drops its queued handshakes and unaccepted connections. Graceful restarts need careful draining, socket hand-off, or the Linux 5.14+ net.ipv4.tcp_migrate_req sysctl. Resizing the group also remaps UDP flows.
  • Advanced routing can be accomplished using SO_INCOMING_CPU for CPU cache locality and BPF_PROG_TYPE_SK_REUSEPORT for custom load-aware connection steering.
