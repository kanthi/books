Chapter 12: Testing and Debugging

In scientific research, buggy code is dangerous. It doesn’t just crash your computer—it can produce plausible-looking but subtly incorrect calculations, invalidating an entire semester of lab work.

This chapter teaches you systematic strategies for testing your functions and using Spyder’s visual debugger to locate and fix bugs with confidence.

       Bug Detection Spectrum:
       
       [ Overt Bug ]               ------> Program crashes with a loud traceback.
       (Easy to fix!)
       
       [ Covert Bug (Silent) ]     ------> Program runs to completion, but prints
       (The dangerous one!)                a wrong number (e.g. 2.45 instead of 4.90).

12.1 Black-Box vs Glass-Box Testing

When verifying a function, there are two distinct perspectives:

  Black-Box Testing:
  Input (X) --> [ ??? Unknown Interior ??? ] --> Output (Y)
  (Test against the specification without looking at the internal code)

  Glass-Box (White-Box) Testing:
  Input (X) --> [ if condition -> loop -> return ] --> Output (Y)
  (Design tests to exercise every internal branch, loop, and path in the code)
  • Black-Box Testing: You test the function based solely on its docstring and specifications. It tests whether the software delivers what the user expects.
  • Glass-Box Testing: You inspect the code lines directly and choose inputs specifically designed to trigger every if, elif, and else branch, and to test loops with zero, one, and multiple iterations.

12.2 Designing Test Cases: Typical, Edge, and Boundary Values

A good scientist does not test a function with just one random number. Always test three categories of inputs:

                  Input Domain: e.g. Speed v in [0, 100] m/s
       +-----------------------------------------------------------+
       |   0                10              50              99 100 |
       +-----------------------------------------------------------+
           ^                                ^                    ^
           +-- zero                         +-- typical          +-- maximum
  1. Typical Cases: Normal expected values (e.g., \(v = 25.0\)).
  2. Boundary Cases: Values right at the limits of validity (e.g., \(v = 0.0\) or \(v = 100.0\)).
  3. Edge / Extreme Cases: Empty inputs ([]), single-element collections, negative numbers where positives are expected, or very large floats (\(10^{15}\)).

Runnable Example: Testing a Velocity Calculator

def average_velocity(distance, time):
    """Computes v = d / t. Distance >= 0, Time > 0."""
    if time <= 0:
        raise ValueError("Time must be strictly positive!")
    if distance < 0:
        raise ValueError("Distance cannot be negative!")
    return distance / time

# Formal test suite
def test_average_velocity():
    # 1. Typical case
    assert average_velocity(100.0, 5.0) == 20.0, "Failed typical case"
    
    # 2. Boundary: Zero distance
    assert average_velocity(0.0, 5.0) == 0.0, "Failed zero distance boundary"
    
    # 3. Boundary: Small time step
    assert abs(average_velocity(1.0, 0.01) - 100.0) < 1e-9, "Failed small time case"
    
    # 4. Edge cases: Expecting exceptions
    try:
        average_velocity(50.0, 0.0)
        print("ERROR: Zero time should have raised ValueError!")
    except ValueError:
        pass  # Expected behavior!

    print("All test cases passed successfully!")

test_average_velocity()

12.3 Types of Bugs

Understanding the nature of a bug determines how you hunt it down:

Bug Category Characteristics How to Catch It
Overt Obvious crash with an explicit Python error (e.g. ZeroDivisionError). Read the traceback line number.
Covert (Silent) The code runs without error but outputs incorrect physics numbers. Unit tests and assertion checks.
Persistent Occurs every single time you run the script with the same inputs. Reproduce it in Spyder with a breakpoint.
Intermittent Occurs unpredictably (often caused by unseeded random numbers or file race conditions). Fix random seeds (seed=42) to make it persistent.

12.4 Hypothesis-and-Confirmation Debugging

Do not change lines of code at random hoping the bug disappears! Follow the scientific method:

  1. Observe the failure: "Output is negative (-5.4), but energy must be >= 0."
  2. Formulate a hypothesis: "Perhaps velocity was subtracted instead of added."
  3. Design an experiment: Insert a print statement or check the Variable Explorer.
  4. Confirm or reject: Check whether the intermediate variable matches expectation.
  5. Apply the fix: Test again to verify the bug is eliminated.

12.5 IDE-Based Debugging in Spyder

Spyder provides a world-class graphical debugger built directly into the Editor and Console.

       Editor Margin:
       Line 14:   [*]  result = calculate_force(m, a)  <-- Red Breakpoint Dot!

Debugging Steps:

  1. Set a Breakpoint: Click in the Editor margin next to any line number. A **red dot (*)** appears.
  2. Start Debugger: Press Ctrl + F5 (or click the blue Pause/Play debug icon).
  3. The program runs until it reaches your breakpoint, then pauses execution!
  4. The IPython console prompt changes to ipdb>.
  5. Inspect State: Look at the Variable Explorer—you can see the exact values of all variables at this exact split-second in time!
  6. Step Through:
    • Step Over (Ctrl + F10): Execute the current line and advance to the next.
    • Step Into (Ctrl + F11): Dive inside a function call to see how it computes.
    • Continue (Ctrl + F12): Resume full-speed execution until the next breakpoint.
    • Stop (Ctrl + Shift + F12, or Cmd + Shift + F12 on macOS): Quit the debugging session. Shift + F12 sets a conditional breakpoint. It does not stop the debugger.

12.6 Debugging a Recursive Function Step by Step

Let us debug a recursive countdown function to see the call stack in action:

def countdown(n):
    print(f"Entering countdown(n={n})")
    if n == 0:
        print("Blast off! (Base case reached)")
        return
    countdown(n - 1)
    print(f"Exiting countdown(n={n})")

countdown(3)

Output Trace:

Entering countdown(n=3)
Entering countdown(n=2)
Entering countdown(n=1)
Entering countdown(n=0)
Blast off! (Base case reached)
Exiting countdown(n=1)
Exiting countdown(n=2)
Exiting countdown(n=3)

Notice how the frames unwind in reverse order from the stack! If you omit the base case if n == 0, Python recursively calls until hitting RecursionError: maximum recursion depth exceeded.
