Telling Plan What Apply Will Know: convert and the assume Functions

After reading this chapter, you will be able to resolve unknown-value plan errors in conditional logic and resource counts by asserting type and value constraints at plan time using convert, assumenotnull, assumestringprefix, and assumeequal.

The Plan-Time Unknown Problem

OpenTofu operates in distinct phases. During tofu plan, OpenTofu constructs the dependency graph, reads state, evaluates expressions, and asks providers to generate proposed changes. During tofu apply, it executes the proposed graph operations against external APIs.

This separation creates an information gap. When a resource is first created or modified in a way that requires recreation, some or all of its attributes cannot be known until the API returns a response during apply. OpenTofu represents these values internally with a special marker: (known after apply), or an unknown value.

Unknown values propagate through expressions. If value \(A\) is unknown, then any transformation \(f(A)\)—such as concatenation, index lookup, or hashing—is usually also unknown. In most resource configurations, unknown attributes are harmless; OpenTofu simply defers sending them to the provider until apply.

However, certain core language constructs cannot tolerate unknowns during planning:

  • count: OpenTofu must know the exact number of resource instances to construct the graph. If count evaluates to an unknown number, planning fails immediately.
  • for_each: The keys of a map or set passed to for_each determine the distinct instance addresses. Unknown keys cause planning to abort.
  • Module and resource enable flags: A common idiom like count = var.enabled && resource.id != null ? 1 : 0 fails if resource.id != null evaluates to unknown.

Consider a conditional expression evaluating an unknown string:

local.is_ready = random_id.cluster.hex != null

If random_id.cluster.hex is unknown, OpenTofu cannot determine whether the value will eventually be null or a concrete string. The expression random_id.cluster.hex != null evaluates to unknown. If that local feeds count, plan aborts with:

Error: Invalid count argument
The "count" value depends on resource attributes that cannot be determined until apply.

OpenTofu 1.13.0 (released September 30, 2026; 1.13.2 is the latest patch release as of October 21, 2026) adds two tools for this gap: the assume... family of functions and the convert function. They let module authors state facts about values that are still unknown. OpenTofu attaches those facts to the unknown value, so comparisons such as != null or startswith() can return known results during plan.

Note

Compatibility note. convert() and the assume... functions are OpenTofu language additions from 1.13.0. A module that calls them needs OpenTofu 1.13.0 or later, and other tools that read HCL configurations won’t recognize them.

The assume Function Family

The assume... family provides hints to the plan-time evaluator about values that will only be finalized during apply. OpenTofu already automatically infers many structural assumptions from provider schemas, but providers frequently fail to signal non-nullability, string structure, or known constants. Furthermore, dynamic data decoded from strings (such as JSON or YAML) lacks static provider schema guarantees entirely.

When you wrap an expression in an assume... function, you enter an explicit contract:

  1. At Plan Time: OpenTofu treats the assumption as a fact. Downstream operations that depend on that specific invariant (such as null checks or prefix comparisons) evaluate to known values.
  2. At Apply Time: OpenTofu inspects the actual value returned by the provider or function. If the assumption is violated, the run aborts immediately with an error rather than applying corrupted infrastructure.

This chapter covers the three you will reach for most: assumenotnull, assumestringprefix and assumeequal. The family also has length hints for collections: assumelistlength, assumelistlengthmin and assumelistlengthmax, plus the matching assumesetlength... and assumemaplength... functions. With those, length(...) != 0 can be known during plan.

assumenotnull

assumenotnull(value) asserts that value will not be null once resolved.

output "vpc_id" {
  value = assumenotnull(aws_vpc.main.id)
}

If aws_vpc.main.id is unknown at plan time, standard OpenTofu logic treats aws_vpc.main.id != null as unknown. Wrapping the reference with assumenotnull informs the evaluator that whatever string eventually arrives, it will not be null. Consequently:

  • assumenotnull(aws_vpc.main.id) != null evaluates to true during plan.
  • assumenotnull(aws_vpc.main.id) == null evaluates to false during plan.

This allows parent modules or dependent resources to use count = module.network.vpc_id != null ? 1 : 0 without plan errors.

assumenotnull requires that the input value has a known type at plan time. If you pass a value of dynamic type (for example, an attribute extracted from an untyped jsondecode payload), OpenTofu cannot verify the type structure. In such cases, assumenotnull must be paired with convert.

assumestringprefix

assumestringprefix(string, prefix) asserts that the string attribute, once known, will begin with the given literal prefix.

output "validated_vpc_id" {
  value = assumestringprefix(aws_vpc.main.id, "vpc-")
}

Cloud providers commonly use identifier prefixes to differentiate resource types (vpc-, subnet-, igw-, ami-). Often, module logic branches on resource types:

local.is_vpc = startswith(module.network.resource_id, "vpc-")

Without an assumption, startswith(unknown, "vpc-") evaluates to unknown, preventing its use in count or for_each. With assumestringprefix:

  • startswith(assumestringprefix(aws_vpc.main.id, "vpc-"), "vpc-") evaluates to known true during plan.
  • Once aws_vpc.main.id is known, OpenTofu checks it. If the value does not begin with vpc-, the function call fails with an error and the run stops there.

You can compose assumption functions directly:

output "vpc_id" {
  value = assumenotnull(assumestringprefix(aws_vpc.main.id, "vpc-"))
}

assumeequal

assumeequal(actual, expected) asserts that actual will equal expected when applied. It returns the value of expected.

locals {
  target_region = assumeequal(data.aws_region.current.name, "us-east-1")
}

The behavior of assumeequal has specific semantics:

  1. Type Precedence: The type of the second argument (expected) wins. The first argument is converted to the type of the second argument.
  2. Metadata from expected wins: The result is always the second argument, so the sensitivity and ephemerality of actual are effectively ignored. If the result must stay sensitive, make expected sensitive too, for example with sensitive().
  3. Plan-Time Knownness: Because the return value is expected, the expression is fully known during plan, allowing any downstream equality check or string interpolation to proceed immediately.
  4. Apply-Time Enforcement: During apply, if actual resolves to a value not equal to expected, OpenTofu halts with an error.

The following table summarizes the three assumption functions:

Function Primary Purpose Plan-Time Effect Apply-Time Enforcement
assumenotnull(val) Guarantee non-null value != null resolves to true Errors if value is null
assumestringprefix(str, pfx) Guarantee string prefix startswith(..., pfx) resolves to true Errors if prefix does not match
assumeequal(act, exp) Force value to known target Replaces unknown with exp Errors if act != exp
assumelistlengthmin(list, n) (and siblings) Bound a collection’s length length(...) comparisons can be known Errors if the length is out of bounds

Type Coercion with convert

OpenTofu is statically typed under the hood, but expressions like jsondecode(), yamldecode(), or dynamic provider outputs produce values of dynamic type (dynamic). Dynamic types delay type checking until runtime and prevent the plan evaluator from reasoning about object keys or nested attributes.

The convert(value, type) function converts a value to an explicit type constraint.

locals {
  raw_payload = jsondecode("{\"retries\": 3, \"enabled\": true}")
  typed_data  = convert(local.raw_payload, object({
    retries = number
    enabled = bool
  }))
}

In earlier versions of the language, forcing a dynamic type into a concrete schema required awkward workarounds, such as passing the value through an auxiliary module variable with a declared type block. The convert() function makes type coercion a first-class language expression.

Combining convert with assumenotnull

Because assumenotnull requires its target to have a known type, attempting to call assumenotnull directly on an arbitrary attribute of an untyped JSON payload can fail. Combining convert with assumenotnull guarantees both the type structure and the non-null invariant at plan time:

locals {
  api_response = jsondecode(data.http.config.response_body)
  vpc_id       = assumenotnull(convert(local.api_response.vpc_id, string))
}

By explicitly casting local.api_response.vpc_id to string, OpenTofu establishes the type constraint. assumenotnull then establishes the non-null invariant, allowing local.vpc_id != null to resolve during plan.

Hands-On Lab: Resolving Unknown Plan Errors

In this lab, you will reproduce an “Invalid count argument” error caused by an unknown attribute returned from a child module. You will then fix the error using assumenotnull without waiting for the resource to be created. Finally, you will explore convert and assumestringprefix using the interactive console.

The lab uses OpenTofu 1.13.2 and the hashicorp/random provider (~> 3.7).

Lab Architecture

The lab directory contains two configurations:

  • before/: A parent module calling a child module that generates a random_id. The parent attempts to evaluate count = module.id.value != null ? 1 : 0. Planning fails because the child output is unknown.
  • after/: The identical architecture, but the child module wraps its output in assumenotnull(). Planning succeeds.
lab/
├── before/
│   ├── main.tf
│   └── modules/
│       └── id/
│           └── main.tf
└── after/
    ├── main.tf
    └── modules/
        └── id/
            └── main.tf

The Unassisted Failure: before/

First, inspect the child module that generates a random identifier.

terraform {
  required_version = ">= 1.13.0"
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.7"
    }
  }
}

resource "random_id" "this" {
  byte_length = 8
}

output "value" {
  description = "The unassumed generated identifier."
  value       = random_id.this.hex
}

Now inspect the root module, which attempts to use this output in a conditional count expression on a terraform_data resource.

terraform {
  required_version = ">= 1.13.0"
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.7"
    }
  }
}

module "id" {
  source = "./modules/id"
}

resource "terraform_data" "consumer" {
  count = module.id.value != null ? 1 : 0

  input = module.id.value
}

Execute initialization and planning inside the before directory.

cd before && tofu init -input=false >/dev/null && tofu plan -input=false -no-color

The plan command produced this output:

The Solution: after/

In the after/ configuration, update the child module output to assert that random_id.this.hex will never be null once computed.

terraform {
  required_version = ">= 1.13.0"
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.7"
    }
  }
}

resource "random_id" "this" {
  byte_length = 8
}

output "value" {
  description = "The assumed non-null generated identifier."
  value       = assumenotnull(random_id.this.hex)
}

The root module configuration remains identical.

terraform {
  required_version = ">= 1.13.0"
  required_providers {
    random = {
      source  = "hashicorp/random"

module "id" {
  source = "./modules/id"

resource "terraform_data" "consumer" {
  count = module.id.value != null ? 1 : 0

Interactive Evaluation with tofu console

You can test type conversions and assumptions interactively without writing full module files.

Test convert() by transforming a dynamic JSON list of numbers into a typed list of strings:

echo 'convert(jsondecode("[1,2]"), list(string))' | tofu console

The console command produced this output:

tolist([
  "1",
  "2",
])

The output shows that each number in the JSON string was coerced into a string element inside a typed list.

Next, test assumption failure. Pass an invalid prefix to assumestringprefix():

echo 'assumestringprefix("vpc-123", "subnet-")' | tofu console

The console command produced this output:

╷
│ Error: Invalid function argument
│ 
│   on <console-input> line 1:
│   (source code not available)
│ 
│ Invalid value for "value" parameter: assumption was not upheld.
╵

The value is already known in the console, so OpenTofu checks the assumption straight away and rejects it. The error message is generic: “assumption was not upheld”. It doesn’t name the prefix, so give each assumption a clear spot in your configuration so a failure is easy to trace.

Common Mistakes and Pitfalls

1. Violating Assumptions at Apply Time

Assumptions are hard guarantees. If a provider returns a value that contradicts an assumption, OpenTofu aborts the apply step.

# Dangerous: an optional resource attribute may actually return null
output "public_ip" {
  value = assumenotnull(aws_instance.server.public_ip)
}

If the instance is placed in a private subnet without a public IP address, aws_instance.server.public_ip resolves to null. During plan, OpenTofu assumed it was non-null. When the real value arrives during apply, the function call fails. It raises the same “Invalid function argument … assumption was not upheld” error shown in the console lab, and the run stops.

The documentation also warns that different OpenTofu versions may catch a broken assumption at different points, during plan in one release and only during apply in another. Treat an assumption as a promise you can back up, not as a way to quiet the planner.

Only use assumenotnull on attributes that are guaranteed by the provider or API specification to exist once created (such as generated resource IDs, ARNs, or computed hashes).

2. Using assumenotnull on Dynamic Types Without convert

assumenotnull cannot analyze values whose type itself is unknown or dynamic. Consider an untyped object from decoded YAML or JSON:

locals {
  data = jsondecode(var.raw_json)
  # Incorrect if data.item has dynamic type
  valid = assumenotnull(local.data.item)
}

If OpenTofu cannot verify the type schema during plan, it cannot evaluate assumenotnull. The fix is to cast the dynamic attribute to a concrete type first:

locals {
  data  = jsondecode(var.raw_json)
  valid = assumenotnull(convert(local.data.item, string))
}

3. Dropping sensitivity with assumeequal

assumeequal(actual, expected) returns expected, and only the markings on expected carry through. Suppose a resource attribute is sensitive and you predict it with a plain expression. The result is no longer sensitive:

locals {
  # The provider marks connection_uri as sensitive; the result here is not.
  db_uri = assumeequal(
    example_database.main.connection_uri,
    "postgres://app@${var.db_host}:5432/app",
  )
}

If the value must stay redacted, wrap the expected value: assumeequal(example_database.main.connection_uri, sensitive("postgres://...")). The documentation recommends exactly this.

4. Overusing Assumptions Instead of Direct Logic

Do not use assumption functions when standard language constructs suffice. If a value is already known at plan time (such as an input variable or a static string local), standard equality (==), non-null checks (!= null), or functions like startswith() evaluate cleanly without needing assume.... Reserve the assume... family for boundaries where values originate from resource attributes or external data sources that remain unknown until apply.

Summary

  • OpenTofu 1.13.0 introduces convert and the assume... function family (assumenotnull, assumestringprefix, assumeequal and the collection length hints) to provide plan-time hints about unknown values.
  • assumenotnull(value) resolves != null comparisons to true during plan, unblocking conditional count and for_each expressions.
  • assumestringprefix(string, prefix) enables plan-time evaluation of startswith() expressions on unknown resource attributes.
  • assumeequal(actual, expected) forces an unknown value to evaluate as expected during plan; the type of expected wins and sensitivity is ignored.
  • convert(value, type) transforms dynamic types (such as jsondecode() output) into concrete OpenTofu types.
  • If an assumption turns out false, the call fails with “assumption was not upheld” and the run stops.
  • These functions require OpenTofu 1.13.0 or later.
