Chapter 3: Boot, Initialization, and Runtime Environment

A secure Linux operating system cannot be constructed on an untrusted or compromised foundation. If an adversary tampers with the firmware, alters bootloader parameters, or modifies early userspace binaries before the kernel establishes its security subsystems, all subsequent user-space protections—including firewalls, file permissions, and Mandatory Access Control—are rendered futile.

This chapter details the mechanisms required to establish an unbroken chain of trust from initial hardware power-on through bootloader execution, kernel parameter validation, systemd service sandboxing, dynamic library loading, and package supply chain integrity.

Firmware, UEFI, and Secure Boot

Modern x86_64 and ARM64 platforms replace legacy BIOS with the Unified Extensible Firmware Interface (UEFI). The cornerstone of firmware security is UEFI Secure Boot:

┌────────────────────────────────────────────────────────────────────────┐
│                      SECURE BOOT CHAIN OF TRUST                        │
│                                                                        │
│   Hardware / ROM       UEFI NVRAM           EFI System Partition (ESP) │
│   ┌──────────────┐     ┌──────────────┐     ┌────────────────────────┐ │
│   │ Platform Key │────►│ Key Exchange │────►│ Microsoft Third-Party  │ │
│   │ (PK - OEM)   │     │ Key (KEK)    │     │ UEFI CA (in db)        │ │
│   └──────────────┘     └──────────────┘     └───────────┬────────────┘ │
│                                                         │ verifies     │
│                                                         ▼              │
│                                             ┌────────────────────────┐ │
│                                             │ Shim Bootloader (shim) │ │
│                                             └───────────┬────────────┘ │
│                                                         │ verifies     │
│                                                         ▼              │
│                                             ┌────────────────────────┐ │
│                                             │ GRUB Bootloader        │ │
│                                             └───────────┬────────────┘ │
│                                                         │ verifies     │
│                                                         ▼              │
│                                             ┌────────────────────────┐ │
│                                             │ Linux Kernel (vmlinuz) │ │
│                                             └────────────────────────┘ │
└────────────────────────────────────────────────────────────────────────┘
  1. The Signature Database (db) & Forbidden Database (dbx): The UEFI firmware stores certificates in non-volatile RAM. The db contains trusted certificates permitted to execute, while dbx maintains a revocation list of known compromised bootloaders and kernels.
  2. The Shim Loader: Distribution vendors cannot force OEMs to embed unique keys for each Linux distribution. Instead, Microsoft signs a small first-stage bootloader known as shim using its widely trusted third-party UEFI CA.
  3. Machine Owner Keys (MOK): Shim introduces the MOK facility, allowing local administrators to enroll private signing keys to sign custom out-of-tree kernel modules (such as proprietary GPU drivers) without disabling Secure Boot.
# Verify Secure Boot status on a running system
mokutil --sb-state

# List enrolled Machine Owner Keys
mokutil --list-enrolled

If Secure Boot is disabled, an attacker with physical access or root privileges can install a persistent bootkit in the EFI System Partition (ESP) that loads before the kernel and hooks hypervisor interrupts.

The Boot Loader: GRUB Security

The Grand Unified Bootloader (GRUB 2) is the standard bootloader across modern Linux distributions. By default, GRUB presents an interactive console where anyone with console access can press e to edit boot parameters. An attacker can append init=/bin/bash or systemd.unit=emergency.target to bypass authentication and drop directly into an unauthenticated root shell.

Securing GRUB with Authentication

To prevent unauthorized boot manipulation, GRUB menus must be protected with cryptographically hashed credentials:

# Step 1: Generate a PBKDF2 password hash using grub-mkpasswd-pbkdf2
grub-mkpasswd-pbkdf2
# Enter password: *********
# PBKDF2 hash of your password is grub.pbkdf2.sha512.10000.E729...

# Step 2: Configure GRUB credentials in /etc/grub.d/40_custom
cat << 'EOF' | sudo tee -a /etc/grub.d/40_custom
set superusers="grubadmin"
password_pbkdf2 grubadmin grub.pbkdf2.sha512.10000.E729...
EOF

# Step 3: Regenerate grub.cfg and restrict file permissions
sudo update-grub
sudo chmod 0600 /boot/grub/grub.cfg

Once configured, standard boot proceeds automatically, but pressing e to edit kernel command lines or booting alternate kernels requires the grubadmin credentials.

Kernel Parameters and Boot-Time Security

The kernel’s behavior and exploit mitigation features can be tuned during initialization using kernel command-line arguments in /etc/default/grub:

# Add to GRUB_CMDLINE_LINUX_DEFAULT in /etc/default/grub
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash slab_nomerge init_on_alloc=1 init_on_free=1 page_alloc.shuffle=1 pti=on module.sig_enforce=1 lockdown=confidentiality"

Exploit Mitigation Kernel Flags

Parameter Defensive Mechanism
slab_nomerge Prevents merging of kernel slab caches with similar sizes, hindering heap-overflow exploitation across different kernel structures
init_on_alloc=1 Zeros allocated heap and page memory upon allocation, mitigating use-of-uninitialized-memory bugs
init_on_free=1 Zeros memory pages upon free, preventing sensitive data retention and use-after-free data leaks
page_alloc.shuffle=1 Randomizes page allocator freelists, increasing entropy against return-oriented programming (ROP)
pti=on Enforces Page Table Isolation unconditionally, protecting against speculative execution side-channel attacks
module.sig_enforce=1 Rejects any kernel module lacking a valid cryptographic signature matching the kernel’s trusted keyring
lockdown=confidentiality Blocks userspace from reading or modifying kernel memory via /dev/mem, /dev/kmem, and debugfs

After updating /etc/default/grub, execute sudo update-grub and reboot the machine to apply the mitigations.

Systemd and Service Security

systemd is the init system and service manager on all major enterprise Linux distributions. While historically criticized for complexity, modern systemd includes a rich declarative sandboxing framework that allows administrators to strictly isolate daemons without writing custom C wrappers.

Key Systemd Security Directives

A hardened systemd unit file (or override drop-in) isolates services using Linux namespaces, cgroups, and capabilities:

# /etc/systemd/system/myapp.service.d/override.conf
[Service]
# Execute with an unprivileged, dynamically allocated user
DynamicUser=yes
User=myapp
Group=myapp

# Filesystem Isolation
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
ReadWritePaths=/var/lib/myapp /var/log/myapp

# Kernel and Device Protection
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
PrivateDevices=yes

# Privilege and Syscall Restrictions
NoNewPrivileges=yes
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
AmbientCapabilities=CAP_NET_BIND_SERVICE
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
RestrictNamespaces=yes
RestrictRealtime=yes
MemoryDenyWriteExecute=yes
SystemCallFilter=@system-service
SystemCallFilter=~@privileged @resources @obsolete

Auditing Services with systemd-analyze security

systemd includes a built-in automated security auditor that inspects unit definitions and calculates an exposure score from 0.0 (safest) to 10.0 (exposed):

# Audit the security score of a service unit
systemd-analyze security myapp.service
→ Overall exposure level for myapp.service: 1.2 OK 🙂
  ...
  ✓ ProtectSystem=strict               Service has strict read-only /usr, /boot, /etc
  ✓ NoNewPrivileges=yes                Service cannot acquire new privileges
  ✓ PrivateTmp=yes                     Service has private /tmp and /var/tmp

Shared Libraries and Dynamic Linking

When an ELF binary executes in Linux, the kernel loads the executable and invokes the dynamic linker (/lib64/ld-linux-x86-64.so.2). The linker resolves external symbols by scanning directories listed in the binary’s DT_RUNPATH, environment variables, and /etc/ld.so.cache.

The /etc/ld.so.preload Threat Vector

The file /etc/ld.so.preload allows administrators (or rootkits) to specify shared libraries that are injected into every single dynamically linked process launched on the system. Adversaries frequently write malicious user-mode rootkits into /etc/ld.so.preload to hook functions like readdir(), open(), and pam_authenticate(), hiding malicious files and bypassing logins.

# Verify that ld.so.preload does not exist or is completely empty
ls -la /etc/ld.so.preload

# Ensure /etc/ld.so.conf and /etc/ld.so.conf.d/ are strictly root-writable
sudo chmod 0644 /etc/ld.so.conf
sudo chmod -R 0644 /etc/ld.so.conf.d/

Binary Hardening Flags: RPATH vs RUNPATH

Avoid compiling software with insecure hardcoded library paths (RPATH). Use RUNPATH, and ensure compiling includes stack protection and Read-Only Relocations (RELRO):

# Check binary hardening features with checksec
checksec --file=/usr/bin/ssh
# RELRO: Full RELRO | Stack: Canary found | NX: NX enabled | PIE: PIE enabled

Package Management and Software Supply Chain

Linux distributions maintain signed package repositories verified via public-key cryptography.

┌────────────────────────────────────────────────────────────────────────┐
│                     PACKAGE SIGNATURE VERIFICATION                     │
│                                                                        │
│   Package Maintainer ──► Signs Release Index with GPG Private Key      │
│                                   │                                    │
│                                   ▼                                    │
│   Distribution Mirror ──► InRelease / Release.gpg                      │
│                                   │                                    │
│                                   ▼ Downloaded by apt / dnf            │
│   Local Machine: /etc/apt/trusted.gpg.d/ ──► GPG Public Key            │
│   Verification: Matches signature? Yes ──► Install package             │
│                                    No  ──► Abort transaction          │
└────────────────────────────────────────────────────────────────────────┘
  1. Modern GPG Key Storage: Legacy practices stored trusted keys directly in the global keyring /etc/apt/trusted.gpg. Modern distributions require placing armored keys into /etc/apt/keyrings/ and binding them strictly to individual repository sources via the signed-by directive in /etc/apt/sources.list.d/.
  2. Preventing Dependency Confusion: Restrict third-party PPAs and external mirrors. Unvetted repositories can push malicious packages with inflated version numbers (epoch:999) that overwrite core system utilities.

Configuration Drift and System Integrity

Over time, administrative changes, hotfixes, and unauthorized edits cause host configurations to drift away from the secure baseline.

File Integrity Monitoring (FIM) with AIDE

Advanced Intrusion Detection Environment (AIDE) builds an encrypted cryptographic database of file attributes (SHA-256 hashes, inodes, permissions, timestamps):

# Install and initialize AIDE database
sudo apt install -y aide
sudo aideinit

# Move baseline database to active production location
sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db

# Perform manual integrity audit
sudo aide --check

Integrity Measurement Architecture (IMA) and EVM

For high-assurance deployments, the Linux kernel includes IMA and Extended Verification Module (EVM). IMA measures file hashes before execution and stores the measurements in the TPM chip (PCR 10). If an executable’s hash does not match an approved cryptographic signature signed by the enterprise PKI, the kernel blocks execution with EPERM.
