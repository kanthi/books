User services, lingering, and session lifecycle

Linux service management is not restricted to global daemon processes managed by system-level PID 1. Standard non-root users can manage their own background services, timers, and socket-activated daemons without administrative privileges. After reading this chapter, you will be able to structure user-level systemd unit files in standard directory hierarchies, control user session lifecycles through systemd-logind and PAM integration, decouple user services from active login sessions using lingering (loginctl enable-linger), and identify standard operational pitfalls when running user systemd managers.

Architecture of system versus user systemd managers

Modern systemd architectures separate global system orchestration from per-user service orchestration. The system manager runs as PID 1 with root privileges, initializing hardware, network stacks, system storage, and system-wide services. User managers run as unprivileged processes—one per active user UID—executing an instance of the systemd --user binary under the user’s unprivileged credentials.

The system manager manages user managers through a dedicated system service unit template: user@UID.service (for example, user@1000.service). When a user authenticates to the system, systemd-logind.service coordinates with the Pluggable Authentication Modules (PAM) stack to trigger the execution of this system unit. The system unit instantiates systemd --user inside a dedicated control group (/user.slice/user-1000.slice/user@1000.service), isolating user services from root tasks and other users’ environments.

The user manager provides individual users with service recovery, dependency graph execution, timer schedules, and socket activation without granting full sudo or system-level root access.

Unit file lookup paths and precedence for user units

User managers locate unit files across standard directory paths. Similar to the system manager, user unit loading follows a strict precedence order where local user configurations override vendor-supplied defaults.

When resolving unit names, the user instance of systemd searches the following directories in descending order of priority:

  1. Runtime units: /run/user/UID/systemd/user/ (transient units created at runtime)
  2. Local user configuration: ~/.config/systemd/user/ (user-specific unit files and drop-ins)
  3. Local administrator overrides: /etc/systemd/user/ (system-wide user units installed by root for all users)
  4. Runtime system overrides: /run/systemd/user/ (system-wide transient user units)
  5. Distribution / Package vendor units: /usr/lib/systemd/user/ or /lib/systemd/user/ (installed by package managers)
Note

To deploy an unprivileged service instance, create the user configuration directory and place the unit file in ~/.config/systemd/user/:

[Unit]
Description=Laboratory Application User Service
After=network.target

[Service]
Type=exec
ExecStart=/usr/bin/python3 -m http.server 8080
Restart=on-failure
RestartSec=5s

[Install]
WantedBy=default.target

Units placed in ~/.config/systemd/user/ affect only the owning account. Units placed in /etc/systemd/user/ by a system administrator become available to all user managers on the system, allowing users to enable or disable them individually within their own user session scope.

User session lifecycle and PAM integration

The lifecycle of a user manager is tightly coupled to user authentication sessions by default. When an unprivileged user logs into a Linux system—whether via SSH, text console, or graphical display manager—the login process passes through the PAM authentication stack.

The pam_systemd.so module registers the login session with systemd-logind.service. Upon receiving session registration, systemd-logind performs the following sequence:

  1. Checks if a user@UID.service instance is already active for the target UID.
  2. If no instance exists, systemd-logind requests systemd (PID 1) to start user@UID.service.
  3. The system manager creates /run/user/UID/ with appropriate permission masks (0700 owned by UID) and mounts an isolated tmpfs runtime directory.
  4. systemd (PID 1) launches systemd --user under the target UID.
  5. systemd --user parses user unit directories and activates default.target.

       v
  PAM Stack  ------->  pam_systemd.so

Session termination defaults

By default, systemd user managers terminate when the user closes their last active login session. When an SSH session closes or a user logs out of a console:

  1. systemd-logind detects that zero active login sessions remain for the UID.
  2. systemd-logind signals systemd (PID 1) that the session scope has ended.
  3. Unless explicit configuration overrides this behavior, systemd (PID 1) stops user@UID.service.
  4. systemd --user sends SIGTERM (followed by SIGKILL after TimeoutStopSec=) to all processes running under its control group hierarchy.
  5. The runtime directory /run/user/UID/ is unmounted and cleaned up.

Under default operating settings, any background job, screen session, or user systemd service started by an unprivileged user dies upon logout.

Decoupling user services with lingering

For servers and headless workstations, terminating user services on logout is undesirable. Long-running user workloads—such as background data indexers, user-scoped container runtimes, or build agents—must start automatically at system boot and remain running across logouts.

Systemd provides the lingering feature through systemd-logind to alter user service lifetimes.

When lingering is enabled for a user account, systemd-logind changes the user manager activation lifecycle: - The system manager starts user@UID.service automatically during system boot (as soon as systemd-user-sessions.service completes), without requiring an interactive user login. - When all active login sessions for the user terminate, systemd-logind leaves user@UID.service running. - Background user units remain active until the host system is shut down or rebooted.

Managing lingering state with loginctl

Lingering status is managed using the loginctl command-line utility, which communicates with systemd-logind.service over D-Bus.

Note

Not run here. System control binaries are unavailable in this environment. According to the primary loginctl(1) documentation, enabling and checking linger status uses the following commands.

To enable lingering for a specific user:

loginctl enable-linger alice

To disable lingering for a user, restoring standard session-bound cleanup:

loginctl disable-linger alice

To inspect whether lingering is active for a given user account, query user attributes via loginctl:

loginctl show-user alice --property=Linger

When lingering is enabled, systemd-logind writes an empty state marker file to /var/lib/systemd/linger/username. The presence of this file instructs systemd-logind during boot to request the activation of user@UID.service for that account.

State Spawns user manager on boot Session logout behavior Runtime /run/user/UID/ state
Disabled (Default) No (waits for first login) user@UID.service terminated immediately Unmounted and cleared on logout
Enabled (enable-linger) Yes (during system startup) user@UID.service remains running Preserved in tmpfs across logouts

Service management, environment, and socket activation

Operating services under systemctl --user introduces operational differences compared to system-level service management.

Command routing and execution

All standard systemctl subcommands operate against the user manager when passed the --user flag:

Note

Not run here. System control binaries are unavailable in this environment. The following commands demonstrate standard user service management.

# Enable a user service to start on user manager boot/login
systemctl --user enable labapp.service

# Start a user service immediately
systemctl --user start labapp.service

# Check the status of a user service
systemctl --user status labapp.service

When executing systemctl --user commands inside an SSH session, systemctl connects to the user D-Bus socket located at /run/user/UID/systemd/private or through the DBUS_SESSION_BUS_ADDRESS environment variable.

Environment variables in user units

System managers run PID 1 with an isolated, fixed environment defined by system defaults. User managers inherit environment variables during initialization, but their environment environment can differ from an interactive login shell:

  • Non-interactive SSH commands or lingering boots bypass full shell profile scripts (~/.bashrc or ~/.bash_profile).
  • Variables like PATH, LANG, and HOME are set by PAM or systemd defaults, not by user shell configurations.
  • Environment variables like DISPLAY or WAYLAND_DISPLAY are set dynamically when a GUI session attaches, but are absent when the user manager initializes at boot via lingering.

To supply environment variables explicitly to user units, define an Environment= directive inside the unit file, or set user-wide manager environment blocks using environment.d:

# Placed in ~/.config/environment.d/10-user-env.conf
PATH=/home/alice/.local/bin:/usr/local/bin:/usr/bin:/bin
DATA_DIR=/home/alice/data

Unprivileged socket activation

User units support socket activation via .socket unit files. Because unprivileged users cannot bind to privileged TCP ports (ports lower than 1024), user socket units must bind to unprivileged ports (port 1024 and higher) or Unix domain sockets.

[Unit]
Description=Laboratory Application User Socket

[Socket]
ListenStream=127.0.0.1:8080
ListenStream=/run/user/%U/labapp.sock

[Install]
WantedBy=sockets.target

When traffic arrives on port 8080 or the Unix domain socket, the user manager activates labapp.service and passes the file descriptor to the service process, enabling socket-activated user daemons.

Common mistakes and pitfalls

1. Placing user units in system unit paths

Placing user service files in /etc/systemd/system/ instead of ~/.config/systemd/user/ (or /etc/systemd/user/) causes systemd to attempt to run the service under PID 1 with root context, or fails due to missing user path variables. Always place unprivileged user services in ~/.config/systemd/user/.

2. Assuming lingering is enabled by default

Engineers frequently configure a user systemd service using systemctl --user enable labapp.service and expect it to run indefinitely on a server. Upon logging out of SSH, the process terminates. Enabling user unit autostart via systemctl --user enable only guarantees startup when the user manager starts. Lingering must be explicitly activated using loginctl enable-linger <username> for the service to start at boot and survive logouts.

3. Attempting to bind privileged ports in user units

User units execute without root privileges. Attempting to set ListenStream=80 or ListenStream=443 in a user socket unit results in a permission denied error (EACCES). Use unprivileged ports (e.g., 8080) or assign explicit Linux capabilities (such as CAP_NET_BIND_SERVICE) via ambient capabilities or socket proxies if port numbers below 1024 are required.

4. Relying on shell profile environment variables

Relying on variables exported in ~/.bashrc inside a user service file leads to subtle failures. When lingering boots user@UID.service at system startup, no interactive shell is spawned, so ~/.bashrc is never parsed. Always define explicit environment variables using Environment= directives within the unit file or environment drop-ins in ~/.config/environment.d/.

5. Running sudo systemctl --user

Executing sudo systemctl --user is a common operational mistake. Running systemctl --user under sudo attempts to connect to the root user’s manager socket while referencing the invoking user’s environment, resulting in connection failure or mismatched D-Bus session permissions. Never use sudo when managing user services with systemctl --user.

Key takeaways

  • User Systemd Managers: Executed as unprivileged instances of systemd --user managed by user@UID.service under PID 1.
  • Lookup Directories: User unit files reside in ~/.config/systemd/user/ (user-specific), /etc/systemd/user/ (system-wide user overrides), and /usr/lib/systemd/user/ (vendor packages).
  • Session Lifecycle: Default user managers are spawned by systemd-logind via pam_systemd on login and terminated along with all processes on session logout.
  • Lingering: loginctl enable-linger <user> forces systemd-logind to spawn the user manager at boot and keep it active across user logouts.
  • Port and Privilege Limits: User managers cannot bind to network ports below 1024 without explicit privilege delegation, and inherited environment variables differ from interactive login shells.
