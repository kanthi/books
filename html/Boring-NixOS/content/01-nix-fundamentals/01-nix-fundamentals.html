Nix Fundamentals — How It Actually Works

The traditional operating system model is mutable: packages overwrite shared files in /usr/lib and /usr/bin, creating unpredictable state and silent breakage. The boring default of Nix is: every package is an immutable, content-addressed path under /nix/store, determined strictly by cryptographic hashes of its inputs.

Mental model

In traditional package managers (apt, dnf, brew), installing package A can silently upgrade library B, breaking package C that depended on the old version of B. This is the root cause of dependency rot and non-reproducible environments.

Nix solves this by treating software installations like a pure functional evaluation:

  1. The Nix Store (/nix/store): Every artifact lives in an isolated directory whose path includes a cryptographic hash, such as /nix/store/s69al102...-ripgrep-14.1.0.
  2. Deterministic Hashes: The hash is computed from all inputs that produce the package: source code, compiler flags, dependencies, and build scripts. If any dependency changes by a single bit, the output path changes.
  3. No Ambient State: Builds run inside isolated sandboxes without access to the host network or root filesystem. A program cannot inadvertently link against whatever compiler happened to be installed in /usr/bin.
  4. Symlink Trees: Environments and user profiles are symlink trees pointing to specific /nix/store paths. Upgrading or switching environments simply means swapping a symlink.
  5. Garbage Collection: Deleting a package removes the symlink from your profile. The underlying store paths remain safely until nix-collect-garbage cleans unreferenced store entries.
/nix/store/
├── a1b2c3d4...-glibc-2.39/
├── f9e8d7c6...-ripgrep-14.1.0/  -> references glibc-2.39
└── b7a6c5d4...-ripgrep-14.0.0/  -> references older glibc

Both versions coexist on the same disk without collision or conflict.

Worked examples

Case 1: Inspecting the Nix Store

Check where an installed utility actually lives on disk.

Run:

which rg

Output:

/nix/store/z1k947f6y788sfaivs931h26hsvb3506-ripgrep-14.1.0/bin/rg

Notice that the binary does not reside in /usr/bin/rg. It is an immutable, isolated path.

Case 2: Querying Exact Runtime Dependencies

Inspect the dependency graph of an executable using nix-store -q --references.

Run:

nix-store -q --references $(which rg)

Output:

/nix/store/7r44p12l4b72j9m9l09k96yghz02f8n7-glibc-2.39
/nix/store/z1k947f6y788sfaivs931h26hsvb3506-ripgrep-14.1.0

Every library needed by rg is explicitly recorded. There are no undeclared ambient dependencies.

Case 3: Evaluating a Pure Expression

Save as hello.nix. A minimal Nix expression that defines a string value.

# hello.nix
let
  greeting = "Hello, reproducible world!";
in
greeting

Run:

nix-instantiate --eval hello.nix

Output:

"Hello, reproducible world!"

Nix is an expression language. Evaluating an expression computes a deterministic value.

Case 4: Creating a Trivially Reproducible Derivation

Save as greeting.nix. A complete self-contained derivation using the built-in derivation primitive.

# greeting.nix
derivation {
  name = "desk-greeting";
  system = builtins.currentSystem;
  builder = "/bin/sh";
  args = [
    "-c"
    "echo 'Desk system operational' > $out"
  ];
}

Run:

nix-build greeting.nix

Output:

these 1 derivations will be built:
  /nix/store/m6a1p...-desk-greeting.drv
building '/nix/store/m6a1p...-desk-greeting.drv'...
/nix/store/k3b29...-desk-greeting

Inspect the generated output:

cat result

Output:

Desk system operational

result is a local symlink pointing directly into /nix/store.

Case 5: Garbage Collection and Roots

Remove the symlink and run garbage collection.

Run:

rm result
nix-collect-garbage

Output:

finding garbage collector roots...
deleting garbage...
deleting '/nix/store/k3b29...-desk-greeting'
1 store paths deleted, 0.00 MiB freed

Because no active symlink (garbage collector root) references desk-greeting, the store reclaims the space.

The trap

Save as bad_build.sh. Trying to run conventional make install or pip install globally directly writes into system directories, creating untracked file clutter.

# bad_build.sh
# Anti-pattern: mutating shared system state
sudo cp myapp /usr/local/bin/myapp

When /usr/local/bin/myapp breaks after an OS update, no tool knows which dependencies it relied upon or how to roll it back.

The fix: Define software as a Nix derivation or shell environment. Every file remains tracked, sandboxed, and reversible.

The boring rule

  • All binaries and libraries belong in /nix/store, never in mutable system paths.
  • Depend on explicit store paths, never on whatever happens to be on $PATH.
  • Use nix-store -q --tree to inspect dependency chains.
  • Run nix-collect-garbage -d periodically to remove stale generations and unreferenced store paths.

Try this

  1. Run nix-store -q --tree $(which nix) and observe the complete tree of dependencies required by the Nix binary itself.
  2. In greeting.nix, modify the greeting text to 'Front desk open' and re-run nix-build. Note how the hash in the resulting /nix/store path changes.
  3. Check your current garbage collector roots using nix-store --gc --print-roots.
