Pulumi ESC: environments, secrets, and dynamic credentials

After this page you can explain what Pulumi ESC adds on top of stack configuration, sketch an environment YAML that holds secrets and non-secrets, open an environment for a pulumi up, and know where ESC stops and stack config begins.

What was and was not run

pulumi and the ESC CLI were not available on the authoring box and installs were not allowed. Layouts, commands and YAML below follow the current Pulumi ESC documentation (pulumi.com/docs/esc/). Marked Not run here where a live CLI would be required.

Thesis

Stack configuration (Part 01) is the right place for values that differ per stack: instance size, region, a feature flag. It is the wrong place to reinvent an organisation-wide secrets store, to duplicate the same database password into twenty stacks, or to mint short-lived cloud credentials by hand.

Pulumi ESC — Environments, Secrets, and Configuration — is Pulumi’s hierarchical environment layer. An environment is a named document (YAML) that can import other environments, pull secrets from providers, and expose a flat set of values to pulumi, CI, or any process that opens it. Stacks then consume those values instead of re-storing them.

Mental model

┌──────────────────────────── ESC environment ────────────────────────────┐
│  imports: [acme/prod-shared]                                            │
│  values:                                                                │
│    aws:     { login: { fn::open::aws-login: … } }   # dynamic creds     │
│    dbPassword: { fn::secret: "…" }                  # encrypted secret  │
│    region: us-east-1                                # plain config      │
└──────────────────────────┬──────────────────────────────────────────────┘
                           │  pulumi config env add  /  esc run
                           ▼
                 Pulumi stack (dev / prod)
                 program reads config + OIDC/env
Layer Owns Lifetime
ESC environment Shared secrets, provider logins, org defaults Independent of any one stack
Stack configuration Per-stack overrides (instanceType, feature flags) Bound to that stack’s state
Program code How resources are declared Versioned in git

An environment document

Environments live in the Pulumi Cloud (or a self-hosted backend that supports ESC) and are edited as YAML. A minimal shape looks like this (illustrative; Not run here):

values:
  region: us-east-1
  dbPassword:
    fn::secret: "replace-me"
  # Dynamic credentials are opened when the environment is opened,
  # not stored as long-lived static keys in the document.
  aws:
    login:
      fn::open::aws-login:
        oidc:
          duration: 1h
          roleArn: arn:aws:iam::123456789012:role/pulumi-deploy
          sessionName: pulumi-esc

Points that matter in review:

  1. fn::secret marks a value as secret so ESC encrypts it at rest and redacts it in logs, the same class of protection stack secrets get.
  2. fn::open::… providers mint dynamic values (OIDC cloud logins, vault reads) at open time. The document stores how to open them, not the raw credential.
  3. Imports let a leaf environment pull in acme/prod-shared and override only what must differ.

Opening an environment for a stack

Two common operator paths (commands from the docs; Not run here):

# Attach an environment to a stack so `pulumi up` sees its values
pulumi config env add acme/prod-shared

# Or run an arbitrary command with the environment opened into the process
esc run acme/prod-shared -- pulumi up

Once attached, values appear to the program through the usual config APIs (pulumi.Config().require_secret("dbPassword"), provider env vars from the login provider, and so on). Prefer reading secrets through the config/secret APIs rather than printing them.

ESC vs stack secrets (chapter 03)

Concern Stack pulumi config set --secret ESC environment
Scope One stack Many stacks / many projects via imports
Rotation Edit that stack Edit once in the environment
Dynamic cloud login Manual / external OIDC wiring First-class fn::open:: providers
Local plaintext Pulumi.<stack>.yaml Encrypted ciphertext in the stack file Values live in the ESC service; stack keeps a reference

Keep per-stack knobs in stack config. Promote anything shared or short-lived into ESC.

Common mistakes

  • Duplicating the same fn::secret into every stack YAML “for convenience” — you lose rotation and audit.
  • Treating ESC as a replacement for least-privilege IAM: an opened OIDC role should still be scoped to the deploy task.
  • Logging opened values in CI (echo $DB_PASSWORD) — redaction in ESC does not protect a shell that prints them.
  • Assuming every backend supports ESC the same way — confirm your Pulumi Cloud / self-host version before designing around imports.

Exercises

  1. Sketch an environment that imports acme/base and overrides only region.
  2. List three values in your current project that should move from stack config to ESC, and three that should stay.
  3. (Not run here) On a machine with ESC configured, run esc open <env> --format json and confirm secrets are redacted in the default view.

Summary

ESC is the shared, hierarchical layer for secrets and dynamic credentials; stack configuration remains the per-stack dial. Open an environment for a deploy, keep long-lived static keys out of git, and rotate once at the environment rather than twenty times at the stack.
