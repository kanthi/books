Copy Range Types: core::range and Why a..b Was Never Copy

After this page you can explain why std::ops::Range cannot implement Copy, use the new core::range types stabilized in Rust 1.95.0 and 1.96.0 to store copyable range spans in your structs, convert smoothly between legacy and modern ranges, index slices directly with them, and design clean APIs that accept both.

The problem: structs, spans, and error E0204

Engineers who build parsers, compilers, text editors, and binary protocols frequently model sub-slices and byte spans. A span is conceptually trivial: a pair of indices marking the beginning and end of a token or buffer region. Because a pair of usize values is small (typically 16 bytes on a 64-bit target) and possesses pure value semantics, such descriptors should naturally implement Copy.

For years, the intuitive way to declare such a span in Rust was to reuse the standard library range type:

#[derive(Clone, Copy, Debug)]
pub struct SourceSpan {
    pub range: std::ops::Range<usize>,
}

fn main() {
    let span = SourceSpan { range: 0..10 };
    let copy = span;
    println!("{copy:?}");
}

Attempting to compile this code with rustc --edition 2024 span_error.rs fails immediately with compiler error E0204:

error[E0204]: the trait `Copy` cannot be implemented for this type
 --> span_error.rs:2:12
  |
1 | #[derive(Clone, Copy, Debug)]
  |                 ---- in this derive macro expansion
2 | pub struct SourceSpan {
  |            ^^^^^^^^^^
3 |     pub range: std::ops::Range<usize>,
  |     --------------------------------- this field does not implement `Copy`

Because std::ops::Range<usize> does not implement Copy, any structure containing it as a field cannot derive Copy either. For years, Rust programmers were forced to choose between annoying workarounds: 1. Reimplement custom pair types such as struct Span { start: usize, end: usize } and manually write conversions. 2. Store (usize, usize) tuples, losing the semantic intent and slice-indexing conveniences of range types. 3. Drop Copy from enclosing structs and sprinkle .clone() calls across every AST pass, token visitor, and slice utility.

To understand why Rust was designed this way, we have to examine the relationship between ranges and iterators in early Rust.

Why std::ops::Range was never Copy

In Rust 1.0, convenience won out over clean separation of concerns. To make for i in 0..10 work without requiring explicit method calls like (0..10).iter(), std::ops::Range<Idx> was defined directly as an Iterator:

impl<Idx: Step> Iterator for std::ops::Range<Idx> {
    type Item = Idx;
    fn next(&mut self) -> Option<Idx> { ... }
}

In std::ops::Range, the range boundary descriptor and the iteration cursor are the exact same data structure. The start field serves as the moving pointer that is incremented on every invocation of Iterator::next().

Making an active iterator Copy creates severe semantic traps. An iterator represents an ongoing traversal through a sequence. If an iterator were Copy, passing it by value to a helper function, evaluating it in an expression, or assigning it to a temporary variable would silently copy its internal state.

The small program below illustrates the hazard using explicit Clone on a partially consumed std::ops::Range:

fn main() {
    let mut original = 0..6;

    // Consume the first item: 0
    let first = original.next();

    // Fork the cursor state midway through iteration
    let mut forked = original.clone();

    // Advance both streams independently
    let second_original = original.next();
    let second_forked = forked.next();

    println!("original: first={first:?}, second={second_original:?}");
    println!("forked:   next={second_forked:?}");
}

Running rustc --edition 2024 fork.rs && ./fork produces:

original: first=Some(0), second=Some(1)
forked:   next=Some(1)

Notice what happened: both original and forked independently yield the number 1. With an explicit .clone() call, this duplication of traversal state is visible in source code. But if std::ops::Range implemented Copy, every pass-by-value would implicitly duplicate the iteration cursor.

Consider an iterator consumer like take_two(mut it: impl Iterator): passing an iterator into it would leave the caller’s copy untouched at its prior position rather than advancing the caller’s cursor. Because implicit cursor forking contradicts standard iterator expectations, Rust made the deliberate decision that types implementing Iterator should almost never implement Copy. Consequently, std::ops::Range could never be Copy.

The new types in core::range

The permanent solution is to separate the range descriptor (the geometric interval) from the iteration cursor (the transient traversal state). This design was codified in RFC 3550 and implemented in the standard library:

  • Rust 1.95.0 stabilized the module core::range along with core::range::RangeInclusive and core::range::RangeInclusiveIter.
  • Rust 1.96.0 stabilized core::range::Range, RangeIter, RangeFrom, RangeFromIter and RangeToInclusive. (RangeToInclusive has no start, so it has no iterator type.)
  • The same types are re-exported as std::range, so std::range::Range and core::range::Range name one type.

These modern types represent pure bounds. When their underlying bound types implement Copy (such as usize), the range types themselves implement Copy.

Type Legacy counterpart Implements Iterator? Implements Copy? Public fields
core::range::Range<T> std::ops::Range<T> No (IntoIterator) Yes (if T: Copy) start, end
core::range::RangeInclusive<T> std::ops::RangeInclusive<T> No (IntoIterator) Yes (if T: Copy) start, last
core::range::RangeFrom<T> std::ops::RangeFrom<T> No (IntoIterator) Yes (if T: Copy) start
core::range::RangeToInclusive<T> std::ops::RangeToInclusive<T> No Yes (if T: Copy) last

Notice a crucial structural detail for RangeInclusive: in core::range::RangeInclusive, the upper boundary field is named last, reflecting that the bound is inclusive, while core::range::Range retains start and end.

IntoIterator vs Iterator: decoupling bounds from traversal

Because modern range types do not implement Iterator, they cannot be directly polled via .next(). Instead, they implement IntoIterator.

When you want an iterator, you produce one by value via into_iter() or by reference via .iter():

use core::range::Range;

let r = Range { start: 0, end: 5 };

// Produce an iterator cursor explicitly
let mut iter = r.iter();
assert_eq!(iter.next(), Some(0));

// The original range r was NOT consumed or mutated because r is Copy!
assert_eq!(r.start, 0);
assert_eq!(r.end, 5);

The resulting iterator is core::range::RangeIter<T>, a dedicated cursor type. RangeIter implements Iterator, but RangeIter does not implement Copy. This cleanly separates responsibilities: - Range<T> is the immutable or copyable interval description. - RangeIter<T> is the mutable, non-copyable state machine driving traversal.

Because IntoIterator is the trait that powers Rust’s for loops, range types can be passed directly to for loops without boilerplate:

let r = Range { start: 1, end: 4 };

for val in r {
    // Under the hood, this calls r.into_iter()
}

// Because r is Copy, r is still valid here!
let again = r;

This resolves the long-standing tension: intervals can be freely copied, while loops and iteration remain clean and safe.

Syntax and converting between legacy and new

In Rust edition 2024, built-in range syntax (a..b, a..=b, a..) continues to produce legacy std::ops types. Making a..b emit core::range::Range is a breaking change for code that calls .next() directly on a..b or passes a..b to functions expecting std::ops::Range.

A future edition is planned to make the standard range syntax produce the modern core::range types by default. Until that planned edition arrives, working with modern ranges requires explicit construction or conversion.

Converting from legacy to modern ranges

Modern ranges implement From for their corresponding legacy types:

use core::range::{Range, RangeFrom, RangeInclusive};

// From half-open syntax:
let r: Range<usize> = Range::from(0..10);

// From inclusive syntax:
let inc: RangeInclusive<usize> = RangeInclusive::from(1..=5);

// From unbounded-end syntax:
let from: RangeFrom<usize> = RangeFrom::from(100..);

You can also construct core::range::Range directly using struct syntax, since its fields are public:

let r = core::range::Range { start: 10, end: 20 };

Converting from modern ranges to legacy ranges

Modern ranges also implement Into<std::ops::Range>:

use core::range::Range;

let modern = Range { start: 5, end: 15 };

// Convert back to std::ops::Range
let legacy: std::ops::Range<usize> = modern.into();
assert_eq!(legacy, 5..15);

This bidirectional compatibility ensures you can adopt core::range in internal data structures without breaking downstream libraries that still require legacy ranges.

Slicing with core::range

Range types exist primarily for two tasks: iteration and slicing. The new types in core::range implement core::slice::SliceIndex<[T]>. That means you can pass them directly inside bracket indexing operators &slice[r] and &mut slice[r]:

use core::range::Range;

let numbers = [10, 20, 30, 40, 50];
let window = Range::from(1..4);

// Indexing works directly
let sub: &[i32] = &numbers[window];
assert_eq!(sub, &[20, 30, 40]);

You do not need to convert modern ranges back to std::ops ranges before indexing slices, strings, or vectors.

Worked example: a complete copyable span

The following standalone program demonstrates the complete lifecycle of modern ranges: deriving Copy on an enclosing data structure, bitwise copying, iterating via both into_iter() and .iter(), using RangeInclusive::contains(), consuming an unbounded RangeFrom, slicing a backing array, and converting back to legacy std::ops::Range.

use core::range::{Range, RangeFrom, RangeInclusive};

#[derive(Clone, Copy, Debug)]
struct Span {
    r: Range<usize>,
}

fn main() {
    // 1. Construct Span and demonstrate that it is Copy
    let span1 = Span {
        r: Range::from(0..4),
    };
    let span2 = span1; // Bitwise copy!

    println!("span1: {:?}, span2: {:?}", span1, span2);

    // 2. Iterate via into_iter()
    print!("span1.r.into_iter(): ");
    for x in span1.r.into_iter() {
        print!("{x} ");
    }
    println!();

    // 3. Iterate via iter()
    print!("span2.r.iter(): ");
    for x in span2.r.iter() {
        print!("{x} ");
    }
    println!();

    // 4. Use RangeInclusive::from(1..=3) with contains
    let inc = RangeInclusive::from(1..=3);
    println!("inc.contains(&2): {}", inc.contains(&2));
    println!("inc.contains(&4): {}", inc.contains(&4));

    // 5. Use RangeFrom::from(7..).iter().take(2)
    print!("RangeFrom::from(7..).iter().take(2): ");
    for x in RangeFrom::from(7..).iter().take(2) {
        print!("{x} ");
    }
    println!();

    // 6. Slice an array directly with the modern range
    let data = [100, 200, 300, 400, 500, 600];
    let subslice = &data[span1.r];
    println!("subslice: {:?}", subslice);

    // 7. Convert back to legacy std::ops::Range with .into()
    let legacy: std::ops::Range<usize> = span1.r.into();
    println!("converted to legacy: {:?}", legacy);
}

Running rustc --edition 2024 span.rs && ./span produces:

span1: Span { r: 0..4 }, span2: Span { r: 0..4 }
span1.r.into_iter(): 0 1 2 3 
span2.r.iter(): 0 1 2 3 
inc.contains(&2): true
inc.contains(&4): false
RangeFrom::from(7..).iter().take(2): 7 8 
subslice: [100, 200, 300, 400]
converted to legacy: 0..4

Notice what to look for when running this binary: - span1 and span2 print identical range boundaries, confirming the copy succeeded without error E0204. - Both into_iter() and iter() visit the indices 0 1 2 3. - inc.contains(&2) evaluates to true, while inc.contains(&4) evaluates to false. - RangeFrom::from(7..) generates numbers starting at 7, and .take(2) caps iteration at two items (7 and 8). - The subslice retrieves the first 4 elements from data ([100, 200, 300, 400]). - The legacy conversion prints 0..4 as an std::ops::Range.

API design guidance: when and how to expose modern ranges

When updating your libraries for modern Rust, follow these guidelines to balance ergonomics with backwards compatibility.

Store core::range in structs

Whenever a data structure needs to retain an interval—such as token spans in an AST, buffer view offsets, or memory windows—store core::range::Range<usize> instead of std::ops::Range<usize>. This allows your struct to derive Copy, Eq, and Hash whenever the index type supports them, removing the .clone() calls that a non-Copy field forces on every caller.

Accepting ranges in public functions

Because a..b still creates legacy ranges in edition 2024, requiring callers to write Range::from(a..b) at every call site is unergonomic. To accept both legacy syntax and modern ranges, write function signatures that accept impl Into<core::range::Range<usize>>:

use core::range::Range;

pub fn extract_region(data: &[u8], bounds: impl Into<Range<usize>>) -> &[u8] {
    let r: Range<usize> = bounds.into();
    &data[r]
}

fn demo() {
    let buf = b"hello world";

    // Call with legacy syntax:
    let _ = extract_region(buf, 0..5);

    // Call with modern Copy range:
    let modern = Range { start: 6, end: 11 };
    let _ = extract_region(buf, modern);
}

This pattern provides the best of both worlds: zero friction for callers using literal range syntax 0..5, and zero friction for callers passing copyable Range fields stored in structs.

Pitfalls

1. Assuming range syntax emits modern ranges in edition 2024

Writing let r = 0..10; in Rust edition 2024 still produces std::ops::Range<i32>. Do not expect r to be Copy. If you need a copyable range, you must explicitly write Range::from(0..10) or construct core::range::Range { start: 0, end: 10 }. Range syntax will change only in a planned future edition.

2. Calling .next() directly on core::range::Range

Because modern ranges are not iterators, calling r.next() will fail to compile. You must obtain an iterator cursor first:

use core::range::Range;

let r = Range::from(0..5);

// Compiler error: no method named `next` found for struct `core::range::Range`
// r.next();

// Correct:
let mut iter = r.iter();
let first = iter.next();

3. Re-iteration behavior differences

With legacy ranges, passing an iterator into a loop consumes it permanently:

let mut legacy = 0..3;
for x in legacy.by_ref() { /* ... */ }
// legacy is now exhausted!

With modern ranges, calling for x in r passes r by value. Because Range implements Copy, the original variable r remains intact, and iterating over it a second time starts traversal fresh from start:

use core::range::Range;

let r = Range::from(0..3);
for _ in r {}
for x in r {
    // Executes again! Starts from 0.
}

While this matches user expectations for collections, programmers accustomed to legacy ranges may mistakenly expect r to be consumed.

4. Field names in RangeInclusive

In core::range::RangeInclusive, the upper boundary is stored in the public field last, not end:

use core::range::RangeInclusive;

let inc = RangeInclusive::from(1..=10);
assert_eq!(inc.start, 1);
assert_eq!(inc.last, 10); // Field is `last`, not `end`

Accessing .end on RangeInclusive will result in a field resolution error.

Summary

  • std::ops::Range could never implement Copy because it implements Iterator. Copying an iterator implicitly would cause silent cursor forking and confusing traversal bugs.
  • core::range and RangeInclusive were stabilized in Rust 1.95.0.
  • core::range::Range, RangeFrom, RangeToInclusive and their iterator types were stabilized in Rust 1.96.0 (and are re-exported in std::range).
  • Modern range types represent pure bounds and implement Copy when their bound types implement Copy.
  • Modern ranges do not implement Iterator. They implement IntoIterator; call .iter() or .into_iter() to create a non-copyable RangeIter cursor.
  • Range syntax a..b still produces legacy std::ops::Range in edition 2024. A future edition is planned to transition range syntax to modern ranges.
  • You can convert between legacy and modern ranges seamlessly using Range::from(a..b) and .into().
  • Modern ranges can directly index slices via &slice[r].
  • Store core::range::Range in custom types like spans and AST nodes to make them Copy, and accept impl Into<Range<usize>> in public function signatures for maximum caller convenience.
