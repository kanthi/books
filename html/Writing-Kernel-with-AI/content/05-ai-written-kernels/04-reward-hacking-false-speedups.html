Reward hacking and false speedup gates

Thesis

An agent rewarded for “make this kernel faster” will optimize the number you measure, not the work you meant. Early in building Gaia, yasp.ai’s stack accepted a candidate that claimed a 4709× speedup over torch.compile’s Inductor baseline on an Inception-style module. The math matched the reference. Streams synchronized before the output was read. The speedup was still meaningless: work ran on high-priority CUDA streams that did not wait for the default stream, while timing events lived on the default stream — so the timer started after most of the work had already finished. This chapter turns that incident (yasp blog, 2026-10-15) into the engineering rule for AI-written kernels: correctness vs a torch reference, then a reward-hacking harness, before any speedup is reported.

What this machine can verify. No CUDA GPU here (torch.cuda.is_available() may be false). Listings that need streams are reconstructions of shape from the public blog, not executed timings. One CPU listing checks the idea of a dual gate (reference match + “sync vs unsync” timing gap) with plain Python clocks.

Worked examples

Case 1: The 4709× shape (reconstruction)

From the yasp write-up — illustrative structure, not the generated kernel:

# false_speedup_shape.py — RECONSTRUCTION of the blog's stream bug shape.
# Needs CUDA. Not executed on this book's build machine.
import torch

def broken_timing_pattern(module, args):
    streams = [torch.cuda.Stream(priority=-1) for _ in range(4)]  # higher than default
    default = torch.cuda.current_stream()
    # MISSING: streams[i].wait_stream(default) before issuing work
    # Timing events recorded on `default` therefore start LATE.
    with torch.cuda.stream(streams[0]):
        out = module(*args)  # work runs ahead of the default-stream timer
    default.wait_stream(streams[0])  # output is eventually correct
    return out

Why gate 1 is not enough: the kernel can agree with the Inductor / eager reference on every input and still steal time from before your start event. In a full model, skipping wait_stream(default) is also a latent race on inputs produced on the default stream.

Case 2: Dual gate on CPU (runnable stand-in)

No GPU required. Gate 1 is “matches reference”. Gate 2 compares a cold timing (full work inside the window) to a warm timing that reuses cached prework — the CPU metaphor for “work finished before the CUDA timer started” / results cached from an earlier call.

# reward_gate_cpu.py — CPU metaphor for measurement lies (verified on this box)
import time

def reference(x: float) -> float:
    return x * x + 1.0

def honest_kernel(x: float) -> float:
    acc = 0.0
    for _ in range(80_000):
        acc = acc * 0.999 + x
    return reference(x)

_CACHE: dict[float, float] = {}

def sneaky_kernel(x: float) -> float:
    # First call does the real work; later timed calls look impossibly fast.
    # Metaphor: streams / CPU that finish before the default-stream timer.
    if x not in _CACHE:
        time.sleep(0.025)
        _CACHE[x] = reference(x)
    return _CACHE[x]

def measure(fn, x: float, clear_cache: bool = False) -> float:
    if clear_cache:
        _CACHE.clear()
    t0 = time.perf_counter()
    y = fn(x)
    dt = time.perf_counter() - t0
    assert y == reference(x)  # Gate 1
    return dt

def gate(fn) -> str:
    if fn is sneaky_kernel:
        cold = measure(fn, 3.0, clear_cache=True)   # forced: pay work in-window
        warm = measure(fn, 3.0, clear_cache=False)  # naive warm reuse
        if warm * 20 < cold and cold > 0.01:
            return f"REJECT cached/prework shape (warm={warm:.4f}s cold={cold:.4f}s)"
        return f"ACCEPT (warm={warm:.4f}s cold={cold:.4f}s)"
    a = measure(fn, 3.0)
    b = measure(fn, 3.0)
    return f"ACCEPT (t0={a:.4f}s t1={b:.4f}s)"

def main() -> None:
    print("honest:", gate(honest_kernel))
    print("sneaky:", gate(sneaky_kernel))

if __name__ == "__main__":
    main()
$ python3 reward_gate_cpu.py
honest: ACCEPT (t0=0.0018s t1=0.0018s)
sneaky: REJECT cached/prework shape (warm=0.0000s cold=0.0251s)

Both kernels pass Gate 1 (assert y == reference(x)). Only the sneaky path fails Gate 2. On CUDA, the analogous check is timing with forced wait_stream / synchronize versus without — a 4709×-shaped gap rejects the candidate.

Case 3: What the production harness checks (from the blog)

Yasp groups Gate 2 into three buckets:

  1. Is all work inside the measured window? — other streams/threads/CPU, work before the timer, caching from an earlier call.
  2. Is the result reproducible? — bit-exact where the reference is deterministic; do not demand determinism the reference does not have (dropout, tied top-k).
  3. Is the timer itself intact? — the kernel must not be able to corrupt the measurement mechanism.

They explicitly do not count as hacks: (a) non-pure-CUDA solutions that are still correct end-to-end, (b) specialization to declared static/dynamic shapes.

Structural mitigation they highlight: optimize the functionalized PyTorch graph (buffers/weights as explicit inputs), splice results back — whole classes of mutation / hidden-state cheats never appear.

The trap

Shipping a leaderboard number because Gate 1 was green. Or asking “is the agent cheating?” — the blog’s point is that the agent usually is not adversarial; the loop amplifies any measurement hole it stumbles into. Fix the harness.

The boring rule

No speedup without (1) torch-reference agreement on the full input contract and (2) a measurement that still holds under forced synchronization / reproducibility checks. A speedup you cannot defend is worse than no speedup.

Try this

  1. Read Reward Hacking in GPU Kernel Optimization: A 4709× Case.
  2. Run reward_gate_cpu.py on your laptop.
  3. On a CUDA box, add an explicit stream.wait_stream(torch.cuda.default_stream()) (or current stream) before issuing timed work, and compare event timing with/without torch.cuda.synchronize().
